# Как здесь работать

Этот файл читают исполнители — люди и программы. В нём правила работы в дереве:
у каждого названа причина и команда, а там, где правило проверяет машина, — хук
или работа CI, которая его проверяет.

## Дерево

Компилятор flang написан на flang и печатает сам себя в C и ещё в девять языков.
Второй реализации языка нет.

```
bootstrap/          компилятор, напечатанный в C99 и закоммиченный; из него собирается bootstrap/flang
flang/self/         исходники компилятора, на flang
flang/stdlib/       библиотека, на flang
flang/concurrency/  процессы, надзор, планировщик, связь между узлами
flang/proof/        независимая проверка доказательств, пробы, таблицы
flang/src/emit/     рантаймы десяти целей; копируются в вывод дословно
docs/flang/         контракты языка: SPEC.md каждого слоя
docs/tasks/         открытые задачи, файл на задачу
scripts/            проверки дерева, пересборка bootstrap/, выпуск, сайт
.flangrc            настройки и короткие команды: строки script.<имя> = <команда>
```

Полная раскладка — `docs/repository-layout.ru.md`.

## Сборка

```sh
git submodule update --init      # packaging/homebrew-tap и packaging/asdf-plugin
make -C bootstrap                # нужны sh, make и cc
bootstrap/flang --version
```

`compiler_flang.c` — одна единица трансляции на 56 МБ, поэтому `-j` сборку не
ускоряет. Замер 27 ноября 2026 на машине разработки:
`make -C bootstrap -j8 CFLAGS='-std=c99 -O2'` с чистого дерева — 12 мин 56 с.
С флагами `Makefile` по умолчанию (к ним добавлен `-flto`) время в этот день не
мерили.

Короткие команды зовутся так: `bootstrap/flang run-script <имя>`. Без имени
команда печатает весь список.

## Правка компилятора попадает в `bootstrap/flang` только пересборкой `bootstrap/`

Правка в `flang/self/**` меняет исходник. Собранный компилятор о ней не знает,
пока `bootstrap/` не напечатан заново:

```sh
sh scripts/bootstrap-reprint.sh            # напечатать bootstrap/ заново
sh scripts/bootstrap-reprint.sh --check    # напечатать и сравнить с закоммиченным байт в байт
sh scripts/bootstrap-reprint.sh --bystro   # сравнить только входы печати, секунды
```

Обе полные команды идут часы на одном ядре. Последние строки
`docs/reprint-ledger.tsv`: печать 22 ноября 2026 — 6886 с и пик 69,2 ГиБ, сверка
15 ноября 2026 — 6246 с и пик 68,2 ГиБ; машина в это время была занята другими
запусками. Порядок работы — `docs/reprint-runs-start-from-a-clean-tree.md`,
цена — `docs/reprint-cost.md`.

Поэтому `bootstrap/` перепечатывают партиями, отдельным коммитом
`chore(seed): …`. Если ваша правка в `flang/self/**` ждёт такой партии, скажите
об этом в теле коммита: проверки, которые идут на `bootstrap/flang`, её ещё не
видят.

## Три правила о порождённых файлах и новых словах

**1. Порождённое руками не правят.** `bootstrap/**` и `scripts/seed-fingerprint`
пишет `scripts/bootstrap-reprint.sh`; `CHANGELOG.md` и `changelog.json` —
`changelog:build`. Причина: ручная правка стирается следующей печатью, а до неё
дерево и компилятор расходятся. Проверяют работа `seed-fingerprint` в
`binary.yml` (`sh scripts/bootstrap-reprint.sh --bystro`) и `changelog:check`
(`pages.yml`, `release.yml`).
Правку рантайма C вносят в `flang/src/emit/c/`.

**2. Новое слово типа вводят и применяют двумя изменениями.** Сначала слово
добавляют в компилятор, не применяя его в позициях типа; затем перепечатывают
`bootstrap/`; затем применяют. Причина: `bootstrap/flang` читает исходники
дерева, и файл со словом, которого он не знает, прочесть не может.
Проверяет работа `seed-words` в `ci.yml`:

```sh
bootstrap/flang run-script seed:type-words
```

**3. Недоказанное постусловие проверяется при работе программы.** Если
`обеспечивает` не доказано, в напечатанный код ставится проверка, и ложное
постусловие остановит программу при первом же вызове — в том числе сам
компилятор после перепечатки. Перед коммитом посмотрите отчёт:

```sh
bootstrap/flang check <файл> --proof
```

## Числа и отчёт о работе

- Число в отчёте, задаче или документе берётся из запуска команды. Рядом
  называют команду, дерево (коммит) и компилятор, которым мерили: то же число из
  соседней копии дерева значит другое.
- Отрицательный результат записывают так же, как положительный.
- Запуск, снятый по времени (код 124 у `timeout`), — это «не измерено», а не
  «не сошлось».
- В отчёте есть раздел о том, что не сделано и что принято без проверки.
- У новой проверки есть проба, которая показывает, что проверка умеет отказать.
  Проверяет `forgery-probe:check` в хуке перед пушем.
- Число в документе помечают так, как описано в `docs/prose-numbers.md`; такие
  пометки сверяет с деревом `prose-numbers-guard` (хук перед пушем, работа
  `prose-numbers` в `ci.yml`).

## Ветка, коммит, запрос на слияние

Работа идёт через запросы на слияние в ветку `dev` репозитория
<https://github.com/digitable-lol/flang>.

```sh
git config core.hooksPath .githooks
git config user.name the-homeless-god && git config user.email zimtir@mail.ru
git fetch origin && git switch -c <приставка>/<тема> origin/dev
…
git push origin <приставка>/<тема>
gh pr create --base dev
```

- **Своя копия дерева.** В общей рабочей копии не работают: чужое перебазирование
  и чужой индекс ломаются без предупреждения. Заводите клон или `git worktree`.
- **Ветка от свежего `dev`.** Иначе в запрос попадут чужие старые коммиты, и
  проверка сообщений отвергнет запрос из-за них.
- **Сообщение коммита — по-английски:** `type(scope): what is now true`,
  заголовок утверждает, что теперь верно. Заголовок попадает в журнал изменений
  дословно. Правила — `docs/commit-messages.md`; проверяют хук `commit-msg` и
  работа `commit-messages` (`commit-messages.yml`) на каждом запросе.
- **`Co-Authored-By` не добавляют.**
- **Скрипты оболочки и Python не растут**, Markdown растёт только в `docs/`,
  `.ai/` и четырёх файлах корня (`README.md`, `AGENTS.md`, `DESCRIPTION.md`,
  `CHANGELOG.md`): новую оснастку пишут планом на flang (`.fscript`). Проверяют хук `pre-commit`
  (`.githooks/no-growth.fscript`) и та же работа `commit-messages`.
- **Добавленная строка flang — не длиннее 120 знаков, ветвления — не глубже
  двух.** Пределы записаны в `.flangrc`; проверяют `pre-commit`
  (`.githooks/lint-growth.fscript`) и работа `commit-messages`.
- **Перед пушем** хук `pre-push` запускает 31 быструю проверку и останавливает
  пуш, если хоть одна красна. Остальное идёт в CI.
- **Имена новых файлов — английские слова**, не кириллица и не транслит.
  Проверяют работы `cyrillic-file-names` и `translit-file-names` в `ci.yml` и
  хук перед пушем. Уже существующий транслит не переименовывают: на эти имена
  ссылаются заметки о выпусках и сборка сайта.

Перечень работ CI — `docs/ci-inventory.md`.

## Что запустить перед запросом

```sh
bootstrap/flang check <файл> --proof          # отчёт о доказательствах файла
bootstrap/flang test <файл|каталог>           # примеры
bootstrap/flang run-script tests              # связь, планировщик и надзор на девяти целях; нужны все тулчейны
bootstrap/flang run-script docs:changed       # страницы со вставками из кода, тронутые веткой
bootstrap/flang run-script jargon:changed     # слова на тронутых страницах для посетителя
```

В описании запроса назовите команды, которые запускали, их вывод и код возврата,
а также то, что запустить не смогли.

Два ключа пределов легко перепутать. `--step-limit N` (он же `--предел-шагов`)
задаёт предел шагов самого компилятора на этот запуск и годится при любой
команде. `--max-steps N` у `io` — предел шагов на один виток плана. Оба ключа
задают предел, а не добавляют к умолчанию: число меньше умолчания предел
опускает.

## Задачи

Одна открытая задача — один файл в `docs/tasks/`; закрытая задача из каталога
удаляется. Взять задачу — вписать себя в шапку отдельным коммитом до начала
работы. Правила — `docs/tasks/README.md`, приоритеты дефектов —
`docs/zero-bug-policy.md`.

```sh
bootstrap/flang run-script tasks:board     # что в работе и что свободно; около двух минут
bootstrap/flang run-script tasks:check     # шапки и номера целы
bootstrap/flang run-script tasks:number    # номер для новой задачи
```

## Слова в текстах

Внутренние слова проекта («семя», «сторож», «ведомость» и подобные) уместны в
задачах и в этом файле. На страницах сайта, в `README.md`, в `man flang`, в
справке и сообщениях компилятора их нет. Правила и список проверяемых страниц —
`docs/guide/writing-documentation.ru.md`, список слов и потолки находок —
`docs/jargon.json`.

```sh
bootstrap/flang run-script jargon:changed   # страницы, тронутые веткой
bootstrap/flang run-script jargon:mine      # то же со списком находок
bootstrap/flang run-script jargon:check     # все страницы; идёт в CI, работа jargon в binary.yml
bootstrap/flang run-script jargon:lower     # опустить потолки до нынешних чисел
```

- У каждой страницы записан потолок находок. Больше потолка — красно; меньше
  потолка — тоже красно, пока потолок не опущен командой `jargon:lower`.
- `jargon:debt` записывает нынешние числа как новые потолки и может их поднять.
  Его запускают после чистки страниц, а не вместо неё.
- Полные проверки `jargon:check` и `jargon:list` идут минуты и занимают
  гигабайты памяти; на общей машине их запускают через очередь (см. ниже).

## Кеш доказательств

Кеш ускоряет повторную проверку и включается переменной `FLANG_PROOF_CACHE=on`.
Файлы лежат в `.flang-cache/proofs/` или по пути из этой переменной; в git они
не идут. Устройство — [ADR-0080](../docs/adr/0080-a-proof-cache-remembers-pure-calls-across-runs.md)
и `docs/site/verdict-cache.ru.md`.

Правило: выпуск на кеш не опирается. Перед меткой всё пересчитывается без
`FLANG_PROOF_CACHE`. Причина: запись кеша — сохранённое утверждение «доказано»,
и подписанную ключом машины запись кеш примет без пересчёта. Основанием для
«доказано» остаётся независимая проверка `flang/proof/checker/checker.c`.

Правило проверяет составное действие `.github/actions/release-without-cache`,
его зовут `binary.yml`, `ci.yml`, `install-path.yml`, `build-macos.yml` и
`release.yml`. На пути выпуска с заданной `FLANG_PROOF_CACHE` работа падает
кодом 1. Режим `workflows` того же действия запрещает работам самим задавать эту
переменную, режим `self-test` проверяет само действие.

## Выпуск

Порядок выпуска с командами — `docs/releasing.md`. Правила, которые проверяет
машина:

- **Кран Homebrew и плагин asdf — отдельные репозитории**
  (`digitable-lol/homebrew-tap`, `digitable-lol/asdf-flang`), в дереве они
  подключены сабмодулями `packaging/homebrew-tap` и `packaging/asdf-plugin`.
  `brew` и `asdf` ставят из них, а не из `packaging/homebrew/` и
  `packaging/asdf/`. Версию, адрес и sha256 формулы и файлы плагина сверяют
  `homebrew-formula:check` и `asdf-plugin:check` в `install-path.yml` и в
  `release.yml` до выкладки архива. Без развёрнутых сабмодулей обе проверки
  красны.
- **Заметка о версии вписана в `docs/release-notes.json` до метки.** Из неё
  `scripts/site/release-body.fscript` собирает текст релиза на GitHub; без
  заметки `release.yml` останавливается до сборки архива. Текст релиза руками не
  пишут.
- **Заметка — четыре списка:** `исправления`, `ломающие`, `улучшения`,
  `известные`, в каждой половине (`ru`, `en`) и с заголовком в одно
  предложение. Пункт — одна строка до 160 знаков с приставкой `[компонент]`, без
  `**` и без пояснений в скобках, кроме «(было X)». Проверяет
  `releases:page:check` (`ci.yml`, `release.yml`).

## На общей машине разработки

Этот раздел относится только к машине, где под одной учётной записью работают
несколько исполнителей. На своей машине он не нужен.

Тяжёлые запуски идут через очередь, которая считает память:

```sh
PAMYAT=45G /srv/flang-rabota/vorota/flang-vorota -- <команда>
/srv/flang-rabota/vorota/flang-vorota --schet      # сколько памяти роздано и кто её держит
/srv/flang-rabota/vorota/flang-vorota --snyat 3    # снять запуск с места 3
```

| переменная | что значит |
|---|---|
| `PAMYAT` | предел адресного пространства запуска; его просят с запасом над измеренным пиком, иначе запуск умрёт у предела |
| `PIK` | измеренный пик занятой памяти (`/usr/bin/time -f '%M'`); очередь считает по нему, если он назван |
| `VETVEY` | сколько процессов flang запуск порождает внутри себя |
| `INDIVISIBLE=yes` | запуск нельзя снимать на середине (перепечатка `bootstrap/`) |

- От одного исполнителя — не больше двух тяжёлых запусков разом: машину
  останавливает сумма запусков, а не размер одного.
- `pkill` и `killall` не используют: учётная запись общая, и команда снимет
  чужие запуски. Снимают по месту, `--snyat`. Перед `kill` по номеру проверьте,
  что процесс ваш: `ls -l /proc/<номер>/cwd`.
- Служба `flang-memory-watchdog` снимает самый крупный запуск, когда свободной
  памяти меньше 45 ГиБ, и пишет об этом в `/srv/work/storozh-pamyati.log`.
  Запуск пропал без объяснения — сначала посмотрите этот файл.
- Файлы, над которыми начинаете работать, объявляют заранее:
  `/srv/priyom/claim взять <ветка> <файл>...`; `claim` без доводов показывает,
  кто что держит.
