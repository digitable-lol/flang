## Раздвоенный `origin`: числа, снятые с зеркала, спорят с числами с GitHub

18 августа на этом споткнулись трое подряд, и стоит это одной команды:

```
git remote -v
  origin  /home/a/projects/flang                    (fetch)   ← ЗЕРКАЛО
  origin  https://github.com/digitable-lol/flang.git (push)   ← НАСТОЯЩИЙ
```

**`fetch` и `push` у одного имени ведут в разные места.** `git fetch origin`
тянет с локального зеркала, `git push origin` толкает на GitHub. Зеркало
обновляют руками, и оно отстаёт: 18 августа на нём стоял `f56409b`, а на
GitHub — `b30e4edd`, и между ними лежала ветка двоичного с 36 переименованиями.

**Следствие, из-за которого это опасно:** числа, снятые с зеркала, и числа,
снятые с GitHub, **оба верны про своё дерево** и противоречат друг другу.

| | зеркало `f56409b` | GitHub `b30e4edd` |
|---|---:|---:|
| `«Обстановка терма»` в `self/proofterm.flang` | 0 | 49 |
| `«Собрать поле ядра»` в `self/` | 0 | 308 |
| `«В ёлочках обязательств»` в `self/` | 0 | 74 |
| `«Строка функции ведомости»` в `self/` | 0 | 36 |

Замер, сделанный по всем правилам, дал вывод «переименований нет ни одного» —
и вывод был неверен, потому что мерили не то дерево. Проверка была правильной,
данные — нет.

**Два правила, и второе появилось из-за первого.**

1. Указание, пришедшее с чужими числами, проверяется теми же числами ДО правки.
   Имя цели переименования обязано существовать в дереве: ноль вхождений цели
   значит «переименовывать не во что», и такая правка есть удаление.
2. **Сперва проверь, на что смотрит `origin`.** Прежде чем мерить дерево —
   `git remote -v` и `git rev-parse origin/main`. Расходятся `fetch` и `push` —
   заведи настоящий удалённый отдельным именем и тяни с него:

```
git remote add github https://github.com/digitable-lol/flang.git
git fetch github && git rebase --onto github/main <база> <ветка>
```

Первое правило без второго не спасает: оно говорит «проверь числами», а числа
берутся из того же протухшего дерева.

## Потолок рабочего пути ходит только вниз: правило печати нельзя класть «к своим»

`flang/test/rabochiy-put.test.mjs` меряет, сколько файлов и строк JavaScript
поднимается в процесс на обычном `flang check`, и держит потолок: **20 файлов,
29 722 строки**. Правило одностороннее — число может падать (каждый
переключённый на flang слой его опускает) и не может расти.

Ловушка в том, что нарушить его легко из лучших побуждений. Сторож печати
просился в `flang/src/conc.mjs` — там таблица возможностей целей и два таких же
сторожа рядом, и довод «одно знание не должно лежать в двух файлах» здесь
обычно решающий. Сто строк подняли путь до 29 822, и тест покраснел.

**Куда класть общее правило печати.** В `flang/src/`, рядом с
`target-occupied.mjs` и `target-plan.mjs`, — эти файлы `check` не грузит, и в
потолок они не входят. В сам `flang/src/emit/` класть нельзя: каталог — реестр
бэкендов, и всякий `.mjs` в нём становится ещё одной целью печати
(`flang emit --target plans`). На этом уже спотыкались дважды.

**Как проверить до коммита:**

```
node --test flang/test/rabochiy-put.test.mjs
```
