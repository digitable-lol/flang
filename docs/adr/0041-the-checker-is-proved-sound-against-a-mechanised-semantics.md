## 1. Что доказано сегодня, и о чём эта теорема НЕ говорит

Сегодня у каждого правила ведомости есть лемма Lean о МОДЕЛИ значений
(`Model.lean`: значения `«Знач»`, арифметика с округлением `«Округление»`,
списки, суммы, тексты, суждение `«Судим» Γ P`). Это доказывает: **каждое правило
в отдельности состоятельно в модели.** Не доказано:

1. что сверщик применяет правила так, как они сформулированы, — его код на C
   никакой теоремой не связан с леммами; связь держится пробами;
2. что композиция шагов записи (посылки, основания «из N M», подстановки текстом
   `вставить_вместо`) даёт вывод цели, а не только набор верных строк;
3. что модель значений совпадает с вычислителем языка (`interpret.flang`):
   округление в модели «грубое», IEEE-754 binary64 не воспроизведён.

Это три разных разрыва, и закрывать их надо по одному, называя, какой закрыт.

## 2. Решение

### 2.1. Глубокое вложение: терм, запись и приёмка — данные Lean

В `flang/proof/lean/` заводятся новые файлы (существующие `Model.lean` и
`Rules.lean` не переписываются — их правит партия Э, ADR-0037):

- `Term.lean` — индуктивный тип терма языка в объёме ведомости (литерал, имя,
  `плюс`/`минус`/`умножить`/`остаток`, `если`, `разбор`, свёртка, отбор, `длина`,
  вызов, квантор по элементам, существование) и функция `оценить : Терм → Мир →
  Знач` поверх `Model.lean`. Сегодняшний `«Терм» W := W → Знач` остаётся как
  сокращение: `оценить т` — его частный случай;
- `Record.lean` — индуктивный тип записи: утверждение, блок `вывод`, шаг с
  именем правила, посылками и основанием — ровно то, что описано в `README.md`;
  это и есть спецификация формата, которую просит 1313 §3;
- `Acceptance.lean` — отношение `Принят : Запись → Prop`, зеркалящее `шаг_вывода`
  сверщика случай за случаем: для каждого имени правила — те же побочные
  условия, что в C (вид основания, сличение подстановкой, захват);
- `Consistency.lean` — теорема: **`Принят з → Судим (допущения з) (цель з)`**,
  индукцией по записи, каждый случай — леммой из `Rules.lean`.

### 2.2. Сверка модели с кодом: расходятся — краснеет

Отношение `Принят` делается разрешимым (`принят? : Запись → Bool` с теоремой
`принят? з = true → Принят з`), и прогон на C и в Lean сравнивается на всём
наборе: 216 честных записей и 459 подделок. Любое расхождение вердиктов —
находка: либо сверщик принимает то, что модель не принимает (дыра), либо
наоборот (модель строже кода, и тогда либо чинится модель, либо ужесточается
код). Сверка ставится в `run.sh` рядом с подделками и красит.

### 2.3. Что остаётся снаружи теоремы — названо

- **Вычислитель.** Теорема — о модели. Разрыв 3 §1 закрывается отдельно:
  округление в модели уточняется до binary64 (тогда леммы, зависящие от
  округления, переигрываются), а совпадение с `interpret.flang` проверяется
  дифференциальным прогоном на сетке границ (968 входов сверки правила порядка
  уже есть — образец).
- **Разбор исходника.** Сверщик читает исходник `.flang` текстом (`требует`,
  объявления). Модель принимает уже разобранную запись; соответствие текста и
  разобранного — вне теоремы, и это названо.
- **Печать в C/JS/…** — ADR-0030, не здесь.

### 2.4. Порядок

1. `Term.lean` + `оценить` — и доказательство, что существующие леммы правил
   переформулируются через `оценить` без потери (иначе модель терма не та).
2. `Record.lean` по `README.md`; расхождения прозы и кода сверщика — в 1313 §3.
3. `Acceptance.lean` для правил, у которых есть приём в C (13 в `шаг_вывода` плюс
   узлы), по одному; `Consistency.lean` растёт вместе — теорема доказана для
   подмножества правил, и подмножество названо числом.
4. Сверка §2.2 в `run.sh`; первое расхождение — задача.
5. Уточнение округления до binary64.

## 3. Цена

Lean: ориентировочно 2–4 тысячи строк на четыре файла — это оценка по объёму
`Rules.lean` (2175 строк на 110 лемм), не замер. Времени — недели, не дни.
Доверенная база ПОСЛЕ: ядро Lean + `Model.lean`/`Term.lean` (что считается
значением) + сверка вердиктов; `checker.c` перестаёт быть единственным судьёй
логики и остаётся исполняемыми воротами. Строк кода `checker.c` — +0 по замыслу
(изменения в нём — только починка расхождений, найденных сверкой).

## 4. Что отвергнуто

- **Верифицировать `checker.c` как программу** (Frama-C, VST): дороже на порядок и
  привязывает теорему к одной реализации; модель + сверка вердиктов даёт то же
  доверие двум реализациям сразу (C и `checker.flang`).
- **Переписать сверщик на Lean и извлекать**: извлечённый код зависел бы от
  Lean-тулчейна на машине сборки; «один `cc`» — обещание 1.0.
- **Считать 459 подделок доказательством.** Это и есть §1 `road-to-1-0.md`.

## 5. Риски

- **Lean на машине сборки нет**: ставится `elan`; прогон Lean — отдельная работа
  CI, не блокирующая сборку двоичного.
- **Модель может оказаться строже кода** в мелочах текстового сличения — сверка
  это покажет; каждое расхождение записывается, а не подгоняется.
- **Партия Э правит `Model.lean`** параллельно (отображение для Э6): новые файлы
  импортируют, но не правят его.

## 6. Как проверить, что решение исполнено

1. `flang/proof/lean/run.sh` собирает четыре новых файла; теорема
   состоятельности принята Lean для N правил из 13 приёмов, N назван.
2. Сверка вердиктов C ↔ Lean на всём наборе: расхождений 0 (или каждое — задачей).
3. `README.md` ссылается на `Record.lean` как на спецификацию формата (1313 §3).
4. `docs/road-to-1-0.md` §3 переписан числом: «теорема о состоятельности есть
   для N из M правил».

## 7. Где не уверен

- Объём и срок — оценка. Первая веха (§2.4 п.1–2) покажет настоящую цену.
- Уточнение округления до binary64 может опрокинуть леммы, доказанные при
  «грубом» округлении; это открытие, а не поломка, и оно записывается.
