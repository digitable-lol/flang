# ADR-0078. TLS 1.3 собран на языке и работает напечатанным, а `«Запросить»` по https остаётся за curl

**Состояние:** предложено. Принимает владелец.
**Дата:** 7 октября 2026.
**Основание:** `flang/stdlib/tls-client.flang` (новый), `flang/stdlib/certificate-path.flang`
(новый), `flang/stdlib/rsa.flang` (RSA-PSS, исправление `«R по модулю»`),
`flang/stdlib/der.flang` (`«Кусок»` без свёртки по всему списку),
`flang/stdlib/x25519.flang` (переименования), `docs/examples/https/https-get.flang`,
`docs/examples/https/rfc8448-vectors.flang`, `docs/examples/https/rfc8448-handshake.flang`,
`docs/examples/https/tls-forgeries.flang`, `docs/examples/crypto/rsa-pss-vectors.flang`.
**Рядом:** [ADR-0007](0007-encryption-by-request-to-an-external-host.md) — https у
`«Запросить»` исполняет curl; [ADR-0077](0077-the-host-hands-out-octets-from-the-system-random-source.md) —
источник тайны; [ADR-0012](0012-trust-roots.md) — корни доверия — довод программы;
задача [0048](../tasks/0048-tls-is-assembled-end-to-end.md).
**Короткие команды:** `tls:engine`, `tls:get`, `tls:rfc8448`, `tls:forgeries`
(`.flangrc`).

## 1. Что собрано

Клиент TLS 1.3 (RFC 8446) целиком на языке, без чужой программы на пути
рукопожатия: набор `TLS_AES_128_GCM_SHA256`, группа x25519, подпись сервера
`rsa_pss_rsae_sha256`, цепочка `sha256WithRSAEncryption` до корня из связки,
сверка имени узла по `subjectAltName`, запрос `GET` по HTTP/1.1 внутри TLS.

| часть | где | чем сверено |
|---|---|---|
| RSA-PSS (EMSA-PSS-VERIFY, MGF1 на SHA-1 и SHA-256, соль длиной хеша) | `rsa.flang`, `«Подпись PSS верна»` | все 60 векторов `pss-vect.txt` (PKCS #1 v2.1, ключи 1024–2048 бит) приняты, 60 подделок (перевёрнут один бит подписи) отвергнуты — прогонщиком напечатанного `rsa.flang`, 9,79 с на все 120; три вектора (1024, 1025 и 2048 бит) лежат в `docs/examples/crypto/rsa-pss-vectors.flang` |
| X25519 в доле ключа | `tls-client.flang`, `«Полёт за приветом»` | общий секрет RFC 8448 сошёлся с обеих сторон |
| HKDF, стенограмма, расписание секретов, ключи записей | `tls.flang`, `tls-handshake.flang`, `tls-client.flang` | 108 значений раздела 3 RFC 8448, см. §3 |
| слой записей AES-128-GCM в обе стороны | `«Пройти полёт»`, `«Закрытая запись»`, `«Ответ сервера»` | все закрытые записи раздела 3 расшифрованы и зашифрованы обратно октет в октет |
| цепочка до корня, срок, `basicConstraints`, имя узла | `certificate-path.flang` | живой узел `www.google.com` (цепочка до GTS Root R1) и подделки §4 |
| клиент HTTPS GET поверх голого TCP | `docs/examples/https/https-get.flang` | `www.google.com`, `example.com`, свой `openssl s_server` |

По дороге найдена и исправлена ошибка в `rsa.flang`: `«R по модулю»` считало
2^(16k) mod n как 2^(16k) − n, что верно только при старшем 16-битном разряде
модуля не меньше 2^15. На векторах с модулем 1025–1031 бит степень по модулю
выходила неверной: до правки приняты 18 векторов из 60, все 42 отказа — на этих
модулях. `«R по любому модулю»` для таких модулей считает остаток удвоениями;
модули 1024, 2048, 3072 и 4096 бит идут прежней дорогой. Ошибка касалась и
PKCS #1 v1.5.

Ключ клиента берётся поручением `«Случайные октеты»` (64 октета: 32 на тайный
скаляр X25519 и 32 на случайное ClientHello). В журнале поручений живого прогона:
`Прочитать доводы`, `Случайные октеты`, `Текущее время`, `Прочитать файл`
(связка корней), `Открыть соединение`, чтение и запись октетов в соединение — и
`Записать файл` с `Запустить процесс` для двигателя (§2).

## 2. Почему счёт идёт напечатанным, а не толкователем

План (`план` языка) исполняет толкователь `flang io`; напечатать план в C нельзя
(`FLANG_PLAN_UNSUPPORTED`: план печатает только цель `js`). Поэтому счёт
рукопожатия вынесен в чистые функции `«Привет клиента шестнадцатеричным»`,
`«Финиш словом»`, `«Запрос по полёту словом»`, `«Ответ сервера словом»`, а план
зовёт их одним из двух способов:

* **толкователем** — прямо, если двигатель не назван;
* **напечатанным C** — `flang emit flang/stdlib/tls-client.flang --target c --cli`
  (`bootstrap/flang run-script tls:engine`), план пишет запрос в файл и
  запускает прогонщик поручением `«Запустить процесс»`.

Функции одни и те же; меняется только, кто их считает.

Замеры, одна машина, один записанный полёт `www.google.com` (4411 октетов от
сервера, три записи):

| этап | толкователь | напечатанный C со сторожами | напечатанный C без сторожей |
|---|---:|---:|---:|
| ClientHello (X25519 открытого ключа) | 158,7 с | 0,20 с | 0,17 с |
| Finished клиента (X25519 общего, расшифровка 4305 октетов, стенограмма) | 4899,8 с | 2,71 с | 1,03–1,07 с |
| проверка цепочки, CertificateVerify, запрос | 3402,2 с | 2,83 с | 0,83–0,84 с |
| весь раздел 3 RFC 8448 (108 значений и подпись) | 4400,28 с | 2,83 с | 1,36 с |
| шесть проверок RSA-PSS (три вектора и три подделки) | 699,72 с | — | — |
| 120 проверок RSA-PSS (60 векторов и 60 подделок) | — | 9,79 с | 5,91 с |

«Сторожа» — проверки постусловий в напечатанном коде; ключ `emit
--no-postconditions` их снимает (обещания судятся по-прежнему). Двигатель
`tls:engine` печатается без них.

### 2.1. Толкователь не проходит рукопожатие с живым узлом по времени

Измерено, сколько настоящий узел ждёт клиента: `www.google.com` отвечает, если
между его полётом и Finished клиента не больше 9 с, и молчит при 12 с; так же
ведёт себя пауза между Finished и запросом (проба на `ssl.MemoryBIO`, задержка
вставлялась вручную). Одна только X25519 толкователем — 158,7 с. Значит
рукопожатие толкователем с живым узлом не завершается при любом терпении
клиента; это свойство счёта, а не кода TLS.

Живой прогон толкователем тоже снят: план посчитал ClientHello, открыл
соединение с `www.google.com`, принял полёт сервера и считал Finished; через
7115 с процесс `flang io` кончился сигналом 13 (SIGPIPE) — при записи в
соединение, которое узел давно закрыл. Ответа плану не пришло.

### 2.2. Почему Finished клиента уходит раньше проверки цепочки

Тот же срок в ~9 с запирал и напечатанный C со сторожами, пока счёт шёл одним
шагом (8,4–9,3 с): узел молчал. Рукопожатие разбито на два шага:

1. `«Финиш словом»` — расшифровать полёт, сверить порядок сообщений и Finished
   сервера, послать свой Finished;
2. `«Запрос по полёту словом»` — цепочка до корня, срок, имя, CertificateVerify,
   и только после них — запись с запросом.

До проверки цепочки в соединение уходит только Finished клиента — код
аутентичности стенограммы, в нём нет данных приложения. Данных приложения узел
до проверки не получает ни одного октета.

## 3. RFC 8448, раздел 3 — все 108 значений

`docs/examples/https/rfc8448-vectors.flang` берёт из раздела входы (тайные ключи
обеих сторон, ClientHello, записи сервера, полезную нагрузку данных и тревог) и
пересчитывает всё остальное: открытые ключи, общий секрет, ранний, производный,
секрет рукопожатия, четыре секрета трафика, главный, `exp master`, `res master`,
`resumption`, все справки HKDF (`info`), все ключи и векторы, оба Finished, все
шесть закрытых записей (расшифровкой и обратным шифрованием).

```
векторов RFC 8448, раздел 3: 108, из них входов 7, сошлось 108;
подпись CertificateVerify (rsa_pss_rsae_sha256): сошлась; разошлись:
```

Подделка ожидания: в копии файла изменён последний знак секрета `c hs traffic`
(он стоит в разделе трижды) — `сошлось 105; разошлись: 21 …, 68 …, 77 …`.

Разделы 4–7 RFC 8448 (возобновление по PSK, 0-RTT, HelloRetryRequest,
аутентификация клиента) не сверялись: клиент этих режимов не умеет.

## 4. Подделки

Записанный полёт своего `openssl s_server` (корень и лист RSA-2048 сделаны для
пробы) прогоняется `«Шаг рукопожатия»` с одной испорченной частью
(`docs/examples/https/tls-forgeries.flang`, `bootstrap/flang run-script tls:forgeries`):

| подделка | ответ |
|---|---|
| честный полёт | `ГОТОВО` |
| чужое имя узла (`example.org`) | `FLANG_TLS_NAME` |
| время после конца срока листа | `FLANG_TLS_EXPIRED` |
| перевёрнут один октет закрытой записи | `FLANG_TLS_RECORD` |
| перевёрнут октет подписи CertificateVerify, запись зашифрована заново | `FLANG_TLS_SIGNATURE` |
| корня нет в связке | `FLANG_TLS_CHAIN` |

Те же отказы на живом соединении со своим сервером: имя `127.0.0.1` вместо
`localhost` — `FLANG_TLS_NAME`; лист со сроком 2020–2021 — `FLANG_TLS_EXPIRED`;
свой корень при системной связке — `FLANG_TLS_CHAIN`. Ни в одном отказе запрос
не ушёл.

## 5. Живые узлы

| узел | итог | от первого поручения до ответа |
|---|---|---|
| `www.google.com/generate_204` | `HTTP/1.1 204 No Content`, 203 октета ответа | 8113, 8044, 9328 мс (три прогона) |
| `example.com/` | `HTTP/1.1 200 OK`, 928 октетов | 15 425 мс |
| свой `openssl s_server`, порт 8443 | `HTTP/1.0 200 ok`, 3766 октетов | 4892 мс |

`curl` на тот же `generate_204`: 0,016–0,021 с на запрос.

Из 8–9 с прогона на счёт двигателя приходится около 2 с; остальное —
толкователь плана (запись 190 КБ запроса с связкой корней, разбор ответов) и
запуск процессов.

## 6. Что стоит битовая операция

Профиль (`gprof`) шага Finished без сторожей: функции, которые считают битовые
операции арифметикой — `«Исключающее или трёх»`, `«Исключающее или байтов»`,
`«Свести к байту»`, `«Веса байта поля»`, `«Шаг сдвига блока»`,
`«Большинство»`, `«Выбор»`, `«Веса слова»` — вместе около 55 % собственного
времени, ещё 9 % — пересборка таблицы подстановки AES на каждом вызове
(`«Таблица подстановки»` — постоянный список, который печать не выносит).

Встроенные `и`, `или`, `исключающее или` и сдвиг над числом в [0, 2^32) сняли бы
эти 55 %: по закону Амдаля шаг Finished стал бы около 0,5 с вместо 1,03 с.
Цена примитива — правка `flang/self` (лексер, разбор, типы: операнды — `нат`
ниже 2^32, итог — тоже), правила ядра для границ итога, рантаймы десяти целей
печати и партия печати. Это работа уровня ADR-0036 (точное целое), а не
библиотеки. Порядка величины против curl она не меняет: 0,5 с против 0,02 с.

## 7. Решение

1. **TLS 1.3 на языке остаётся в библиотеке и примерах** как сверяемая формула и
   как клиент, который работает напечатанным.
2. **`«Запросить»` по https не переводится на свой TLS.** Основания числом:
   * рукопожатие толкователем с живым узлом не завершается (§2.1);
   * напечатанным — 2 с счёта и 8–9 с прогона против 0,02 с у curl;
   * покрытие уже curl: один набор, одна группа, одна схема подписи, только
     `sha256WithRSAEncryption` в цепочке; нет ECDSA, P-384, SHA-384,
     HelloRetryRequest, возобновления, ALPN и HTTP/2, отзыва;
   * у хозяина нет способа держать напечатанный двигатель внутри себя: план
     зовёт его отдельным процессом.
3. **Когда пересматривать:** когда план можно будет напечатать в C (тогда счёт
   и соединение живут в одном процессе), и когда в языке появятся битовые
   операции. До того свой TLS — для клиентов, которым нужна проверяемая
   формула и которые согласны на секунды на соединение.

## 8. Чего это решение не делает

* **Хозяин двоичного умирает от SIGPIPE**, когда план пишет в соединение,
  закрытое другой стороной: вместо отклика `«Сбой»` процесс кончается
  сигналом 13. Найдено живым прогоном толкователем (§2.1), не исправлено.

* Отзыв сертификата не проверяется (ни CRL, ни OCSP) — как и у curl по ADR-0007.
* `keyUsage`, `extendedKeyUsage`, ограничение длины пути и имён не сверяются.
* Цепочка: только RSA и `sha256WithRSAEncryption`; ECDSA-корень на пути —
  отказ `FLANG_TLS_CHAIN`/`FLANG_TLS_SIGNATURE`.
* Ответ дочитывается до `close_notify` или до закрытия соединения; кусочная
  упаковка HTTP (`chunked`) не снимается, перенаправления не исполняются.
* Слово `«Случайные октеты»` знает только компилятор после партии печати
  (ADR-0077): двоичный ствола отвечает на `https-get.flang`
  `FLANG_UNKNOWN_NAME`. Замеры этого документа сняты двоичным, напечатанным из
  этих исходников без ядра и без сторожей (`emit … --no-check
  --no-postconditions`, 23 мин 33 с, пик 14,6 ГиБ).
