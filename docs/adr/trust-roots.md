# ADR-0011. Корни доверия — довод программы, а не постоянная языка; умолчание двоичного хозяина — системный список

**Состояние:** ПРЕДЛОЖЕНИЕ, владельцем не рассмотрено
**Дата:** 26 августа 2026
**Основание:** словарь поручений [`flang/self/parser.flang`](../../flang/self/parser.flang);

`flang/src/emit/js/flang_host_browser.js`, `flang/src/emit/js/flang_io.js`,

что РЕШАЕТ; [ADR-0007](0007-encryption-by-request-to-an-external-host.md) — там

## Задача

Клиент TLS, который проверяет сертификат сам, обязан откуда-то взять **список
корневых удостоверяющих центров**. Это не код, а **данные**, и потому вопрос
«чему доверять» не решается тем же способом, что «как считать подпись».

Задача 0048 требует назвать решение вслух: **берём системный список либо носим
свой**. Ниже показано, что оба ответа неполны, и что развилка на самом деле
другая.

## Что уже есть, замерено

Сертификат читается своими руками: `x509.flang` достаёт издателя, субъекта,
срок, серийный номер и алгоритм подписи. Подпись есть чем проверить:
`rsa.flang` — PKCS#1 v1.5 поверх SHA-256, `ecdsa.flang` — P-256. Отзыв читается:
`crl.flang`.

**Корней доверия в дереве нет ни одного.** Ни файла, ни модуля, ни решения.

Системный список на этой машине есть, и вот он числами:

```
$ stat -c '%s' /etc/ssl/certs/ca-certificates.crt      182140
$ grep -c 'BEGIN CERTIFICATE' /etc/ssl/certs/ca-certificates.crt   121
$ wc -l < /etc/ssl/certs/ca-certificates.crt           3000
$ ls /etc/pki/tls/certs/ca-bundle.crt
ls: cannot access '/etc/pki/tls/certs/ca-bundle.crt': No such file or directory
```

Сто двадцать один корень, сто восемьдесят два килобайта. **Второго обычного пути
на этой же машине нет** — то есть путь к списку не одинаков даже между двумя
семействами систем, не говоря о хозяине вкладки браузера.

## Решающая улика: два хозяина из пяти прочитать файл не могут ВОВСЕ

Счёт по вхождению имени поручения в файл хозяина — это ПОТОЛОК того, что место
умеет:

```
$ for f in flang/src/emit/js/flang_host_browser.js flang/src/emit/js/flang_io.js \
           flang/src/emit/c/flang_conc.c bootstrap/compiler_flang.c; do
    printf '%s: ' "$f"; grep -c 'Прочитать октеты из файла' "$f"; done
flang/src/emit/js/flang_host_browser.js: 0
flang/src/emit/js/flang_io.js: 0
flang/src/emit/c/flang_conc.c: 2
bootstrap/compiler_flang.c: 1
```

| хозяин | читает октеты из файла |
|---|---|
| двоичного, `flang_repl.c` | да |
| планировщика, `flang_conc.c` | да |
| точка раскрутки, `compiler_flang.c` | да |
| вкладки браузера, `flang_host_browser.js` | **нет** |
| цикл поручений, `flang_io.js` | **нет** |

У вкладки браузера файловой системы нет **по устройству**, и никакая работа
этого не изменит — тот же довод, которым ADR-0008 отверг поручение «Позвать
чужое».

**Следствие, ради которого ADR и пишется.** Если библиотека проверки цепочки
сама пойдёт читать `/etc/ssl/certs/ca-certificates.crt`, она перестанет
работать у двух хозяев из пяти — и перестанет не отказом, а тем, что у неё нет
поручения, которым спросить. Список корней **не может быть постоянной
библиотеки**.

---

## Решение

**Принято три вещи разом, и они разного веса.**

### 1. Библиотека не знает, откуда берутся корни: они — ДОВОД

`trust-store.flang` и проверка цепочки принимают список корней **октетами, входом**
и отвечают на чисто счётный вопрос: сходится ли цепочка на одном из этих корней.
Ни поручения, ни пути, ни имени файла внутри библиотеки нет.

Это ровно граница ADR-0008: **на flang пишется то, что РЕШАЕТ.** «Сходится ли
цепочка» — решает. «Где лежит список» — ждёт и зависит от машины, значит это
дело хозяина и того, кто пишет программу.

### 2. Умолчание для двоичного хозяина — СИСТЕМНЫЙ список, названный в программе

Пример `examples/https/` читает `/etc/ssl/certs/ca-certificates.crt` поручением
`«Прочитать октеты из файла»`. Путь стоит **строкой в программе**, а не в
библиотеке: программа для другой системы напишет другой путь, и менять для
этого библиотеку не придётся.

Довод против «носить свой список в дереве» — не размер, а **обязанность**:

* корни **отзывают**, и отзыв обязан доехать до пользователя. Системный список
  обновляет пакетный менеджер машины; список, лежащий в git, обновляется тогда,
  когда кто-то вспомнит. Между «вспомнил» и «не вспомнил» стоит принятая
  подделка;
* дерево, которое носит свой набор корней, становится удостоверяющим органом:
  оно решает за пользователя, кому верить. Это ответственность другого рода,
  чем «компилятор печатает верный код», и брать её молча нельзя;
* 182 килобайта данных, которые надо сверять глазами при каждом обновлении, —
  ровно тот машинный ввод, про который AGENTS.md говорит «git сливает их без
  единого знака конфликта».

### 3. Пустой список корней значит «не доверяем НИКОМУ»

Это записано отдельным пунктом, потому что противоположное умолчание —
обычная дыра. Нет файла — **названный отказ**, а не тихое «проверять нечем,
пропустим». Функция проверки цепочки на пустом списке корней обязана отвечать
«не сошлось», и на это можно написать пример, который проверяется при `check`,
без единого файла.

---

## Что отвергнуто и почему

| путь | почему не он |
|---|---|
| **Свой список корней в дереве** | отзыв корня не доезжает; дерево становится удостоверяющим органом; 182 КБ машинного ввода на ручной сверке |
| **Библиотека сама читает системный файл** | два хозяина из пяти такого поручения не знают вовсе — счёт выше; путь к файлу не одинаков даже между двумя семействами систем |
| **Доверять всему, что подписано, без корней** | это не «слабее», это отсутствие проверки: подделает кто угодно |
| **Спросить у хозяина «проверь сам»** | ровно то, что делает сегодня curl (ADR-0007). Задача 0048 требует обратного |

---

## Цена принятого решения — названа, а не спрятана

1. **Программа зависит от машины.** На машине без `/etc/ssl/certs/ca-certificates.crt`
   тот же пример ответит отказом. Это честнее скрытого умолчания, но это цена.
2. **Разбор ста двадцати одного корня стоит счёта.** Список приезжает в PEM:
   3000 строк основания 64 надо перевести в октеты и разобрать как DER. Цена в
   секундах **на сегодня не замерена** — это долг, и он записан здесь, а не
   выдан за ноль.
3. **Отзыв по-прежнему не проверяется.** `crl.flang` умеет ответить «этот
   серийный номер отозван», но взять список отзыва неоткуда: адрес CDP из
   сертификата не достаётся, загрузки нет, OCSP нет. Дыра та же, что у curl
   ([[neither-path-checks-certificate-revocation]]), и это решение её не
   закрывает.
4. **Ограничений имени (`nameConstraints`) и политик нет.** Проверяется
   сходимость подписи, срок и связь издатель↔субъект — не больше.

## Чего это решение НЕ даёт

* **Не даёт «соединение защищено».** Даже с проверенной цепочкой тайный ключ
  клиента берётся из источника, который повторим
  ([[tls-in-flang-is-blocked-by-a-missing-random-key-not-by-cost]]). Обещание
  про защиту здесь писать нельзя, и оно не пишется.
* **Не даёт доверия хозяину вкладки.** Там корни придётся подать иначе, и здесь
  этот путь только назван.

## Как это решение проверять

1. Проверка цепочки на **пустом** списке корней отвечает «не сошлось» — примером
   при `flang check`, без единого файла.
2. Проверка цепочки на списке, где корень есть, отвечает «сошлось» — тем же
   способом.
3. Прогон примера `examples/https/` на этой машине читает системный список
   поручением и называет число прочитанных корней.
4. Тот же прогон с `--no-read` отвечает `FLANG_IO_DENIED` — полномочия
   принуждаются хозяином, потому что хозяин знает, что его просят сделать.
