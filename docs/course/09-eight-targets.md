# Отличие третье: одна программа в восемь языков

Восемь целей печати: `c`, `csharp`, `elixir`, `go`, `java`, `js`, `python`,
`rust`. Не «транспиляция примерно» — печатается работающая программа с
рантаймом, прогонщиком, файлом сборки и, где у цели такое есть, манифестом
пакета (`go.mod`, `Cargo.toml`, `flang.csproj`).

**Хватает двоичного.** Прежде эта глава начиналась словами «двоичный печатает
только в C, остальные семь — через npm». Сегодня это **неправда**, и снято это
прогоном: все восемь целей печатает сам двоичный, а команда `flang` из пакета
npm его же и запускает — [разобрано в главе про установку](01-install.md).

## Берём одну функцию из дерева

`examples/leetcode/035-search-insert-position.flang`, LeetCode 35:

```
тотальная функция «Шаг места вставки»
  принимает акк: число, эл: число, цель: число
  возвращает число
  обеспечивает «элемент меньше цели двигает место на единицу» если эл меньше цель то (результат равен (акк плюс 1)) иначе да
  обеспечивает «иначе место стоит на прежнем» если не (эл меньше цель) то (результат равен акк) иначе да
  …
  если эл меньше цель то акк плюс 1 иначе акк

тотальная функция «Место вставки»
  принимает элементы: список числа, цель: число
  возвращает число
  …
  свёртка элементы начиная с 0 как акк и эл → «Шаг места вставки» от акк и эл и цель
```

**Файл с прошлого замера переписали, и переписали содержательно.** Шаг свёртки
вынесли из лямбды в обычную функцию — «знак в знак, накопитель стал доводом», как
сказано в шапке самого файла, — и повесили на него **два постусловия**. Довод
назван там же: «на лямбду обещание вешать не на что; на функцию — есть». Файл
вырос с 27 строк до 46, а примеров стало пять вместо трёх.

Это и объясняет, почему в напечатанном C ниже стоит вызов
`mesto_vstavki_shag_mesta_vstavki`, а не расписанное тело витка.

## Печатаем во все восемь

```bash
for t in c csharp elixir go java js python rust; do
  flang emit examples/leetcode/035-search-insert-position.flang \
        --target $t --out ./out-$t
done
```

Что получилось:

| цель | файлов | байт |
| --- | ---: | ---: |
| c | 6 | 313 204 |
| csharp | 9 | 163 717 |
| elixir | 4 | 134 132 |
| go | 5 | 93 045 |
| java | 8 | 141 214 |
| js | 2 | 40 460 |
| python | 4 | 95 611 |
| rust | 7 | 135 931 |

*Восемь прогонов, 27 августа 2026, двоичным от 23 августа 16:00 UTC (дерево не
установлено, не новее `883fe9a9`). Число файлов не изменилось ни у одной цели с
прошлого замера; байты выросли у семи из восьми и убыли у одной — `js` со
40 565 до 40 460.*

Сорок шесть строк на flang — и триста с лишним килобайт C. Это не раздутость:
почти всё — рантайм языка, одинаковый для любой программы, и от размера
исходника он не зависит.

Печать говорит о себе сама. Вот что она ответила на цели `go`:

```
проверок при работе снято 2: постусловие доказано ядром обо всех входах и
проверено примерами функции — в напечатанный код оно не едет.
напечатано файлов 5, байт 93045, в ./out-go
аргументы напечатанной программы по типам не проверяются: это ограничение двоичного flang, полная проверка есть в версии для Node
проверено перед печатью — разбор, типы, завершаемость и ядро доказательств.
ПРИМЕРЫ НЕ ПРОГНАНЫ: их считает вычислитель на самом языке, и на самых больших
программах он в предел шагов этого бинарника не укладывается — свяжи с ними
печать, и компилятор перестал бы печатать сам себя. Прогоните их отдельно:
flang test <файл>
собрать: cd <каталог> && go build ./...
```

Четвёртая строка этой расшифровки — **сама уже неправда, и это видно из неё же**:
«версии для Node» не существует, её удалили из дерева. Про границу она говорит
верно (за вход напечатанной программы отвечает вызывающий), а про то, где искать
недостающее, — нет. Курс показывает её как есть, потому что расшифровка — это
замер, а не пересказ.

Пять файлов цели `go` — это ровно то, что нужно, чтобы собрать и запустить:

```
out-go/cli/main.go
out-go/flang/mesto_vstavki.go
out-go/flangrt/flang_runtime.go
out-go/go.mod
out-go/Makefile
```

**Печать проверяет программу перед тем, как печатать.** `emit` зовёт те же
проверки, что `check`: непроверенную программу он печатать откажется, и
программу с несошедшимся примером — тоже.

## Как выглядит напечатанное

`out-c/mesto_vstavki.c`:

```c
fl_status mesto_vstavki_mesto_vstavki(fl_ctx *ctx, fl_value elementy, fl_value cel, fl_value *result, fl_error *error) {
  fl_value fl_t2 = fl_nothing();
  FL_TRY(fl_require_list(ctx, elementy, "свёртка", &fl_t2, error));
  fl_value akk = fl_number(0.0); /* «акк» */
  const fl_mark fl_t4 = fl_region_open(ctx);
  for (size_t fl_t3 = 0; fl_t3 < fl_t2.as.list.count; fl_t3 += 1) {
    const fl_value el = fl_t2.as.list.items[fl_t3]; /* «эл» */
    fl_value fl_t5 = fl_nothing();
    FL_TRY(mesto_vstavki_shag_mesta_vstavki(ctx, akk, el, cel, &fl_t5, error));
    akk = fl_t5;
    FL_TRY(fl_region_recycle(ctx, fl_t4, &akk, error));
  }
  FL_TRY(fl_region_close(ctx, fl_t4, FL_OK, &akk, error));
  *result = akk;
  return FL_OK;
}
```

Свёртка стала обычным `for`. Ни одной проверки завершения в коде нет — она была
не нужна: завершение доказано до печати.

**Это место с прошлого замера изменилось, и изменилось в двух вещах сразу.**
Тело витка больше не расписано на восемь временных значений: шаг свёртки уехал в
отдельную функцию `mesto_vstavki_shag_mesta_vstavki`, а на её месте стоит один
вызов. И вокруг цикла появилась **область**: `fl_region_open`, `fl_region_recycle`
на каждом витке, `fl_region_close` на выходе — то есть память витка переиспользуется,
а не копится. Ни того, ни другого в прошлой расшифровке не было.

## Теперь главное: собрать все восемь и сравнить ответы

У каждой цели напечатан прогонщик с одним и тем же протоколом: **одна строка
JSON на входе, одна строка JSON на выходе**.

Запрос:

```json
{"fn":"Место вставки","args":[{"l":[{"n":"1"},{"n":"3"},{"n":"5"},{"n":"6"}]},{"n":"5"}],"depth":"10000","steps":"1000000"}
```

Значения размечены тегами, потому что JSON беднее flang: `{"n":"…"}` — число
строкой (иначе потерялись бы `NaN`, `Infinity` и `−0`), `{"s":"…"}` — строка,
`{"l":[…]}` — список, `{"r":[…]}` — запись, `{"v":"Имя","f":[…]}` — вариант.

Сборка и прогон каждой цели:

```bash
cd out-c      && make && echo "$ЗАПРОС" | ./flang_cli
cd out-go     && make && echo "$ЗАПРОС" | ./flang_cli
cd out-rust   && make && echo "$ЗАПРОС" | ./target/debug/flang_cli
cd out-java   && make build && echo "$ЗАПРОС" | java -cp . FlangCli MestoVstavki
cd out-python && echo "$ЗАПРОС" | python3 flang_cli.py mesto_vstavki
cd out-js     && echo "$ЗАПРОС" | node flang_cli.js ./mesto_vstavki.js
cd out-elixir && make build && echo "$ЗАПРОС" | elixir -pa _build -e 'Flang.Cli.main(["MestoVstavki"])'
cd out-csharp && make build && echo "$ЗАПРОС" | dotnet bin/Debug/net8.0/flang.dll MestoVstavki
```

**Результат — восемь одинаковых строк** (собрано и запущено 27 августа 2026,
восемь настоящих тулчейнов на этой машине, .NET 10.0.110):

```
c       {"ok":true,"value":{"n":"2"}}
csharp  {"ok":true,"value":{"n":"2"}}
elixir  {"ok":true,"value":{"n":"2"}}
go      {"ok":true,"value":{"n":"2"}}
java    {"ok":true,"value":{"n":"2"}}
js      {"ok":true,"value":{"n":"2"}}
python  {"ok":true,"value":{"n":"2"}}
rust    {"ok":true,"value":{"n":"2"}}
```

Восемь одинаковых строк, восемь языков, один исходник.

**А девятой строки — от интерпретатора самого flang — здесь не будет, и это
честная поправка к прошлой редакции главы.** Она обещала её так:

```bash
flang run examples/leetcode/035-search-insert-position.flang \
  --function "Место вставки" --args '{"элементы": [1,3,5,6], "цель": 5}'
```

Прогон:

```
flang run: «--args» разобрать не удалось — ждался плоский объект скаляров, вроде '{"н":10}'
```

Код возврата **2** — «кривой вызов», а не «нашлась беда в предмете». `--args`
читает только плоский объект скаляров: число, строку, `true`, `false`, `null`.
Список и запись он не разбирает — а на входе здесь список. Прежде глава писала,
что такой вызов примет «npm-овский `flang`»; сегодня команда `flang` из пакета
npm — **тот же самый двоичный**, и отвечает она тем же отказом.

Спросить интерпретатор про эту функцию всё-таки можно, но не через командную
строку, а тем, что живёт внутри программы, — примером:

```bash
flang test examples/leetcode/035-search-insert-position.flang
```

Это и есть отличие третье, снятое прогоном, а не обещанное.

## Одна честная поправка, найденная на этом самом прогоне

У цели `csharp` напечатанный `Makefile` содержит цель `run`:

```
run: build
	$(DOTNET) run -v quiet --nologo -- $(CLASS)
```

На .NET 10.0.110 она **не работает**: ключ `--nologo` доезжает до самой
программы, и та падает.

```
Unhandled exception. System.TypeLoadException: Could not resolve type '--nologo'
in assembly 'flang, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null'.
make: *** [Makefile:15: run] Error 134
```

Обход — звать собранную сборку напрямую, как в списке команд выше:

```bash
dotnet bin/Debug/net8.0/flang.dll MestoVstavki
```

Сама печать при этом верна: `make build` проходит без единого предупреждения, и
программа отвечает правильно. Ломается только удобная обёртка.

## Чем сверяется, что все восемь ведут себя одинаково

Не «на глаз по одному входу», как в этой главе. Механизмов было три, **осталось
два** — и об этом ниже прямым текстом.

**1. Печать против интерпретатора.** Программа печатается в пустой каталог,
собирается настоящим тулчейном (`gcc -std=c99 -Wall -Wextra -Werror -pedantic`),
запускается процессом; на каждом входе сетки обязана дать **то же значение и ту
же ошибку** — код и текст, — что интерпретатор. Берутся для этого стандартная
библиотека и решения LeetCode.

```bash
./ярлык тесты
```

Отдельного ярлыка на одни цели печати больше нет. Он звал
`flang/test/emit-*.test.mjs`, а последний такой файл снят вместе с реализацией
на JavaScript (`5582d5fa`): образец перестал совпадать хоть с чем-нибудь, и
прогон отвечал «tests 0» и кодом 0 — зелёным, не посмотрев ничего. Ярлык снят
22 августа, а то, что от целей осталось, идёт в общем наборе.

**2. Генератор кода у каждой цели один, и он на flang.** Прежняя редакция главы писала
здесь, что у каждой цели **два** кодогенератора — один на JavaScript
(`flang/src/emit/c.mjs`), другой на самом flang, — и что они обязаны выдать
одинаковые байты. Файла `flang/src/emit/c.mjs` в дереве больше нет: реализацию на
JavaScript удалили, и сверять стало нечего с чем. Сегодня в дереве:

```
печать на flang       flang/self/emit-{c,csharp,elixir,go,java,js,python,rust}.flang
                      8 файлов, 31 767 строк
рантаймы целей        flang/src/emit/<цель>/…  31 файл в восьми каталогах
```

Второй каталог — **не вторая реализация**, а готовые куски рантайма, которые
уезжают в вывод дословно.

**Что от этого потеряно, надо назвать прямо.** Сличение байт в байт двух
независимо написанных генераторов кода было самой сильной проверкой печати из
трёх, и её больше нет — вместе с третьей, которая сверяла всю работу инструмента
с ответами второй реализации, включая счёт шагов вычисления. Осталась первая:
сверка напечатанного с интерпретатором на всех программах репозитория.

Это не придирка к прошлой редакции, а честная запись убытка: **проверок печати
стало вдвое меньше**, и случилось это не потому, что печать стала надёжнее, а
потому, что исчезло то, с чем сравнивали.

## Границы, которые надо знать

- **Двоичный печатает все восемь целей.** Границы «только C» больше нет — это
  снято прогоном выше, восемью печатями подряд.
- **JavaScript печатается двумя файлами** — программой и прогонщиком, — без
  файла сборки; остальные семь несут рантайм и `Makefile`.
- **`--args` не берёт списки.** Любой пример со списком на входе с командной
  строки не запускается — ни двоичным, ни через npm, потому что это одно и то
  же. Работает только через `пример` внутри функции.
- **Конкурентная программа печатается не везде.** У Python и JavaScript в
  прогонщике нет прогона процессов, и это сказано в самом файле, а не умолчано.
- **Печать проверяет, а не только переводит.** Непроверенное печатать
  отказывается.

## Задача

Возьмите **другой** файл из `examples/leetcode/` — например
`217-contains-duplicate.flang` — и напечатайте его в три цели: `c`, `go`, `js`.
Соберите и прогоните каждую с одним и тем же запросом.

Функция возвращает `признак`, поэтому ответ будет не `{"n":"…"}`, а `true` или
`false`.

```json
{"fn":"Есть повторы","args":[{"l":[{"n":"1"},{"n":"2"},{"n":"3"},{"n":"1"}]}],"depth":"10000","steps":"1000000"}
```

**Проверка:** три одинаковые строки `{"ok":true,"value":true}`, и то же самое от
интерпретатора:

```json
{"function":"Есть повторы","args":{"элементы":[1,2,3,1]},"result":true}
```

**Дальше:** [Что типы не ловят](10-functor.md).
