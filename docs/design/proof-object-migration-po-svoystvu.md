# Разбор правила «по свойству» на объект доказательства

**Состояние:** разбор под решение. Кода не трогает. Числа сняты чтением и прогоном
на ветке `r/4114` (основание `gh/dev`, `bootstrap/flang` из неё же), сентябрь 2026.

**Область.** Этот разбор — про ОДНУ породу мест: шаг доказательства `по свойству
«имя»`. Образец раскладки — `proof-object-migration.md` (правило «тождество»);
общий объект — `proof-object.md`. Главный вопрос задачи 4114: **ложится ли «по
свойству» на проигрываемый след ВООБЩЕ**, или это иной механизм, не выразимый
цепочкой переписок.

**Ответ сразу, неудобный.** НЕТ. «По свойству» — не правило ядра из закрытого
списка (`PRAVILA[]`, 16 имён), а обоснование ШАГА автора внутри теоремы, наравне с
`по предположению`/`по примеру`/`по закону`. Механизм — «седьмой ход» ядра:
перенести УЖЕ ДОКАЗАННОЕ постусловие другой функции как факт, инстанцировать его по
МЕСТУ ВЫЗОВА и закрыть цель модус-поненсом по охране. Это применение леммы, а не
переписка цели. В объект доказательства оно и сегодня кладётся не цепочкой ходов, а
одной строкой `шаг … по свойству «имя» свойство строка N`, и сверщик проверяет у
неё ПРИВЯЗКУ (имя настоящее, строка — первая), а сам вывод не переигрывает — тот
остаётся на слове ядра. Значит эти места на готовые 9 ходов проигрывателя не
ложатся; чтобы их переиграть, нужен НОВЫЙ структурный ход (перенос постусловия
вызванной + замыкание), а не печать переписок. До того они остаются за
калькулятором (блок Г7).

| закрывается готовым ходом | **0 мест** |
| требует нового структурного хода | **все** (11 в коде, 64 всего) |
| что сверщик проверяет сегодня (задача 3455) | ПРИВЯЗКУ: имя объявлено + `свойство строка N` = первое объявление; вывод — на слове ядра (`сверщик.c:2452`+, комментарий `2467`) |

**Пруф прогоном (числа воспроизводимы, оснастка ниже §6):**

- честная запись с привязкой → **КОД 0**, но в вердикте «сведений проиграно заново
  0 (**ходов проверено 0**)», «Шагов по свойству проверено по существу 3». То есть
  шаги ЗАЧТЕНЫ привязкой, а не переиграны следом.
- рукотворная запись, где цель ЛОЖНА (`результат равен 3` при теле, дающем `0`), но
  свойство настоящее и привязано верно → **КОД 0** («ПРОВЕРЕНО … всё доказанное
  проиграно заново»). Сверщик не заметил ложного вывода, потому что вывод не

- та же запись с подменённой строкой привязки (20 вместо первой 11) → **КОД 1**
  («привязано к строке 20, а первое … объявление — строка 11»). Привязка ловится.

## 1. Что такое «по свойству» — и почему это не правило-переписка

Список правил ядра (`сверщик.c` `PRAVILA[]`, разложение — `proof-object.md §2.1`) —
16 имён (тождество, неотрицательность, порядок, вхождение, разбор случаев,
вычисление …). Каждое разворачивается в цепочку ПЕРВИЧНЫХ ходов над термом цели, и
именно эти цепочки печатает объект доказательства и переигрывает сверщик.

**«По свойству» в этом списке нет.** Это одно из обоснований ШАГА автора внутри
теоремы — рядом с `по предположению`, `по примеру`, `по закону` (`сверщик.c:571`,
`parser.flang:7977`). Ядро зовёт его **седьмым ходом** (`proofterm.flang:2368`,
`1070` «СЕДЬМОЙ ХОД: СЛИЧЕНИЕ ПО ВЫЗОВУ»). Смысл (комментарий ядра дословно):

> у вызова «Г» от а₁ … аₙ, У КОТОРОГО ЕСТЬ ЗНАЧЕНИЕ, постусловие «Г» на этом
> значении истинно

Постусловие вызванной функции — не допущение и не переписка, а ФАКТ: вычислитель
проверяет его после каждого возврата, нарушенное роняет вычисление отказом
`FLANG_PROPERTY`. `по свойству «имя»` этот факт ПРИНОСИТ на место: находит
постусловие с именем (`«Найти постусловие»`, `proofterm.flang:1045`), берёт
заключение места (`«Заключение места»`, `1135`), инстанцирует постусловие по КАЖДОМУ
вызову его функции в заключении — двумя подстановками, параметры→аргументы и
`результат`→сам вызов (`«По свойству при вызовах»`, `1163`), — и закрывает цель
сличением/модус-поненсом (в т.ч. снятием охраны, `proof-kernel.flang:8120`
«модус поненс по охране»).

Сравним с переписками, из которых собран проигрываемый след (`proof-object.md
§2.2`): `развернуть` (раскрыть вызов в тело), `замена по дано` (равное на равное по
допущению), `выбор`/`деление` (ветвь по условию цели), `соседи` (коммутатор одного
узла), `закон` (2 закона IEEE), `закрыть`, `вычислить`, `переписать формой`
(Д1–Д5). **Все они работают НАД ТЕРМОМ ЦЕЛИ и её допущениями.** Ни один не читает
постусловие ДРУГОЙ функции и не инстанцирует лемму по месту вызова. Механизм иной по
роду: переписка преобразует цель, а «по свойству» вносит внешний доказанный факт.

Ту же природу «по свойству» подтверждают его защиты в ядре — их у переписки нет
вовсе:
- **круг** (`proofterm.flang:1102`, `1110`): ссылка на доказываемое сейчас
  постусловие отвергается; факт даёт только постусловие, доказанное РАНЬШЕ и БЕЗ
  него (неподвижная точка «Закрыть без теорем», `2383`+);
- **неоплаченное `требует`** (`2396`): факт с вызванной, у которой предусловие не
  снято, не берётся;
- **по ребру, не по имени** (`2408`): постусловие берётся у функции, реально
  вызванной в узле, а не у первой одноимённой.

Переписка ничего этого не знает и знать не должна — ей нечего ронять в круг.

## 2. Ложится ли на проигрываемый след

### 2.1. На 9 готовых ходов — НЕТ

Диспетчер проигрывателя (`сверщик.c:1051`–`1060`) — закрытый список из девяти
первичных ходов: `развернуть`, `замена`, `соседи`, `выбор`, `деление`, `закон`,
`закрыть`, `вычислить`, `переписать` (формой). Неизвестный ход → отказ («первичных
ходов девять, и список закрыт», `1060`). Ни один из девяти не умеет прочитать
постусловие чужой функции и внести его как факт. **Готовым ходом «по свойству» не
закрывается ни в одном месте.**

Более того, «по свойству» вообще не входит в путь проигрывателя. Гейт 4102 зовёт
`proigrat_blok`, только когда в записи есть строка `ход цель` (`est_hody`,
`сверщик.c:4905`, `4907`). Объект «по свойству» строки `ход цель` НЕ несёт — он
несёт один `шаг … по свойству «имя» свойство строка N` (см. `3455/честная.запись`).
Такой шаг идёт по ОТДЕЛЬНОМУ тракту `sverit_shagi` → `sverit_shag_svoystvom`
(`сверщик.c:2508`, `2530`, `2484`), а не через `proigrat_blok`. Это два разных мира.

### 2.2. Что сверщик проверяет сегодня, а что — нет

Задача 3455 привязала шаг к источнику (`сверщик.c:2452`+). Сверщик делает ровно
две проверки (комментарий `2460`–`2472`):
1. имя, которым сослался автор, — настоящее постусловие модуля
   (`«обеспечивает «имя»»` есть хоть у одной функции);
2. привязка `свойство строка N` указывает на ПЕРВОЕ по файлу объявление этого
   постусловия (`nomer_svoystva`, `2473`).

И прямо назван потолок (`2467`): **«Сверщик не повторяет вывод — не проверяет, что
цель шага ДЕЙСТВИТЕЛЬНО следует из найденного постусловия (это делает ядро … тем же
способом, что у седьмого хода).»** То есть проверена АТРИБУЦИЯ (на что сослались и
там ли оно объявлено), а сам вывод (следует ли цель из свойства — инстанция по
вызову, модус-поненс, снятие охраны) остаётся на слове ядра.

### 2.3. Пруф прогоном

`сверщик <ф> <зап>`, `$?` — хвостом, без трубы (оснастка §6):

```
честная (с привязкой):        КОД 0   ПРОВЕРЕНО … ходов проверено 0; по свойству по существу 3
разрыв (цель ложна, привязка верна): КОД 0   ПРОВЕРЕНО … всё доказанное проиграно заново
разрыв (привязка подменена 20):      КОД 1   НЕ СОШЛОСЬ … первое объявление — строка 11
```

Средняя строка — гвоздь: теорема `результат равен 3` над телом, дающим `0`, зелёная
на КОД 0. Сверщик её пропустил не по недосмотру оснастки, а по устройству: вывод «по
свойству» он не переигрывает. Нижняя строка показывает, что привязка при этом
всё-таки сторожится — подмена строки краснеет.

### 2.4. Можно ли «по свойству» переписать переписками — ЧАСТЬЮ, и это не выход

В простейших местах (сличение охраны, `honest-modus-ponens-by-guard`) цель формально
свелась бы и цепочкой: `развернуть` результат→тело → `развернуть` вызванную →
`деление` по охране → `закрыть тождеством`. Но это ПЕРЕ-ВЫВОД, а не то, что написал
автор: «по свойству» существует именно чтобы ПЕРЕИСПОЛЬЗОВАТЬ уже доказанное, а не
доказывать заново. И он не общий:
- где свойство — само по себе нетривиальная теорема (`высота неотрицательна`,
  `ближайшая стоимость неотрицательна` — с индукцией по носителю), инлайн в конечную
  цепочку переписок не сворачивается: пришлось бы заново провести всю индукцию на
  каждом месте, а при взаимной рекурсии он и не завершится;
- смысл шага другой: цитата леммы против её пере-доказательства.

Поэтому «переписать переписками» — не миграция «по свойству», а его УСТРАНЕНИЕ
пере-выводом, и только там, где лемма тривиальна. Как общий путь — не годится.

## 3. Семьи 11 мест по форме

Механизм замыкания ОДИН на все места — применение объявленного постусловия (седьмой
ход). По ФОРМЕ шага мест две семьи; закрываются они одним и тем же новым ходом.

**Ф1. Весь вывод — один шаг.** Тело теоремы: `по свойству «имя»` прямо перед
`следовательно доказано`. Цель (обычно охраняемое равенство/неравенство) есть
постусловие вызванной функции знак в знак.
- `honest-modus-ponens-by-guard.flang:43,59,85` (3) — охрана `вход больше 0` /
  `1 не больше вход`, свойство «Стража»;
- `body-forms.flang:173` (1) — `результат не меньше 0` по «высота неотрицательна»;
- `examples/paths/shortest-path.flang:348` (1) — «стоимость лучшего соседа
  неотрицательна» по «лучший вариант неотрицателен» (тело — голый вызов);
- `self/defunc.flang:2450,2457` (2) — «слияние … складывает длины»;
- `self/hotswap.flang:1073` (1) — «узел весит не меньше единицы».
- Итого Ф1: **8**.

**Ф2. Шаг ветви под индукцией/разбором.** `то по свойству «имя»` внутри `случай`
индукции: постусловие приносится на половину витка.
- `examples/paths/shortest-path.flang:321,334` (2) — `случай голова и хвост`,
  свойство «ближайшая стоимость неотрицательна»;
- `docs/benchmark2/14-tree-of-numbers.flang:75` (1) — по «высота неотрицательна».
- Итого Ф2: **3**.

Итого в коде **11** (= «~11» задачи). Плюс тестовая проба
`чекер/пробы/программы/Ч392-примечание-вместо-постусловия.flang:173` (копия
body-forms, в счёт кода не идёт). В stdlib тем же механизмом ещё **53** (`aes`,
`crl`, `x509`, `postgres`, `sha1/256`, `hmac`, `kdf`, `scram`, `x25519`, `der`,
`http`, `numtree`, `dictionary`, `hashmap`, `tls`, `utf8`, `strings`) — форма Ф1,
цель `(длина …) не больше/равен …` по постусловию голого вызова.

**Каким ходом закрыть: НИ ОДНИМ ГОТОВЫМ.** Готовых ходов, кроющих «по свойству», —
**0**. Всем 11 (и всем 64 в коде) нужен ОДИН новый структурный ход. Рукотворного
сертификата «на готовом ходе» здесь не бывает по построению — закрывать нечем.

## 4. Что нужно, чтобы «по свойству» переиграть (новый ход, не переписка)

Миграция «по свойству» в объект — это НЕ печать цепочки переписок, а новый
СТРУКТУРНЫЙ приём, родственный `ход дано K предположение по «поле»` индукции (S1) и
прямо названный в `proof-object.md §2.2` как **S2 «постусловие вызванной»** (там же
помечен долгом). Он повторяет в сверщике то, что делает `«Свести по свойству»`
ядра:

1. **печать** (`zapis.flang`): под целью — строка вида
   `ход факт по свойству «имя» строка N вызов ⟨«Г» от …⟩` (имя постусловия, строка
   первого объявления — уже есть от 3455, и КОНКРЕТНЫЙ вызов, по которому идёт
   инстанция);
2. **проверка хода в `proigrat_blok`**: сверщик САМ
   - читает объявление постусловия на строке N (двойная привязка, как развёртка),
   - находит в цели/теле вызов `«Г» от …` и инстанцирует постусловие двумя
     подстановками (параметры→аргументы, `результат`→вызов) — НЕ берёт готовую
     инстанцию из записи (иначе снимок-со-снимком);
   - кладёт результат фактом и закрывает цель сличением/модус-поненсом по охране;
3. **сторож круга и оплаты** — обязателен и нетривиален: факт даётся только от
   постусловия, доказанного РАНЬШЕ и без этой цели (неподвижная точка), и только с
   вызванной, у которой `требует` снято. Это не «ещё один `закрыть`»: это перенос в
   доверенную базу целого приёма ядра.

Оценка веса: это заметно тяжелее, чем `вычислить` (~20 строк) или `переписать
формой`; ближе к отдельному приёму уровня индукции. Точное число — за реализатором;
здесь важно, что это НОВЫЙ ход с собственными сторожами, а не строка в существующем.

**Порода риска — инертный сторож (`proof-object-migration.md §6`).** Если напечатать
такой ход, но не расширить путь проигрывателя на него (или не завести `ход цель` над
шагом «по свойству»), печать станет украшением, а вывод по-прежнему пойдёт на слово
ядра — ровно нынешнее состояние. Проверка та же: под мигрированным местом посадить
ЛОЖНЫЙ факт (проба §6 «разрыв») и убедиться, что стало КОД 1. Пока проба «разрыв»
даёт КОД 0 — ход не переигрывается.

## 5. Не ложится — что это значит для снятия калькулятора (Г7)

Пока нового хода нет, все места «по свойству» закрываются АТРИБУЦИЕЙ (3455), а вывод
остаётся на калькуляторном/ядерном тракте. В терминах Г7: **11 мест кода (и 64
всего) — за калькулятором**, снять его над ними нельзя.

Что нужно для снятия:
1. **новый структурный ход** «постусловие вызванной» (§4) в `proigrat_blok`, с
   инстанцией по месту вызова и модус-поненсом по охране;
2. **сторож круга/оплаты** этого хода, повторяющий неподвижную точку и снятие
   `требует` из ядра;
3. **печать** этого хода в `zapis.flang` для маршрута шага «по свойству» И для
   автоматического «восьмого хода» (`proofterm.flang:2366` — постусловие вызванной
   БЕЗ ссылки автора, на пути «постусловие без теоремы»): без второго часть мест
   останется непокрытой;
4. **перегенерация записей корпуса**: обе нынешние записи (`корпус/honest-modus-
   ponens-by-guard.запись`, `корпус/body-forms.запись`) — СТАРОЙ формы (без привязки
   3455), дают КОД 3; для миграции их надо переснять с ходами.

До всего этого «по свойству» из-под калькулятора не выводится. Это НЕ дефект 3455:
3455 честно и сделал только привязку, а вывод оставил ядру — и написал это в
комментарии. Миграция «по свойству» = отдельная работа над проигрывателем, соразмерная
приёму индукции, а не печать переписок по образцу «тождества».

## 6. Оснастка и пробы (числа)

Untracked, лежит в `оснастка/` рядом (в дерево не коммитится). Источник —
рукотворная копия честного примера и один минимальный модуль-разрыв. `сверщик <ф>
<зап>`, `$?` — хвостом.

| проба | что проверяет | КОД |
|---|---|---|
| `источник.flang` + `честная.запись` (копия `3455/честная`) | честный «по свойству» с привязкой: КОД 0, но «ходов проверено 0», «по свойству по существу 3» — зачтено привязкой, не следом | **0** |
| `источник-разрыв.flang` + `разрыв-вывод-ложен.запись` | цель ЛОЖНА (`результат равен 3` при теле `0`), свойство настоящее и привязано верно → сверщик пропускает: вывод не проверяется | **0** |
| `источник-разрыв.flang` + `разрыв-привязка-подменена.запись` | та же, но `свойство строка 20` вместо первой `11` → привязка ловится | **1** |

Существующие негативные пробы привязки в дереве (не мои, для полноты): 
`пробы/записи/3455/{p-chuzhoe-svoystvo,p-nomer-nol,p-podmenen-nomer,p-privyazka-
snyata,p-za-koncom-fajla}.запись` — все на подмену/снятие привязки, все КОД 1.

Два числа на каждый ход (`proof-object-migration.md §6`): «подделок отвергнуто» и
«честных отвергнуто 0». Здесь честная (КОД 0) и подделка-привязка (КОД 1) сходятся;
но проба «разрыв» (КОД 0 на ложном) показывает, что по ВЫВОДУ подделка сегодня НЕ
отвергается вовсе — мерить будет нечего, пока не появится ход §4.
