# FTS на прикладных примерах

Все примеры исполняются и входят в автоматические тесты репозитория. В именах предметной области нет обязательного CamelCase: составные имена заключаются в `«ёлочки»` или обычные кавычки.

## Три артефакта FTS

1. `.fts` содержит понятную человеку модель и проверяемое утверждение.
2. JSON-контекст содержит конкретный снимок данных приложения.
3. Proof certificate связывает модель, контекст, шаги вывода и заключение SHA-256 дайджестами.

Утилита читает канонический `FtsDocument` и решает, что построить: форму, таблицу, документацию, API-схему, граф или защиту доменной команды.

## 1. Форма регистрации клиента

Модель [`customer-onboarding.fts`](../examples/real-world/customer-onboarding.fts):

```fts
категория «Регистрация клиента» {
  структура «Анкета клиента» {
    ид: Строка
    «полное имя»: Строка
    «электронная почта»: Email
    телефон?: Телефон
    «тип клиента»: «Тип клиента»
    «согласие на обработку»: «Согласие получено»
  }

  функтор «согласие разрешает регистрацию»:
    «Согласие получено» -> «Регистрация разрешена»

  утверждение применить «согласие разрешает регистрацию» {
    свидетельство «Анкета клиента».«согласие на обработку» {
      значение true
      путь ["анкеты", { ид: "КЛ-1042" }, "согласие на обработку"]
    }
  }
}
```

Генерация описания формы:

```bash
npm run build
node examples/utilities/form-schema.mjs \
  examples/real-world/customer-onboarding.fts \
  "Анкета клиента"
```

```json
{
  "kind": "form",
  "id": "Регистрация клиента.Анкета клиента",
  "fields": [
    {
      "name": "электронная почта",
      "control": "email",
      "required": true,
      "domainType": "Email"
    },
    {
      "name": "телефон",
      "control": "tel",
      "required": false,
      "domainType": "Телефон"
    }
  ]
}
```

Production-утилита может добавить поверх структуры layout, компоненты дизайн-системы, маски, локализацию и permissions. Эти UI-настройки не обязаны входить в доказательное ядро.

## 2. Таблица счетов

Модель [`invoices-table.fts`](../examples/real-world/invoices-table.fts) описывает строку реестра и правило эскалации просрочки:

```bash
node examples/utilities/table-columns.mjs \
  examples/real-world/invoices-table.fts \
  "Строка счёта"
```

```json
{
  "kind": "table",
  "id": "Дебиторская задолженность.Строка счёта",
  "columns": [
    { "key": "номер", "header": "Номер", "format": "text" },
    { "key": "сумма", "header": "Сумма", "format": "number" },
    { "key": "просрочен", "header": "Просрочен", "format": "badge" }
  ]
}
```

Тот же документ можно использовать для React/Vue-таблицы, CSV-экспорта, SQL-проекции, документации API или контекста агента.

## 3. DDD command guard

В [`order-shipment.fts`](../examples/real-world/order-shipment.fts) агрегат `Заказ` публикует факт `«готов к отгрузке»`:

```fts
функтор «готовность разрешает команду»:
  «Готов к отгрузке» -> «Отгрузить заказ разрешено»

утверждение применить «готовность разрешает команду» {
  свидетельство Заказ.«готов к отгрузке» {
    значение true
    путь ["заказы", { номер: "ЗК-7781" }, "готов к отгрузке"]
  }
}
```

```bash
node examples/utilities/command-guard.mjs \
  examples/real-world/order-shipment.fts \
  examples/real-world/order-shipment.context.json
```

```json
{
  "allowed": true,
  "command": "Отгрузить заказ разрешено",
  "proofTerm": "готовность разрешает команду(witness(Заказ.готов к отгрузке))"
}
```

Для [`order-shipment.blocked.context.json`](../examples/real-world/order-shipment.blocked.context.json), где склад не подтвердил резерв, результат содержит `"allowed": false` и команда не выполняется.

Критическая граница: FTS доказывает соответствие witness снимку, целостность цепочки типов и неизменность сертификата. Сам расчёт факта `«готов к отгрузке»` пока выполняет доменный сервис. Для проверки расчёта потребуется выразить его отдельным правилом или приложить сертификат нижнего уровня.

## 4. Композиция кредитной политики

[`credit-limit.fts`](../examples/real-world/credit-limit.fts) содержит цепочку:

```text
«Скоринг пройден»
  -> «Риск-проверка разрешена»
  -> «Лимит может быть установлен»
```

Если поменять порядок функторов или тип одного перехода, `fts certify` отклонит цепочку. Если изменить snapshot после сертификации, `fts verify` отклонит сертификат.

## Что здесь является языком, а что утилитой

FTS отвечает за:

- синтаксис и каноническую модель;
- ссылки между структурами, полями и функторами;
- типовую цепочку утверждения;
- проверку конкретного witness;
- сертификат и независимую верификацию.

Прикладная утилита отвечает за:

- React-компоненты и визуальное расположение;
- форматирование денег и дат;
- загрузку данных из БД;
- выполнение команды агрегата;
- выбор доверенных бизнес-законов.

Такое разделение позволяет написать много утилит над одним стабильным документом, не копируя грамматику и правила доказательства.

## Текущие ограничения

Для полноценного промышленного form/table DSL ещё нужны аннотации `label`, `format`, `widget`, `enum`, `permissions`, импорты и версии. Для более сильной бизнес-логики нужны конъюнкция нескольких witness, арифметические предикаты, кванторы и сертификаты законов функторов.

Интеграции React, Node.js, Python и произвольных языков описаны в [Зачем нужен FTS и как его интегрировать](why-and-integration.ru.md).
