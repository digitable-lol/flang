# Четыре покрытия: что каждое значит и чего не значит

Про flang легко прочесть одно число — «661 из 661 = 100 %» — и понять «язык доказан». Число не об
этом. Покрытий четыре, они измеряют разное, и высокое одно не закрывает низкое другое. Здесь они
стоят рядом.

Все числа печатает один сценарий:

```bash
bootstrap/flang io scripts/four-coverages.fscript --plan Measure --timeout 900000
```

Он печатает шапку и четыре раздела. В шапке: дата, коммит дерева и чистота рабочей копии, отпечаток
исходников компилятора, sha256 входов сборки, версия и sha256 собранного компилятора и его свежесть,
sha256 исходника независимой проверяющей программы, версия перечня правил вывода и версия Lean.
Порога у сценария нет: он измеряет и не выносит вердикта.

Код возврата 0 — измерены все четыре покрытия. Код 3 — хотя бы одно измерить не удалось; сценарий
называет, какое и почему. Первое покрытие не измеряется, пока не собрана проверяющая программа
(`make -C flang/proof/checker`). Без Lean в `PATH` сценарий тоже отвечает кодом 3. Число блоков
записи вне модели Lean сценарий не измеряет ни с Lean, ни без него: в разделе 2 всегда стоит строка
«НЕ СНЯТО ЗДЕСЬ: нужен прогон Lean», и на код возврата она не влияет.

Ответ приходит одной строкой JSON: текст отчёта стоит в поле `error` и повторён в
`diagnostics[0].message`, переводы строк записаны как `\n`.

Запуск 28 ноября 2026 года с Lean 4.34.0 занял две минуты и вернул код 0 с последней строкой
«все четыре покрытия сняты». Разделы начинались так:

```
1. ПОКРЫТИЕ СОБСТВЕННЫХ ЗАПИСЕЙ ДОКАЗАТЕЛЬСТВА — доля их мест, переигранных независимым проверяющим
   переиграно независимо        661 из 661 = 100.00 %
   записей в наборе             100 (проверяющий поручился за 88)
   мест вынесено из знаменателя 41 — записи, отвергнутые ЦЕЛИКОМ как заведомо ложные
2. ПОКРЫТИЕ ФОРМАЛИЗАЦИИ — сколько правил вывода судит второй, чужой судья (Lean 4)
   строк перечня правил         170 (из них запретов 25 — ими не выводится ничего)
   имеют лемму в Lean           165 из 170 — без леммы: Св✗✗, Зап✗, Выч✗, Кол6✗, Кол7✗
   в приёмке Lean (Acceptance.lean) 93 правил из 145 правил вывода
   блоков записи, ушедших «вне приёмки», — НЕ СНЯТО ЗДЕСЬ: нужен прогон Lean
3. ИЗВЕСТНЫЕ НАРУШЕНИЯ СОСТОЯТЕЛЬНОСТИ — открыто, поимённо
   открытых нарушений: 3 (список flang/proof/tables/consistency-violations.tsv, …)
4. ПОКРЫТИЕ ТРАНСЛЯЦИИ — сверка перевода flang → C по протоколу печати (flang/translation)
   опытов по ответу плана      41
   правил печати в списке       41
   сверяются с ИСХОДНИКОМ       24 из 41 (у остальных якоря в исходнике нет: сверка идёт C против протокола)
   не переигрываются вовсе      5 из 41 (сличается только текст в составе файла)
```

Ниже — что стоит за каждым разделом. Эти числа устаревают; свежие печатает сценарий.

---

## 1. Покрытие собственных записей доказательства

**Что измеряет.** Долю мест в записях доказательства самого компилятора, которые независимая
проверяющая программа на C ([`flang/proof/checker/checker.c`](../flang/proof/checker/checker.c))
проверила заново, а не приняла от ядра без перепроверки. Записи лежат готовыми в
`flang/proof/checker/tests/records/corpus/` — по одной на программу-образец, всего 100.
<!-- СНЯТО 2026-10-18 файлов flang/proof/checker/tests/records/corpus/*.record = 100 (print batch eight over dev 51d92cf31) -->
Измеряется отдельно: `bootstrap/flang io flang/proof/replay-share.fscript`.

**Что это позволяет сказать.** У этого набора записей слово «доказано» в отчёте компилятора
перепроверено. Вторая программа, в которой нет ни строки компилятора, прошла те же шаги заново и
получила те же выводы.

**Чего не позволяет сказать.**

- Не «100 % программ доказаны». Знаменатель — обязательства этих записей, а не ваши программы.
- Ничего о собранном компиляторе. Записи лежат в дереве готовыми. Совпадают ли они с тем, что
  `bootstrap/flang` печатает сегодня, проверяет отдельная команда
  (`bootstrap/flang io flang/proof/records-nesting.fscript`).
- Не «проверено всё, что есть в наборе». Часть записей проверяющая программа отвергает целиком:
  это нарочные подделки. Их обязательства вынесены из знаменателя, и сценарий печатает их число
  отдельной строкой.
- Не «у каждой записи что-то доказано». Запись, в которой доказанным не числится ничего,
  проверяющая программа не принимает кодом 0: она отвечает кодом 3 и словами «НЕ ПРОВЕРЕНО —
  ВПУСТУЮ». Код 0 без утверждений получает только запись, где сверены доказательства завершения
  или план.

## 2. Покрытие формализации

**Что измеряет.** Сколько правил вывода, которыми пользуется ядро, проверяет вторая, независимая
система — ядро Lean 4. Вопросов два, и они разные:

1. у скольких строк перечня правил ([`flang/proof/tables/inference-rules.tsv`](../flang/proof/tables/inference-rules.tsv) —
   строка на правило) есть лемма в `flang/proof/lean/Rules.lean` или `Term.lean`;
2. сколько приёмов проверяющей программы покрыто отношением приёмки
   `flang/proof/lean/Acceptance.lean`, то есть сколько шагов записи доказательства Lean может
   разобрать. Покрыты все приёмы `шаг_вывода` и мера свёртки через реестр доказанных
   постусловий. Шаг, на котором модель не читает нужного (тело функции не собрано в терм, функции
   шага нет в реестре модели), уходит «вне модели» вместе со всем блоком.

Файлов Lean в дереве 39.
<!-- СНЯТО 2026-11-21 файлов flang/proof/lean/*.lean = 39 (Semantics/Prefix.lean: a claim closed by the rule of the known prefix) -->
Измеряется целиком: `bootstrap/flang io flang/proof/lean/run.fscript --max-steps 4000000000 --timeout 900000`
(нужен Lean в PATH, версия — в `flang/proof/lean/lean-toolchain`). Первый из двух вопросов сценарий
четырёх покрытий считает и без Lean: это подсчёт по тексту, а не доказательство.

**Что это позволяет сказать.** У правила вывода есть теорема в независимой системе, и ложное
правило эта система отвергает. `Trap.lean` — набор нарочно искажённых правил, каждое обязано быть
отвергнуто.

**Чего не позволяет сказать.**

- Лемма о правиле не проверяет вашу программу, которая этим правилом пользуется. Лемма говорит:
  «если посылки верны, заключение верно». Что посылки верны именно здесь, проверяет программа на
  C, а не Lean.
- «Сто процентов строк перечня имеют лемму» и «Lean проверяет сто процентов шагов» — разные
  утверждения. Правила ядра без приёма проверяющей программы (`Инд1`–`Инд4` и другие) Lean в
  записи не проверяет: их шагов в блоке «вывод» нет. Чего модель не читает у приёмов проверяющей
  программы, сказано в шапке `Acceptance.lean`, раздел «Чего модель не читает».
- Сколько блоков записи уходит «вне модели», сценарий не измеряет. На этом месте он всегда
  пишет «НЕ СНЯТО ЗДЕСЬ», а не печатает ноль, в том числе когда Lean установлен. Перепись по блокам —
  `bootstrap/flang run-script lean-model:blocks`. Модель читает блоки `вывод`, блоки
  завершения композицией, утверждения, закрытые правилами «неотрицательность по построению» и
  «ограниченность точным потолком по построению», оглавление таблиц и снятия блоком `вывод`.
  Вне модели стоят ходы, посылки индукции, утверждения, принятые без доказательства, и
  доказательства завершения, которых правило композиции не покрывает. Их число — в выводе
  переписи.

## 3. Известные нарушения состоятельности

**Что измеряет.** Места, где две независимые проверки говорят об одном утверждении разное, либо где
успех проверяющей программы значит не то, что читается. Список лежит одним файлом,
`flang/proof/tables/consistency-violations.tsv`: строка на нарушение, имя и состояние. Что стоит за
каждым именем и чем оно закрывается — [известные нарушения состоятельности](flang/proof/known-soundness-violations.md).

**Зачем стоит рядом с долей.** Доля в 100 % без списка открытых нарушений читается как «нарушений
нет», поэтому сценарий печатает их вместе.

**Чего не позволяет сказать.** Что других нарушений нет. В списке то, что нашли и назвали.
Закрытая строка остаётся в файле с состоянием `closed`.

## 4. Покрытие трансляции

**Что измеряет.** Генерация кода в целевой язык не доказана как программа: проверяется каждый её
запуск (ADR-0030). Генератор кода ведёт протокол перевода, а отдельная программа на C
(`flang/translation/matcher.c`) сверяет протокол с исходником и сгенерированным кодом.
Чисел два. Первое — сколько опытов в
[`flang/translation/run.fscript`](../flang/translation/run.fscript): верные пары обязаны сойтись,
подделки — быть отвергнуты. Второе — сколько правил генерации из закрытого списка
[`flang/translation/PRINT-RULES.tsv`](../flang/translation/PRINT-RULES.tsv) сверяются с текстом
исходника, а не только с протоколом.

**Почему второе число важнее первого.** У правила без якоря в исходнике сверяется «C против
протокола». Согласованная пара «протокол и C» при этом может расходиться с написанной программой:
в протоколе ошибка, C сгенерирован по протоколу, сверка проходит. Только якорь в исходнике
привязывает пару к тому, что написал человек.

**Чего не позволяет сказать.**

- Не «генератор кода доказан». Сверка проверяет один запуск на одной паре файлов.
- Не «сгенерированный код верен». Правила, у которых сверки нет совсем, сравниваются только как
  текст в составе файла; их число сценарий печатает отдельно.
- Ничего о девяти остальных целевых языках: протокол и сверка есть только у C.

## Что со всем этим делать читателю

Если вы выбираете язык: первое покрытие говорит о том, насколько перепроверен отчёт компилятора о
самом себе, а не о ваших программах. Про ваши программы говорит `flang check --proof` на вашем
файле; там же видно, где ядро отвечает «объявлено, не доказано». Сгенерированный код не покрыт
доказательством ни в одном из десяти целевых языков.

Как Lean проверяет правила вывода — `flang/proof/lean/` и [ADR-0041](adr/0041-the-checker-is-proved-sound-against-a-mechanised-semantics.md).
