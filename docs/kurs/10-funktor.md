# Что типы не ловят

Знакомая ошибка. Есть модуль заказов, есть модуль платежей — они описывают одну
и ту же вещь по-разному. Кто-то добавляет в заказ поле, копирует функцию
перевода и забывает перенести одно поле.

Что скажет система типов? Ничего. Типы сходятся: поле есть и там и там, просто
в одно из них кладётся не то. Тесты каждого модуля зелёные: внутри модуля всё
верно. Ошибка живёт **между** модулями, а система типов между модулями не
смотрит.

flang такое ловит. Глава про то, как это устроено — и **где эта проверка не
работает**, потому что второе важнее первого.

## Три модуля об одном заказе

`examples/cat/modules/` — четыре файла. Модуль заказов объявляет свой
интерфейс списком того, что он умеет:

```flang
объект «Заказ»
  сумма является числом
  отменён является числом

тотальная функция «Отменить заказ»
  принимает заказ: «Заказ»
  возвращает «Заказ»
  запись «Заказ» с сумма равным заказ.сумма и отменён равным 1

морфизм «отменить заказ» из «Заказ» в «Заказ»
  даёт «Отменить заказ»
```

Читается это как рисунок из коробочек и стрелок:

```
     ┌─────────┐   отменить заказ    ┌─────────┐
     │  Заказ  │ ──────────────────▶ │  Заказ  │
     └─────────┘   уценить заказ     └─────────┘
```

Коробочка — вид вещи, стрелка — функция, которая на каждый заказ даёт ровно один
ответ.

Модуль платежей описывает тот же заказ в копейках, модуль отгрузки — в рублях. А
четвёртый файл, `reconciliation.flang`, называет **перевод** между ними:

```
тотальная функция «Платёж по заказу»
  принимает заказ: «Заказ»
  возвращает «Платёж»
  запись «Платёж» с копейки равным (заказ.сумма умножить на 100) и возвращён равным заказ.отменён

функтор «Заказ в платёж» из «Заказы» в «Платежи»
  объект «Заказ» отображается в «Платёж» даёт «Платёж по заказу»
  морфизм «отменить заказ» отображается в морфизм «вернуть платёж»
  морфизм «уценить заказ» отображается в морфизм «уценить платёж»
```

Слово `даёт` называет функцию перевода данных. Строки `морфизм … отображается
в морфизм …` называют, какое дело в одном модуле соответствует какому делу в
другом.

## Что из этого следует: квадрат обязан сходиться

Если перевод верен, то два пути обязаны привести в одну точку:

```
                 отменить заказ
      Заказ ──────────────────────▶ Заказ
        │                             │
        │ Платёж по заказу            │ Платёж по заказу
        ▼                             ▼
     Платёж ──────────────────────▶ Платёж
                 вернуть платёж
```

«Сначала отменить заказ, потом перевести в платёж» и «сначала перевести в
платёж, потом вернуть платёж» — это должен быть один и тот же платёж. Иначе
модули понимают отмену по-разному.

По-деловому это читается так: **отменённый заказ отменён везде**.

## Ломаем — и смотрим

Скопируем каталог в сторону и забудем перенести одно поле. В функции
`«Платёж по заказу»` напишем `возвращён равным 0` вместо
`возвращён равным заказ.отменён`, и поправим её собственный пример под новое
тело:

```bash
cp -r examples/cat/modules /tmp/modules
# правим /tmp/modules/reconciliation.flang
flang check /tmp/modules/reconciliation.flang
```

Все восемь функций остаются тотальными. Типы сходятся. Собственные примеры
зелёные. И:

```
FLANG_FUNCTOR_SQUARE: функтор «Заказ в платёж»: квадрат не сходится на стрелке
«отменить заказ»: на {"сумма":500,"отменён":0} путь «Платёж по заказу» после
«отменить заказ» дал {"копейки":50000,"возвращён":0}, а «вернуть платёж» после
«Платёж по заказу» — {"копейки":50000,"возвращён":1}
```

Код возврата 1.

Отказ не говорит «что-то не так». Он **предъявляет заказ**, на котором пути
разошлись, и оба ответа.

В том же файле описаны ещё две порчи, и обе проверены при подготовке курса:

- **забыть про копейки один раз** — в `«Уценить платёж»` написать `минус 100`
  вместо `минус 10000`. Опять квадрат, опять с предъявленным заказом:
  `дал {"копейки":40000}`, а второй путь — `{"копейки":49900}`;
- **добавить в модуль заказов новую стрелку и не отобразить её** — то есть
  выкатить новое требование, забыв про соседей:

```
FLANG_FUNCTOR_NOT_TOTAL: функтор «Заказ в платёж» не отображает морфизм
«удвоить заказ» категории «Заказы»: функтор обязан быть определён на всей
категории домена
FLANG_FUNCTOR_NOT_TOTAL: функтор «Заказ в отгрузку» не отображает морфизм
«удвоить заказ» категории «Заказы»: …
```

  Ловится это ровно потому, что интерфейс модуля объявлен списком стрелок.
  Обратите внимание: отказов **два** — забытыми оказались оба соседа сразу.

## А теперь честная часть, без которой глава была бы рекламой

**В двоичном компиляторе этой проверки нет.** Того самого, который ставится
через `brew`, `asdf` и сборкой из исходников.

Проверьте сами:

```bash
grep -c FUNCTOR bootstrap/compiler_flang.c
```

```
0
```

И на том же испорченном файле:

```bash
# двоичный
flang check /tmp/modules/reconciliation.flang; echo "код возврата: $?"
```

```
модуль «Согласование заказов»: функций 8, из них с доказанным завершением 8; типов 3; файлов вместе с импортами 4
/tmp/modules/reconciliation.flang: проверено — разбор, типы, завершаемость, ядро и примеры; замечаний нет
код возврата: 0
```

```bash
# инструментарий на Node
node node_modules/.bin/flang check /tmp/modules/reconciliation.flang; echo "код возврата: $?"
```

```
FLANG_FUNCTOR_SQUARE: … код возврата: 1
```

**Один и тот же файл. Одна реализация говорит «замечаний нет», другая находит
ошибку.**

Это не мелочь. Все три порчи, описанные в самом примере как «каждая ломает
сборку», прогнаны при подготовке курса обеими реализациями:

| порча | инструментарий на Node | двоичный |
| --- | --- | --- |
| забыли перенести поле | `FLANG_FUNCTOR_SQUARE`, код 1 | **«замечаний нет», код 0** |
| забыли новую стрелку | `FLANG_FUNCTOR_NOT_TOTAL` ×2, код 1 | **«замечаний нет», код 0** |
| забыли про копейки | `FLANG_FUNCTOR_SQUARE`, код 1 | `FLANG_EXAMPLE`, код 1 |

Третью двоичный заметил, но **не квадратом**: вместе с телом разъехался
собственный пример функции. То есть по случайности, а не по делу. Первые две он
не заметил вовсе.

Справка двоичного при этом перечисляет, чего в нём нет: «остальные семь целей
печати и законы на сетке». Про категорную поверхность там не сказано ничего.

**Практический вывод для вас:** если вы пользуетесь категорной поверхностью —
ставьте инструментарий через npm и гоняйте проверку им. Двоичного для этого
недостаточно, и он об этом не предупредит.

## Другие границы этой проверки, названные в самом языке

Разработчики языка называют их сами, и стоит их прочитать до того, как браться:

- **обычную композицию, написанную вызовом, ловит и система типов.** Стрелки
  нужны там, где конвейер **объявляется**, а не вызывается;
- **устройство связи доказано, квадрат — нет.** Концы стрелок, композиция,
  единицы, полнота связи — доказаны сличением объявлений. Квадрат функтора и
  законы стрелок **проверены на сетке из примеров автора**, и ведомость печатает
  размер сетки. Это не доказательство;
- **категория — пометка для читателя** ровно до тех пор, пока не названа списком
  своих стрелок;
- **перевод без реализации** (`отображается в` без `даёт`) не проверяется вовсе:
  такая связь уезжает в «на веру».

Второй пункт стоит перечитать. Проверка ловит настоящие ошибки — но ловит их на
тех значениях, которые вы сами написали в примерах. Пример, которого нет, ошибку
не найдёт.

## Задача

```bash
cp -r examples/cat/modules /tmp/modules
```

1. Внесите первую порчу: в `/tmp/modules/reconciliation.flang` замените
   `возвращён равным заказ.отменён` на `возвращён равным 0` и поправьте пример
   «отменённый заказ остаётся отменённым» под новое тело.
2. Прогоните двоичным. Запишите код возврата.
3. Прогоните npm-овским. Запишите код возврата.
4. Сравните.

**Проверка:** двоичный — код 0 и «замечаний нет»; npm-овский — код 1 и
`FLANG_FUNCTOR_SQUARE` с предъявленным заказом. Если у вас так — вы своими
руками увидели, что «проверено» зависит от того, чем проверяли.
