# Чем проверена установка

Улики к странице [Установка](install.html): что именно запускалось, что
ответило и чего проверить не удалось. Отдельной страницей — потому что
человеку, который ставит язык, нужна команда, а не отчёт о проверке; но
выбрасывать отчёт нельзя, иначе слову «проверено» не на что опереться.

Всё ниже прогнано на одной машине: `cc (Ubuntu 15.2.0-16ubuntu1) 15.2.0`,
`GNU Make 4.4.1`, `node v26.7.0`.

## Выпуск 0.5.1: архив, хеш, формула, сборка

Архив релиза скачан: `flang-0.5.1-c.tar.gz`, **1 515 080 байт**, `sha256sum` —
`ef2cbcbe…61de1`. Внутри ровно **девять файлов**: `LICENSE`, `Makefile`,
`flang.1`, четыре `.c` и два `.h` — ни одного `.o`, ни одного собранного
двоичного файла.

Опубликованная формула скачана отдельно: HTTP 200, 10 891 байт. Её `version` —
`0.5.1`, её `url` ведёт на релиз `v0.5.1`, её `sha256` совпал с посчитанным по
скачанному архиву посимвольно.

Архив собран теми флагами, которые задаёт сама формула
(`-std=c99 -Wall -Wextra -Werror -pedantic -O2`): 78,2 с, ни одного
предупреждения, на выходе `flang` в 7 873 872 байта, и `flang --version`
отвечает `flang 0.5.1`.

**Чего проверить не удалось.** Самого `brew` в окружении нет
(`command -v brew` пуст). Значит непроверенным осталось всё, что умеет только
brew: разбор формулы как Ruby, `bin.install`, песочница сборки, `brew audit`.
Проверено ровно то, что выше: архив, хеш, формула и сборка архива её флагами.

**Формула в дереве отстала от выложенной.** `packaging/homebrew/flang.rb` этого
дерева всё ещё называет `version "0.5.0"` и хеш `7dc75fec…`, а в
`digitable-lol/homebrew-tap` уже лежит 0.5.1. Проверка следит за этим в обратную
сторону — не отстала ли копия в tap; здесь отстал оригинал.

## Почему 0.5.0 заменили: на macOS он не собирался вовсе

Не «плохо ставился», а не собирался ни у кого. В `flang_repl.c` объявлен
`_POSIX_C_SOURCE 200809L`: на glibc эта строка `mkdtemp` ОТКРЫВАЕТ, а на Darwin
ЗАКРЫВАЕТ — заголовки Apple считают уровень видимости по `__DARWIN_C_LEVEL`, и
названный `_POSIX_C_SOURCE` опускает его до чистого POSIX, где `mkdtemp` не
значится. Сборка идёт с `-Werror`, поэтому неявное объявление — остановка, а не
предупреждение: `brew install digitable-lol/tap/flang` не доходил до конца ни
на одном Mac.

Улика, а не пересказ: в распакованном архиве 0.5.0 слово `_DARWIN_C_SOURCE`
встречается **ноль раз**, в архиве 0.5.1 — **три** (объяснение и два `#define`
под `__APPLE__`).

**Чего проверить не удалось.** Машины с macOS в окружении нет, и на Linux этот
красный не воспроизводится ничем: здесь строка работает и без починки.

## asdf: восемь версий в списке, а установка 0.5.1 падает

Три скрипта плагина запущены руками с `PATH=/usr/bin:/bin` — то есть **с Node,
физически отсутствующим в `PATH`**.

```
bin/list-all        → 0.4.1 0.4.2 0.4.4 0.4.5 0.4.6 0.4.7 0.5.0 0.5.1
bin/download 0.5.1  → скачано и распаковано девять файлов
bin/install  0.5.1  → ОТКАЗ
bin/download 0.5.0  →
bin/install  0.5.0  → «flang 0.5.0 установлен»
```

Список версий приходит из релизов GitHub живьём, поэтому 0.5.1 появился в нём
сам. **0.4.8 в нём нет намеренно**: выпуск настоящий, но вложения у него нет, и
`asdf install flang 0.4.8` кончался ошибкой 404. Скрипт отбирает не «релиз
существует», а «архив отдаётся».

Отказ на 0.5.1 выглядит так:

```
cc … -o flang flang_cli.o flang_repl.o flang_runtime.o compiler_flang.o -lm -lpthread
install: No such file or directory
```

Сборка прошла, установка — нет. Опубликованный скрипт делает
`install -m 0755 "${build}/flang_cli"`, а `Makefile` архива 0.5.1 кладёт
`flang`. Починка в этом дереве уже есть — `packaging/asdf/bin/install`
принимает оба имени и вдобавок проверяет `--version` и `--help`, — но в
репозиторий плагина она не выложена, и человеку сегодня достаётся отказ.

После установки 0.5.0 в каталоге версии четыре файла: `bin/flang`,
`lib/libcompiler_flang.a`, `include/flang_runtime.h`,
`include/compiler_flang.h`.

**Из ветки плагин ставить отказывается намеренно.** С `ASDF_INSTALL_TYPE=ref`
он выходит кодом 1 и объясняет: в репозитории компилятор лежит исходником на
самом flang, и первый двоичный файл из него получает Node — то есть ровно та
зависимость, от которой плагин избавляет.

**Чего проверить не удалось.** Ни `asdf`, ни `mise` в окружении нет. Значит
непроверенным осталось всё, что asdf делает вокруг скриптов: `plugin add`,
разводка версий, подстановка в `PATH` через shim. Про mise не прогнано вообще
ничего — строка о нём на странице установки стоит на устройстве плагина, а не
на замере.

## Из исходников: в свежем клоне собранного файла нет

**В свежем клоне собранного файла нет, и это проверено клоном.**
`bootstrap/flang` стоит в `.gitignore`,
`git ls-files bootstrap/` называет восемь файлов, и `git clone --depth 1` с
GitHub кладёт ровно их: `Makefile`, `README.md`, четыре `.c`, два `.h`.
Собранного — ни одного.

Замер снят в этом самом клоне:

| прогон | время | двоичный файл |
| --- | ---: | ---: |
| `make -C bootstrap -j4`, флаги дерева (с `-flto`) | 34,2 с | 7 831 160 байт |
| один вызов `cc` на четыре `.c` (без `-flto`) | 83,5 с | 7 873 872 байта |
| `make` в распакованном архиве 0.5.1, флаги формулы (без `-flto`) | 78,2 с | 7 873 872 байта |

Ни одного предупреждения при `-Wall -Wextra -Werror -pedantic` ни в одном из
прогонов. Время плавает с загрузкой машины, байты — нет: два прогона без
`-flto` дали один и тот же размер до байта, и отличается от них только сборка
с `-flto`.

`make -C bootstrap install PREFIX=…` в пустой префикс положил четыре файла:
`bin/flang`, `lib/libcompiler_flang.a`, `include/flang_runtime.h`,
`include/compiler_flang.h`. Страницы руководства среди них нет: `flang.1`
лежит в `packaging/`, а не в `bootstrap/`, и в архив релиза его кладёт скрипт
выпуска.

`./bootstrap/flang --version` в клоне отвечает `flang 0.5.0`, а не `0.5.1`: тег
`v0.5.1` в `main` не влит, и `package.json` вместе с `FLANG_VERSION` там всё
ещё 0.5.0. Отсюда и оговорка на странице установки: версия будет та, что в
клоне, а не последняя выпущенная.

## Node: git-адрес, реестр и цели печати сверх C

`npm install ../flang` в чистом каталоге: **добавлен 1 пакет за 255 мс**,
зависимостей ноль — ключей `dependencies` и `devDependencies` в `package.json`
нет вовсе. Появились `node_modules/.bin/flang` и `node_modules/.bin/flang-lsp`.

`npm install git+https://github.com/digitable-lol/flang.git` в пустом проекте
даёт то же самое за 11 с. Прошлый прогон этой команды падал на «Could not read
from remote repository»: npm ходит в git по ssh, а ключей на машине не было.
Сегодня ключи есть, и команда проходит; на машине без ключей она может отказать
снова.

Разница двоичного файла и пакета на Node измерена одной командой на одном
файле:

```
двоичный: flang emit проба.flang --target rust
          → «цели „rust“ в этом бинарнике нет. Втащена одна — „c“»
Node:     ./node_modules/.bin/flang emit проба.flang --target rust
          → Cargo.toml, src/runtime.rs, src/lib.rs, src/main.rs
```

**Реестр закрыт с обеих сторон.** `npm view @digitable-lol/flang version`
отвечает **E404**: под собственным именем языка ещё ничего не выложено.
`npm view @digitable-lol/fts version` отвечает **0.4.7** — это старое имя, и
оно отстало от выпуска.

## Команд у двоичного файла десять, а не шесть

`./bootstrap/flang --help` называет все десять, а `flang lock проба.flang`
отвечает JSON-замком и кодом 0 — не отказом со ссылкой на «полный
инструментарий», как можно было бы ждать. Справки двоичного
файла и пакета на Node перечисляют один и тот же набор команд.

Значит, разница между путями ровно одна, и она про печать: у двоичного цель
`c`, у пакета на Node — все {{цели.словом}} ({{цели.список}}) плюс языковой
сервер `flang-lsp`.
