# Кеш доказательств

Ядро доказательств выносит приговор каждому обязательству программы на каждом
`flang check`, `flang emit` и на каждой перепечатке компилятора. Кеш
доказательств хранит ответы ядра между прогонами в каталоге рядом с проектом и
на следующем прогоне отдаёт их, не считая заново. Как `.olean` у Lean: ответ,
однажды посчитанный, лежит на диске и берётся, пока не изменилось ничего, от
чего он зависит.

## Как включить

```sh
FLANG_PROOF_CACHE=on flang check --proof программа.flang
FLANG_PROOF_CACHE=on flang emit программа.flang --target c
FLANG_PROOF_CACHE=/путь/к/каталогу flang check программа.flang
```

Переменная не задана, пуста, `off` или `0` — кеша нет, ядро идёт прежней
дорогой байт в байт. `on` или `1` — каталог `.flang-cache/proofs/` в корне
проекта: ближайший сверху каталог с `.flangrc` или `.git`. Любое другое значение
— путь к каталогу кеша. Каталог в git не идёт (`.gitignore`), и удалить его
можно в любой момент.

| переменная | что делает |
|---|---|
| `FLANG_PROOF_CACHE_STATS=1` | строка в stderr: сколько записей взято с диска, сколько попаданий, сколько новых, сколько обязательств посчитано по сужению |
| `FLANG_PROOF_CACHE_AUDIT=1` | ядро считает ещё и по всей программе и сверяет ответ с ответом по сужениям |
| `FLANG_MEMO_AUDIT=1` | каждое попадание, с диска и из памяти, считается заново и сверяется байт в байт; расхождение — `abort()` |
| `FLANG_PROOF_CACHE_RECHECK=0` | не звать независимый сверщик после прогона с попаданиями |
| `FLANG_PROOF_CACHE_KEY` | файл ключа подписи вместо `~/.config/flang/proof-cache.key` |
| `FLANG_PROOF_CHECKER` | путь к сверщику вместо `flang/proof/checker/сверщик` |

Выпуск кешем не пользуется: на пути метки `FLANG_PROOF_CACHE` задавать
запрещено, это стережёт `.github/actions/release-without-cache`.

## Что кешируется

Запоминаются ответы трёх чистых функций компилятора:

| функция | где | что отвечает |
|---|---|---|
| «Вердикт без теоремы по сужению» | `flang/self/proofterm.flang` | приговор постусловию и утверждению без теоремы |
| «Проверить терм по сужению» | `flang/self/proofterm.flang` | приговор теореме: шаги, случаи, отказы |
| «Значение терма записи» | `flang/self/proof-record.flang` | значение замкнутого терма в записи доказательства |

Из приговоров складывается и отчёт о доказательствах, и запись доказательства (`--record`),
поэтому кешируются оба.

## Ключ

Ключ записи — sha256 от:

- отпечатка самого двоичного: sha256 файла `/proc/self/exe`. Ядро, таблица
  правил вывода, версия ядра и рантайм впечатаны в двоичный, и смена любого из
  них даёт другой отпечаток;
- имени функции;
- ТОЧНЫХ байтов всех доводов вызова, той же записью, которой их сравнивает
  память вызовов внутри прогона ([ADR-0051](../adr/0051-the-proof-kernel-remembers-pure-calls-within-one-run.md)):
  вид значения, число всеми 64 битами, длина и байты строки, имена и значения
  полей по порядку. Места (`span`) входят в ключ как есть.

Функции чистые: ответ — функция доводов. Попадание отдаёт ровно то, что ядро
посчитало бы на тех же байтах.

## Сужение: от чего зависит одно обязательство

Если подать ядру программу целиком, ключ каждого обязательства зависел бы от
всей программы, и правка одной строки промахивала бы весь кеш. Поэтому ядро
считает обязательство по СУЖЁННОЙ программе:

1. Рантайм (`proof_closures` в `flang/src/emit/c/flang_repl.c`) для каждого
   обязательства собирает замыкание: все строки узла обязательства, объявления
   с такими именами среди `functions`, `types`, `statements`, `theorems` (у типа
   имя — его собственное и имена вариантов), их строки, и так, пока очередной проход
   добавляет новое. Отдаёт ядру номера объявлений по возрастанию.
2. Ядро («Сужение замкнуто») НЕ ВЕРИТ рантайму и сверяет сам: номера строго
   растут и лежат в программе, и каждая ссылка каждого взятого объявления и
   самого обязательства — внутри набора. Не сошлось — обязательство считается
   по всей программе и без кеша («без сужения» в строке `FLANG_PROOF_CACHE_STATS`).
3. Сужённая программа — та же запись, у которой четыре поля заменены взятыми
   объявлениями в прежнем порядке. Из уже доказанных фактов остаются факты
   функций набора, из прогонов примеров — прогоны функций набора; список
   неоплаченных `требует` идёт целиком.

Ядро считает обязательство на сужённой программе и при попадании, и при
промахе, поэтому холодный и тёплый прогоны с кешем отвечают одинаково.
Совпадает ли ответ по сужениям с ответом по всей программе, сверяет
`FLANG_PROOF_CACHE_AUDIT=1`.

## Почему попадание не пропускает ложного доказательства

- **Попадание — это пересчёт тех же байтов.** Ключ покрывает все доводы чистой
  функции и сам двоичный, значит запись с этим ключом могла появиться только из
  того же вычисления. Остаётся допущение о стойкости sha256.
- **Сужение честное по построению.** Взятые объявления — байт в байт объявления
  программы, набор замкнут по ссылкам, и все одноимённые объявления в нём.
  Вывод на подпрограмме, где все упомянутые имена разрешаются так же, как в
  программе целиком, остаётся выводом и в ней.
- **Файл не берётся на веру.** Каждый файл кеша подписан HMAC-SHA256 ключом
  машины (`~/.config/flang/proof-cache.key`, 32 случайных байта, права 0600;
  отпечаток двоичного входит в подпись). Испорченный, обрезанный или чужой файл
  отвергается целиком, строкой в stderr, и всё, что в нём лежало, считается
  заново.
- **Независимый сверщик.** После `flang check --proof --record` с попаданиями
  запись по умолчанию проверяет `flang/proof/checker/сверщик`, и его код
  сравнивается с кодом на записи того же файла, снятой без попаданий. Стал
  «НЕ СОШЛОСЬ» там, где без кеша было иначе, — кеш файла снимается, прогон
  повторяется без кеша. Сверщик перечитывает исходник сам, но не всё:
  «на слово ядра» он оставляет имена правил сведения и шаги «по свойству»
  (`docs/flang/proof/checker/README.md`), поэтому полную перепроверку даёт
  только `FLANG_MEMO_AUDIT=1`.

## Где лежит

```
.flang-cache/proofs/<16 знаков отпечатка двоичного>/<16 знаков sha256 пути входа>/
  <pid>-<время>.seg     записи: отпечаток ключа, шаги, глубина, ответ, подпись в конце
  checker               код сверщика на последней записи без попаданий, подписан
```

Каталог на каждый двоичный и на каждый входной файл. Прогон читает все файлы
`.seg` своего каталога, а в конце пишет один новый — записи, которые взял, и
записи, которые посчитал, — и удаляет прочитанные. Записи, не нужные этому
файлу, так и уходят. Файл пишется под временным именем и переименовывается,
поэтому два прогона одного файла разом не портят друг другу ничего: в худшем
случае останутся два целых файла, и следующий прогон сольёт их.

Шаги и глубина вызова лежат вместе с ответом и начисляются на попадании, как у
памяти вызовов внутри прогона: попадание не прячет предел шагов.

## Проверено подлогом

`bootstrap/flang run-script proof-cache:forgery`
(`scripts/guards/proof-cache-forgeries.fscript`, работа `proof-cache` в CI)
греет кеш на маленькой программе, правит её и требует, чтобы прогон с кешем
ответил ровно как прогон без кеша:

- правлено только тело вызванной функции;
- правлено только обещание вызванной функции;
- правлен ввезённый модуль;
- другой двоичный (ядро и таблица правил впечатаны в него): с диска не взято ни
  одной записи;
- испорчен байт файла кеша: подпись не сошлась, файл не взят;
- файл подписан чужим ключом: не взят;
- прогон с `FLANG_PROOF_CACHE_AUDIT=1` и `FLANG_MEMO_AUDIT=1`: каждое попадание
  пересчитано, ответ по сужениям совпал с ответом по всей программе.
