# 1310. Побайтовая сверка семени с исходниками не идёт автоматически — для неё нет раннера на 64 ГБ и сутки с лишним

## Шаги воспроизведения

1. Работы `sverka` и `dve-pechati` в `.github/workflows/reprint.yml` включаются
   переменной репозитория и идут только на своём раннере:

```
grep -c "vars.BOLSHAYA_PAMYAT == 'da'" .github/workflows/reprint.yml
grep -c 'self-hosted, bolshaya-pamyat' .github/workflows/reprint.yml
```

2. Спросить у GitHub, есть ли переменная и раннер:

```
gh api repos/digitable-lol/flang/actions/variables
gh api repos/digitable-lol/flang/actions/runners
```

3. Посмотреть, когда сверка доходила до конца:

```
awk -F'\t' '$2=="сверка"{print $1, $2, $3}' docs/reprint-ledger.tsv
```

## Что происходит

```
$ gh api repos/digitable-lol/flang/actions/runners
{"total_count":0,"runners":[]}
$ gh api repos/digitable-lol/flang/actions/variables
{"variables":[],"total_count":0}
$ awk -F'\t' '$2=="сверка" && $3=="дошла"{d=$1; s=$4; p=$5} END{print d, s, p}' docs/reprint-ledger.tsv
2026-09-08 16895 36.3
$ bootstrap/flang io scripts/seed/reprint-freshness.fscript --на-веру
побайтовая сверка перепечатки НЕ ПРОВЕРЕНА для этого дерева: последняя сверка
2026-09-08, входы печати правились 2026-10-02                            код 1
```

Дата прогона: 2 октября 2026, ствол `09bc6880`. Саму сверку
(`sh scripts/bootstrap-reprint.sh --check`) не запускали: она идёт сутки.

Переменной нет, раннера нет — обе работы (`sverka`, `dve-pechati`)
пропускаются при каждом запуске по расписанию. Сверка печатает компилятор заново
из сегодняшних исходников и сравнивает с каталогом `bootstrap` байт в байт; оба
раза, что она доходила до конца, её запускали вручную.

Держит длительность, а не память, и оба числа выросли.

**Длительность.** Дошедшие заходы печати идут от 10 ч 14 мин (36 839 с,
последняя строка «печать дошла» в `docs/reprint-ledger.tsv`) до 35 ч 45 мин
(заход 23–25 сентября, названный в шапке `scripts/bootstrap-reprint.sh`).
Разница между ними — не работа, а машина: шагов в обоих около 2,77 трлн, то есть
21,6 млн шагов/с против около 68 млн у печати 2 октября. Потолок
задания на раннере GitHub — шесть часов, и в него не попадает ни один дошедший
заход; размер раннера тут ничего не меняет, потому что прогон однопоточный
(`ps -o etimes=,time=` у печати 2 октября совпали посекундно, `%CPU 99,9`).
Свежайший замер цены — печать 1 партии 0.7.24: код 0, 37 679 с (10 ч 28 мин),
в один поток, то есть в 1,7 раза дольше шестичасового потолка задания.

**Память.** Печать 2 октября держала 44,9 ГиБ: `ps -o rss=` дал 47 049 220 КиБ
на 16–17 % потолка шагов и 47 049 988 КиБ на 28 %. Пик так и не снят — заход шёл
без `/usr/bin/time -v`, и 44,9 ГиБ тут нижняя граница, а не пик. В 64 ГБ
наблюдённое влезает с запасом не больше 1,43× против 1,7×, которые считались по
заходам 31 августа (24,3 / 35,4 / 34,7 ГиБ).
В стандартный раннер на 16 ГБ не влезает втрое.

Последняя дошедшая сверка — 8 сентября, 4 ч 41 мин 35 с при пике 36,3 ГиБ, —
мерена на замыкании, которое с тех пор выросло, и к сегодняшнему дню устарела:
`scripts/seed/reprint-freshness.fscript` краснеет на ней кодом 1.

Прав не хватает НЕ ТУТ, и это проверено, чтобы следующий их не искал:

```
$ gh api repos/digitable-lol/flang --jq .permissions
{"admin":true,"maintain":true,"pull":true,"push":true,"triage":true}
```

Завести переменную `BOLSHAYA_PAMYAT` правами можно. Заводить её **нельзя, пока
нет раннера**: работа, поставленная в очередь к несуществующему раннеру, висит до
отмены и выглядит идущей — ровно от этого переменная и стоит.

## Что должно быть

Сверка идёт раз в неделю по расписанию из `.github/workflows/reprint.yml` без
участия человека, и её итог виден в ленте Actions. Раздел «Цена самосборки» в
`docs/ROADMAP.md` называет совпадение напечатанного с закоммиченным байт в
байт главным свойством самосборки.

## Обходной путь

Запускать сверку вручную на машине с 64 ГБ памяти и записывать итог строкой в
`docs/reprint-ledger.tsv`:

```
env -u FLANG_MODULE_DIR LC_ALL=C.UTF-8 FLANG_TMP=<каталог вне дерева> sh scripts/bootstrap-reprint.sh --check
```

## Когда задача сделана

- `gh api repos/digitable-lol/flang/actions/runners` показывает раннер с
  меткой `bolshaya-pamyat`, переменная `BOLSHAYA_PAMYAT` равна `da`;
- работа `reprint-check` прошла по расписанию до конца с кодом 0, и в
  `docs/reprint-ledger.tsv` появилась строка «сверка дошла» этого прогона;
- работа `svezhest` того же файла краснеет, если входы печати правили позже
  последней дошедшей сверки.

## Где живёт правка

Это решение о машине, а не о коде: нужна машина с 64 ГБ памяти и одним быстрым
ядром, свободная на сутки с лишним раз в неделю, зарегистрированная раннером
репозитория. Раннер исполняет код веток репозитория, поэтому машина не должна
быть общей с чужой работой; репозиторий при этом публичный
(`gh api repos/digitable-lol/flang --jq .private` → `false`), и свой раннер на
публичном репозитории — решение ещё и о безопасности, а не только о железе: тот
же довод записан у обеих self-hosted работ в `.github/workflows/reprint.yml`
(«защита не должна держаться на одном отсутствии триггера»). В дереве меняются
только переменная репозитория и, если метка раннера будет другой, две строки
`runs-on` в `.github/workflows/reprint.yml`. Пересборка семени (bootstrap
regeneration) не нужна.

Сократить саму сверку ключом `--no-check` нельзя, и это сказано вслух, чтобы
никто не предлагал: ключ снимает ядро доказательств, но напечатанное им толще и
с отпечатком семени не сходится (`flang emit --help`, «НАПЕЧАТАННОЕ ЭТИМ КЛЮЧОМ
НЕ ГОДИТСЯ В СТВОЛ»). Байтовое равенство он не ускоряет, а отменяет.

До включения стоит закрыть задачу 0311: столкновение имён при печати
обнаруживается на последней стадии прогона и стоит всех его часов.
