# 3509. «разделить … по» в рантайме C считает знаки каждого куска лишним проходом, и пробы скорости поиска нет

Заявка: https://github.com/digitable-lol/flang/issues/161 (пункт 3)

## Шаги воспроизведения

1. План из одного поручения «Прочитать файл»; после отклика «Прочитано» он
   отдаёт число кусков:

```flang
тотальная функция «Сколько кусков»
  принимает текст: строка
  возвращает число
  длина (разделить текст по "Request for Comments:")
```

2. Текст — 10 516 638 байт ASCII с 66 вхождениями разделителя.
3. Прогон и два вопроса к дереву:

```
bootstrap/flang io <план> --plan Split --trust
grep -an "fl_utf8_points(piece" flang/src/emit/c/flang_runtime.c
git grep -l "fl_next_first" -- scripts flang/proof flang/test .github
```

4. Опора для пробы скорости: тот же план над файлом в 105 166 380 байт БЕЗ
   вхождения, в двух видах — с `содержит` и только `длина текст`.

## Что происходит

```
$ bootstrap/flang io <план> --plan Split --trust
{"plan":"Split","result":67,"orders":1, …}             код 0, 0,21 с, пик 121 МиБ
$ grep -an "fl_utf8_points(piece" flang/src/emit/c/flang_runtime.c
4887:      items[count] = fl_text_borrow(piece, bytes, fl_utf8_points(piece, bytes));
4898:    items[count] = fl_text_borrow(piece, bytes, fl_utf8_points(piece, bytes));
$ git grep -l "fl_next_first" -- scripts flang/proof flang/test .github
                                                                  код 1
```

Прогон Split трижды подряд: 0,21 с каждый, пик 121 МиБ (`/usr/bin/time -f`).

Отдельно снята опора для пробы скорости — тот же файл в 105 166 380 байт без
вхождения, трижды каждый вид:

| план | что делает | время |
|---|---|---:|
| `Find` | прочитать файл и спросить `содержит` | 2,52 / 2,58 / 2,54 с |
| `Read` | прочитать файл и вернуть `длина текст` | 2,55 / 2,56 / 2,61 с |

**Разница между ними — в пределах разброса самих прогонов**, то есть `содержит`
над сотней мегабайт на нынешнем `memchr` уже дешевле, чем шум чтения файла, а
пол у этого способа мерить — 2,5 с, в пятьдесят раз выше порога 0,05 с.
Порогом на полное время прогона скорость поиска не замерить ни до правки, ни
после: он покажет 2,5 с в любом случае.

Поиск разделителя в `fl_find` и `fl_razdelit_kuski` идёт через `memchr`
(`fl_next_first`). Неверно два места.
Первое: у каждого куска `fl_utf8_points` заново проходит все его октеты, то
есть строка читается третий раз после счёта кусков и нарезки; для текста, где
знаков столько же, сколько октетов, этот проход не нужен. Второе: ни одна
проверка в дереве не заметит, если поиск вернётся к сравнению на каждом октете —
ответы останутся верными, изменится только время.

Число инструкций на байт снято `valgrind --tool=callgrind` вычитанием: тот же
план над тем же файлом и над входом в 1 021 байт. Вычитание тут обязательно —
пол у прогона больше, чем вся работа над текстом.

| прогон | инструкций |
|---|---:|
| 10 516 638 байт | 1 017 563 768 |
| 1 021 байт (пол: запуск, разбор плана, ядро) | 550 653 358 |
| разница на 10 515 617 байт | **466 910 410 → 44,4 на байт** |

Поимённо на большом прогоне: `fl_razdelit_kuski` 196 825 827 (42,2 % разницы,
18,7 на байт), `fl_text` 84 233 254, `fl_utf8_not_text_at` 73 616 475 (7,0 на
байт), `__memchr_avx2` 69 611 725, `__memcpy` 48 237 222, `fl_razdelit_zdes`
20 696 352. Самого `fl_utf8_points` в разборе НЕТ — он подставлен на место, и
искать его по имени бессмысленно; его проход сидит внутри
`fl_razdelit_kuski`.

## Что должно быть

Это просьба о скорости, а не дефект ответа. «разделить» над текстом ASCII
читает строку не больше двух раз: число знаков куска берётся равным его длине в
октетах, когда в исходной строке знаков столько же, сколько октетов. Скорость
поиска закреплена пробой.

## Обходной путь

Не нужен: ответы верные. На текстах в сотни мегабайт остаётся резать файл на
части до разбора.

## Когда задача сделана

- число инструкций на байт у «Сколько кусков» над текстом ASCII снято
  `valgrind --tool=callgrind` ВЫЧИТАНИЕМ (большой вход минус вход в тысячу
  байт, иначе пол в 550 млн инструкций топит ответ) и стало меньше 44,4; либо
  записано, почему счёт знаков оставлен. `fl_utf8_points` по имени в разборе не
  ищется — он подставлен на место, смотреть надо `fl_razdelit_kuski`;
- есть проба скорости в напечатанном C, и она меряет РАЗНИЦУ, а не полное время
  прогона: над одним и тем же файлом в 105 166 380 байт без вхождения берутся
  два плана — с `содержит` и только `длина текст`, — и краснеет проба по их
  разнице. Порог ставится по замеру при сравнении на каждом октете
  (0,387 с на поиск); сегодня разница тонет в разбросе чтения (2,5 с), и порог на
  полное время прогона отличить ничего не может;
- ответы не изменились: `bootstrap/flang test flang/stdlib/strings.flang` даёт
  `не прошло 0`, и случайные
  запросы «разделить» и «содержит» с латиницей, кириллицей, эмодзи и
  комбинирующим знаком дают тот же вывод байт в байт до и после.

## Где живёт правка

`flang/src/emit/c/flang_runtime.c`: `fl_razdelit_kuski`, `fl_utf8_points`. Файл
копируемый: в напечатанные программы правка попадает со следующим `flang emit`,
в двоичный компилятор — обновлением копии в `bootstrap/` через
`scripts/seed/seed-refresh.fscript`; пересборка семени (bootstrap regeneration)
не нужна. Проба — новый файл в `flang/proof/probes/` и шаг в
`.github/workflows/binary.yml`.

Отдельная задача, здесь не решается: свёртка, копящая список записей, берёт
около 247 байт памяти на запись — решить, снижать это или записать как цену.
