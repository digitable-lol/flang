# 5877. Заслоны роста читают правку без переименований

Предел и заслон приняты решением [ADR-0053](../adr/0053-line-length-and-conditional-depth-are-limits-in-the-settings-file.md).

## Шаги воспроизведения

1. Переименовать файл, в котором есть строка длиннее `max-line-length`, и ничего в нём не менять:

   ```sh
   git mv flang/self/svoystva.flang flang/self/declared-properties.flang
   git add -A
   ```

2. Позвать заслон так, как его зовёт хук перед коммитом:

   ```sh
   bootstrap/flang run-script lint:growth
   ```

## Что происходит

```
flang/self/declared-properties.flang:2: an added line is 955 characters long, the limit is 120
...                                                                                    код 1
```

Заслон берёт правку командой `git -c core.quotepath=off diff --no-renames --numstat --cached`,
поэтому переименование он видит как удаление старого файла и дописывание нового. Все давние
строки такого файла становятся «добавленными», и длинные из них краснят заслон.

**Заслон не один, и второй важнее.** Тот же ключ стоит у `.githooks/no-growth.fscript`
(храповик «оболочка, python и разметка вне `docs/` не растут»), и там переименованный файл
оболочки приходит как новый целиком: `shell grows: … (+17 -0)` на файле, в который не
дописано ни строки.

**АСИММЕТРИЯ, из-за которой обход ниже только кажется обходом.** `--no-verify` снимает
локальные хуки — и всё. Работа `commit-messages` в `.github/workflows/commit-messages.yml`
гоняет `no-growth --plan Range` и `lint-growth --plan Range` в CI, где ключа `--no-verify`
нет. Партия печати `016bdbfcd` прошла не по праву, а потому, что ушла прямо в `dev` без
заявки: у коммита ноль check-runs, а workflow объявлен `on: pull_request`. То есть через
заявку та же слепота — твёрдый красный, и обойти её нечем.

## Что должно быть

Переименование без правки содержимого заслон пропускает: строка, которая и прежде была длиннее
предела, добавленной не считается. Содержимое сверяется по новому имени с содержимым по старому.

## Обходной путь

Обходного пути нет. `git commit --no-verify` и `git push --no-verify` снимают локальные хуки,
но не работу `commit-messages`, которая гоняет оба заслона в CI; через заявку она красна.
Партия печати 0.7.24 (`016bdbfcd`, `4392abeb0`) прошла мимо этого только потому, что ушла в
`dev` без заявки.

## Когда задача сделана

Переименование файла с давней длинной строкой проходит оба заслона без ключа `--no-verify`, а
дописывание длинной строки в тот же файл по-прежнему краснит. Три стороны — пробой: честное
переименование зелено, подлог внутри переименованного красен и назван поимённо, свод с
переименованием и настоящей правкой краснеет именно правкой.

## Чего снятие ключа НЕ делает, и это надо знать

`--numstat` с распознаванием переименований пишет переименование **одним полем** в слитном
виде `docs/{старое.sh => новое.sh}`. Такая строка не кончается на `.sh`, и проверка расширения
перестала бы совпадать: переименованный И выросший файл оболочки прошёл бы незамеченным. У
`no-growth` поле поэтому приводится к новому пути до всякого суда. Четыре вида, которые git
печатает на самом деле, закрыты примерами: обычный путь, переименование внутри каталога,
переезд между каталогами, хвост после закрывающей скобки и переименование без общей части —
его git пишет без скобок вовсе.

**Распознавание переименований порогово, и порог измерен.** Образец
`flang/concurrency/bench/hot-swap.sh`, 82 строки; переписывается первые `k` строк, файл
переименовывается:

| переписано | доля | git видит |
|---|---|---|
| 42 из 82 | 51,2 % | переименование |
| 43 из 82 | 52,4 % | новый файл |

То есть граница — около половины строк (умолчание git: сходство 50 %). Сильно переписанный
при переименовании файл приходит к заслону как новый, и заслон судит его как новый — все его
длинные строки считаются добавленными. Это не щель, а строгая сторона порога: ошибка идёт в
сторону лишней красноты, а не пропуска.

## Где живёт правка

`.githooks/lint-growth.fscript` — снятие правки и счёт добавленных строк.
