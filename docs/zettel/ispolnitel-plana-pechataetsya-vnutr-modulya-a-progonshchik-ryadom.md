# Признак «печатать отдельным файлом» — это «во вкладку не едет», а не «одинаково для всех программ»

Когда план ввода-вывода понадобилось напечатать в JavaScript, готовых образцов
в дереве было два, и они противоречили друг другу. Планировщик конкурентности
(`flang/src/emit/js/flang_conc.js`, 39 485 байт) печатается **внутрь** модуля.
Прогонщик (`flang/src/emit/js/flang_cli.js`, 34 388 байт) печатается **рядом**,
вторым файлом. Оба одинаковы байт в байт для любой программы, оба лежат в одном
каталоге, оба приходят генератору параметром.

Разделяет их не размер и не повторяемость, а один вопрос: **едет ли это во
вкладку**. Прогонщик — командная строка, во вкладку он не едет, и второй файл
для него бесплатен. Планировщик едет, и вынести его наружу значило бы отнять у
модуля обещание «самодостаточен — ни одной зависимости», ради которого
напечатанное вообще можно положить на страницу двумя строками.

Исполнитель плана едет во вкладку — значит его место рядом с планировщиком,
внутри модуля. Заказ формулировался как «исполнитель отдельным файлом, по
образцу `flang_conc.js`», и обе половины заказа оказались несовместимы: образец
`flang_conc.js` — это как раз НЕ отдельный файл.

**Чем подтверждено.** Ветка `vypusk/plan-v-pechati`. Напечатанный модуль
приложения `web/shortener/client.flang` весит 70 243 байта вместе с
исполнителем; страница ввозит его и хозяина, и это два ввоза, а не три.
Побайтовая сверка двух реализаций генератора — 108 программ корпуса из 108.

**Чем ограничено.** Правило проверено на цели JavaScript. У цели C деление
другое и по другой причине: там во «вкладку» не едет ничто, и всё лежит
отдельными файлами рантайма.

# Второе, из той же работы: сверка зеленеет на том, чего не видно в наблюдаемом следе

Это тот же класс, что уже записан в базе под именем «проверка перестала
сравнивать, но зеленеет», но признак у него более узкий и потому полезнее.
За одну работу он всплыл **трижды**, и все три раза одинаково: проверка
сравнивала СЛЕД (напечатанный текст, журнал поручений), а порча сидела в том,
что в след не попадает.

**Способ находить его заранее — не читать проверку, а портить предмет.**
Одиннадцать порч, каждая вносилась по одной и снималась после прогона. Первый
заход дал **девять из одиннадцати**; две дыры — обе про то, чего в следе нет:

| порча | поймана сразу? |
|---|---|
| состояние не продвигается | да — журнал поручений разошёлся со свидетельским |
| отклик хозяина не доходит до шага | да — журнал и прогон приложения |
| «Провал» принят за «Конец работы» | да — прогон приложения |
| **отклик хозяина не проверяется** | **НЕТ** |
| **предел поручений снят навсегда** | **НЕТ** |
| цель обещает план, но печатает без него | да |
| сторож снят у одной цели | да |
| сторож обезврежен целиком | да |
| описатель печатается пустым | да |
| исполнитель не печатается вовсе | да |
| один пробел, добавленный ТОЛЬКО на стороне flang | да — побайтовая сверка |

После двух дописанных проверок краснеют **одиннадцать из одиннадцати**.

Обе пропущенные — про то, чего в журнале нет. Журнал перечисляет ПОРУЧЕНИЯ, то
есть ход НАРУЖУ; отклик — ход обратно, и врать в нём можно молча. Предел же не
значение вовсе, а ключ настройки: он наблюдаем только тем, что прогон
ОСТАНОВИЛСЯ, а прогон, который и так останавливает хозяин, про предел не
говорит ничего.

**Правило.** Если проверка сверяет след, перечисли, чего в следе НЕТ: обратный
ход, ключи настроек, ветки отказа. Каждое такое место требует своей порчи, и
порча — единственный способ узнать, что оно проверено.

**Третье того же рода, из этой же работы.** Проверка «в напечатанном есть слово
`ioPlan`» осталась зелёной после того, как печать описателя была снята целиком:
слова `ioPlan` и `ioRun` встречаются в пояснении к самому исполнителю, а
исполнитель печатается отдельно от описателя. То есть проверка сверяла наличие
комментария. Правило: **искать в напечатанном коде объявления, а не имена**.
`export function ioPlan() {` краснеет, `ioPlan` — нет.

**Чем подтверждено.** `flang/test/emit-plan-refuse.test.mjs`,
`flang/test/app-shortener.test.mjs` и `flang/test/self-emit-js.test.mjs`, ветка
`vypusk/plan-v-pechati`. Порчи вносились по одной, скриптом, с возвратом через
`git checkout` после каждой.

**Грабли самого приёма, стоившие одного повтора.** Скрипт порчи возвращает
дерево через `git checkout -- <каталоги>` — и стирает вместе с порчей ЛЮБУЮ
несохранённую работу в тех же каталогах. Новые проверки, написанные, но не
закоммиченные, были стёрты первым же возвратом, и следующий прогон показал те
же две дыры зелёными — «исправление не помогло». Коммить до порчи, а не после.

# Третье: сторож печати, положенный «к своим», поднял потолок рабочего пути

Отказ печати по плану напрашивался в `flang/src/conc.mjs` — там лежит таблица
возможностей целей и оба соседних сторожа, `требуетПланировщика` и
`требуетХозяина`. Довод был сильный и обычный для этого дерева: одно знание не
должно лежать в двух файлах.

Перевесил замер. `conc.mjs` лежит в РАБОЧЕМ ПУТИ — в наборе из двадцати файлов
JavaScript, который поднимается в процесс на обычном `flang check`. У этого
набора потолок ходит **только вниз**: каждый переключённый на flang слой его
опускает. Сто строк сторожа подняли его с 29 722 строк до 29 822, и
`flang/test/rabochiy-put.test.mjs` покраснел.

**Правило, которое из этого следует.** Правило ПЕЧАТИ не имеет права прирастать
в пути ВЫЧИСЛЕНИЯ. Место такому правилу — рядом с `target-occupied.mjs`, то есть
в `flang/src/`, но вне того, что грузит `check`; в самом `flang/src/emit/` его
держать тоже нельзя — этот каталог реестр бэкендов, и всякий `.mjs` в нём
считается ещё одной целью печати (тот же файл `target-occupied.mjs` уже переехал
оттуда по этой причине).

**Что за это заплачено, названо.** Поля `план` в таблице возможностей целей нет,
значит `flang emit` про план молчит машиночитаемо. Взамен список целей сверяется
с поведением проверкой: цели берутся из каталога, напечатавшие обязаны совпасть
со списком ровно.

**Чем подтверждено.** Ветка `vypusk/plan-v-pechati`: 29 722 → 29 822 → 29 722,
файлов 20 во всех трёх замерах.
