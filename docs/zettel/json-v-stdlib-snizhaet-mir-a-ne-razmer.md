# JSON в стандартной библиотеке снижает МИР хозяина, а не его РАЗМЕР

Перед четвёртой целью было записано предсказание: цену следующего хозяина узла
определяет наличие JSON в стандартной библиотеке, и потому `csharp` — самая
дешёвая из пяти оставшихся. Предсказание сбылось наполовину, и вторая половина
важнее первой.

**Что сбылось.** Мира в хозяине на C# — 14 строк против 23 у Python и 12 у Go.
Дописывать перевозку JSON не пришлось ни строки: `System.Text.Json` есть.

**Что не сбылось.** Хозяин на C# — САМЫЙ БОЛЬШОЙ из трёх. Содержательных строк
(без пустых, без комментариев и без строк из одних скобок) у него 638 против
493 у Go и 424 у Python.

| хозяин | строк | кода | из них не одни скобки | мира |
|---|---:|---:|---:|---:|
| `node.py` | 514 | 428 | 424 | 23 |
| `node.go` | 719 | 617 | 493 | 12 |
| `node.cs` | 1101 | 926 | 638 | **14** |

**Почему так.** «JSON есть» и «JSON даёт динамическое значение» — разные
утверждения, и порог был проведён по первому, а платится по второму. У Python
разбор отдаёт `dict`, у Go — `map[string]any`: и то и другое читается одним
выражением. `System.Text.Json` отдаёт `JsonElement` — типизированное дерево
только для чтения, и каждое поле стоит проверки `ValueKind` плюс
`TryGetProperty`. Разбор кадра провода из трёх строк на Go превращается в
десять на C#, и это ПЕРЕВОЗКА, а не решения: решений в хозяине по-прежнему ноль.

**Признак на будущее, чтобы порог считался правильно.** Спрашивать надо не «есть
ли в стандартной библиотеке JSON», а «отдаёт ли разбор значение, которое
читается без объявления типа». По этому признаку Python и Go — да, C# — нет,
Java (`java.util.Map` после чужой библиотеки) — да, Rust без внешних ящиков —
нет вовсе.

**Чем подтверждено.** `flang/conc/bin/node.cs`, ветка `vypusk/uzel-csharp`,
коммит `ac623fee`; числа печатает сам прогон
`flang/test/uzel-celi.test.mjs` (он считает по разбиению на строки, поэтому даёт
на единицу больше, чем `wc -l`). Работа предъявлена парой «csharp ↔ js» на
дереве до удаления JavaScript: ветка `vypusk/uzel-csharp-proba`, коммит
`d756c344`, прогон печатает «ПОЛНЫЙ УЗЕЛ РАБОТАЕТ НА 4 ЦЕЛЯХ ИЗ 8».

**Чем ограничено.** Числа строк — про ЭТОТ способ письма (скобки на своей
строке, `TreatWarningsAsErrors` напечатанного проекта). Сжать их можно, но
сравнивать тогда придётся заново: у трёх хозяев один автор приёма и разные
языковые привычки, и часть разницы — привычка, а не язык. Мира это не касается:
14 строк мира — счёт по пометке, а не по вкусу.

**Поправка после пятого и шестого замеров.** Признак, названный здесь
(«отдаёт ли разбор значение, читаемое без объявления типа»), верен, но НЕ полон.
По нему `elixir` предсказывался самым дешёвым, а его хозяин вышел самым большим
из пяти — 651 содержательная строка против 638 у C#. Промах не в признаке, а в
том, что ось одна: вторую («можно ли менять состояние хозяина на месте») платит
`elixir`, у которого её нет вовсе. Разложение и таблица пяти хозяев —
[[the-host-price-has-three-axes-not-one]].

Вторая поправка, к последнему абзацу про Rust и C: «JSON придётся писать самому»
опирается на посылку, которой нет. Разбор JSON компилятор ПЕЧАТАЕТ рядом с
модулем — во всех восьми целях, потому что протокол прогонщика это JSON;
у `elixir` он ещё и виден снаружи. Подробности —
[[printed-runner-already-carries-a-json-reader]].
