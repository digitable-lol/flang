# MD5 в библиотеку заводить не стоит, и цена отказа — ровно один способ входа в PostgreSQL

Спрос померен, а не оценён на глаз. Кто в этом дереве мог бы позвать MD5:

| потребитель | что ему нужно | есть ли |
|---|---|---|
| PostgreSQL, вход `scram-sha-256` (по умолчанию с версии 14) | HMAC-SHA256 + PBKDF2 | есть |
| PostgreSQL, вход `md5` | MD5 | НЕТ — единственный потерянный |
| PostgreSQL, вход `password`, `trust` | ничего | есть |
| MySQL, `mysql_native_password` | SHA-1 | есть (`sha1.flang`) |
| MySQL, `caching_sha2_password` | SHA-256 | есть |
| Redis `AUTH`, ACL | открытый текст либо SHA-256 | есть |
| подпись вебхука, JWT HS256, подпись запроса к облаку | HMAC-SHA256 | есть |

То есть **один потребитель из семи**, и тот — способ, который PostgreSQL сам
объявил устаревшим: `password_encryption` по умолчанию `scram-sha-256`, а роль
переводится на него одной командой `ALTER ROLE … PASSWORD …`.

**Цена отказа названа полностью:** программа, которая придёт к серверу с
`host all all … md5` в `pg_hba.conf`, войти не сможет, и драйвер обязан сказать
это словами, а не висеть. Ответ человеку: «переведите роль на scram-sha-256».

**Довод против, кроме спроса.** MD5 без битовых операций — это ещё один модуль
порядка `sha1.flang` (830 строк) и та же цена сжатия блока у толкователя. Но
главное не цена: заведённый примитив начинают звать не по делу. Хеш, у которого
коллизии считаются на ноутбуке, в библиотеке общего пользования — приглашение
взять его для чего-нибудь ещё.

**Что сделало бы этот довод неверным.** Появление потребителя, у которого MD5
не выбор, а протокол: CRAM-MD5 в SMTP/IMAP, старый APOP, подпись у какого-нибудь
внешнего API. Тогда заводить — но как HMAC-MD5 рядом со способом входа, а не
как «ещё один хеш» в общем ряду.
