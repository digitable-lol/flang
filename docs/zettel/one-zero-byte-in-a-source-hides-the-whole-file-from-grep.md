# Один нулевой байт внутри исходника прячет весь файл от `grep` — и счётчик по дереву молча теряет 162 примера

`flang/self/link.flang` содержит строковую константу `"\0"` — нулевой байт как
разделитель ключа. Это законный код, он работает и живёт в дереве с коммита
`72781191`. Но GNU grep, увидев нулевой байт, считает файл ДВОИЧНЫМ и при `-c`
не печатает ничего вовсе — ни числа, ни строки «binary file matches»:

```
$ grep -c 'использует' flang/self/link.flang     # ничего, код возврата 1
$ grep -ac 'использует' flang/self/link.flang    # 3
```

Опасно здесь не то, что grep молчит, а что молчание неотличимо от нуля. Скрипт
вида `n=$(grep -c '^ *пример «' "$f")` получает пустую строку, подставляет ноль
по умолчанию — и файл со 162 примерами уходит в отчёт как файл без примеров.
Ровно это и произошло при первом счёте корпуса: 3945 вместо 3947 и, что хуже,
`link.flang` попал в кучку «файлов без импортов», где ему не место.

**Правило.** Любой обход дерева `.flang` поиском строк обязан звать `grep -a`
(или `rg -a`, или читать файлы самому). Один файл дерева уже двоичный по этому
признаку, и второй появится молча.

**Чем подтверждено.** Ветка `vypusk/progonshchik`, основание `bbe2b370`.
`tr -d '\0' < flang/self/link.flang | wc -c` даёт 133855 при 133856 байтах
файла — ровно один нулевой байт, на строке 893. Счёт по всему корпусу
(`flang/` + `docs/`, 334 файла) с `-a` и без: 3947 против 3945.

**Чем ограничено.** Про поиск строк по дереву. Сам компилятор, лексер и
прогонщик корпуса читают файлы целиком и этой беды не знают: `flang test`
берёт `link.flang` наравне со всеми и гоняет его 162 примера.
