# Планировщик тянет десятки тысяч процессов, не миллионы — и все три стены в реализации

Замер, ветка `work/zamer-processov`, отчёт `docs/planirovshchik-zamer.md`, стенды
в `flang/conc/zamer/`. Цель C, машина под нагрузкой, время процессорное.

| | flang (C) | Erlang/OTP 29, та же машина |
|---|---|---|
| молчащий процесс | **399 байт** | 2 648 байт |
| **процесс, обработавший хоть одно сообщение** | **131 062 байта** | те же 2 648 |
| сообщений/с, 2 процесса | **2,5 млн** | 1,53 млн |
| сообщений/с, 1 млн процессов | **208** | те же 1,53 млн |
| ядер занимает | **1** | все |

Читать так: **на малом масштабе мы быстрее Erlang, на большом — в семь тысяч раз
медленнее**. Молчащий процесс в шесть раз дешевле, работающий — в пятьдесят раз
дороже.

**Три стены, все в реализации, ни одной в модели:**

1. доставка перебирает всю таблицу имён (`fl_conc_address`, `flang_conc.c:506`) —
   цикл со сравнением строк на каждую отправку. Изолировано двумя стендами:
   собеседник в начале списка — 0,54 мкс при любом числе; в конце — 4,8 мс при
   миллионе;
2. куча процесса покупается куском 64 КиБ, а половин две — отсюда 128 КиБ на
   работающий процесс; сто тысяч требуют 14 ГБ;
3. переключение линейно по числу готовых (отсортированный массив с `memmove`).

**Пункты 1 и 2 — по 40–190 строк каждый и дают почти весь выигрыш.**

**Найденные потолки:** ~31 350 сообщений в одном объявлении роняют генератор C
переполнением стека JavaScript; `cc -O2` на 31 000 сообщений идёт 21,7 минуты;
при сильной нехватке памяти не хватает памяти даже на текст диагностики.

**Одноядерность сделана намеренно** — ради повторяемости прогона по зерну, на
этом стоит побайтовая сверка.
