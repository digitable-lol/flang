# Поле чужого ответа берётся ПО МЕСТУ, а не поиском ключа: поиск находит ближайший ключ, а не ваш

Инструмент, который читает ответ компилятора по меткам (`«взять текст за
меткой ключа»`), обязан различать два случая. Ключ, которого во вложенных узлах
не бывает, читается поиском безопасно. Ключ, который у вложенных узлов ТОТ ЖЕ,
поиском читать нельзя: первое вхождение окажется чужим, и ошибка будет тихой.

Замерено на переносе счёта двадцати. У функции «Вставить по»
(`docs/benchmark2/07-vstavit-po.flang`) первый параметр сам объявлен функцией:
`раньше: функция из числа и числа в признак`. В дереве разбора у типа этого
параметра есть свой `"returns"`, и стоит он РАНЬШЕ собственного `"returns"`
функции. Счёт брал тип результата поиском ключа, получал `{"kind":"flag"}`
вместо `{"kind":"list"}`, подставлял в тело заглушку `нет` вместо
`пустой список`, — и утверждение «длина результата неотрицательна», на самом
деле ОСЛАБЛЕННОЕ, записывалось в содержательные. Числу это стоило единицы:
содержательных 10 против 9.

Лечится позицией: взять массив `"params"` целиком, отсчитать его длину и
убедиться, что дальше стоит `,"returns":`. Тогда прочитан ровно свой ключ.

**Признак, по которому третий случай ищется заранее.** Опасны ключи, которые
встречаются и у узла, и у его частей: `returns`, `name`, `body`, `left`,
`right`, `params`. Безопасны ключи, которых у частей не бывает: `functions`,
`postconditions`, `examples`, `span`.

## Куски чужого JSON вырезаются счётом скобок, и разбора JSON для этого не нужно

Поддерево ответа берётся так: текст режется по закрывающей фигурной скобке
(`разделить … по "}"`), в каждом куске считаются открывающие
(`(длина (разделить кусок по "{")) минус 1`), и кусок кончился там, где глубина
вернулась к нулю. Это одна свёртка по списку — то есть тотальна по построению, и
посимвольного обхода строки не требует вовсе.

Квадратные скобки укладываются в тот же счёт двумя способами: заменить `[` на
`{` и `]` на `}` (заменой через `разделить`/`соединить`) — вложенность от этого
не меняется, а длина куска остаётся прежней; либо считать их наравне, когда
нужно разобрать массив на элементы.

Приём годится не всегда, и условие проверяется, а не предполагается: **ни одно
строковое значение ответа не должно содержать скобки, кавычки или косой черты.**
На двадцати деревьях замера таких значений ноль (проверено обходом всех строк
разобранного ответа).

**Чем подтверждено.** Ветка `u/schyot`, 20 августа 2026.
`benchmarks/zamer-tseny/schyot-20.flang` — 1336 строк (726 кода, 323 примера,
146 пояснения), 112 функций, все тотальные, 100 примеров. Отчёт совпадает с
отчётом снятой меры на JavaScript (281 строка) ПОБАЙТОВО: 9 содержательных из
20, доказано хоть что-нибудь у 13, ослабленных 5, даровых 1, не проверено 2.
Время: 3,9 с у меры на Node, 14,5 с у меры на flang — разница в четырёх
процессах на файл против трёх и в том, что план ведёт двоичный.

**Чем ограничено.** Про чтение МАШИННОГО ответа своего же компилятора, у
которого порядок ключей задан печатью и проверяется этой же мерой. Для чужого
JSON, где порядок ключей не обещан, счёт скобок годится, а отсчёт «после
параметров идёт возврат» — нет.
