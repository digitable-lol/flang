# Печать в C и в Python выводит двунаправленные управляющие сырыми — в комментарий шапки

Найдено прогоном 20 августа 2026 при переносе `flang/test/emit-bidi.test.mjs` в
`scripts/bidi-control-guard.flang`.

Проба: модуль и функция, в имени которых стоят все двенадцать двунаправленных
управляющих (U+061C, U+200E, U+200F, U+202A…U+202E, U+2066…U+2069), и строковый
литерал с ними же. Программа проходит `flang check` без замечаний. Дальше она
печатается во все восемь целей, и каждый напечатанный файл просматривается на
сырые кодовые точки.

| цель | файлов | мест с сырыми |
|---|---:|---:|
| c | 6 | 60 |
| python | 4 | 36 |
| csharp, elixir, go, java, js, rust | 35 | **0** |

Место одно и то же у обеих: **комментарий шапки** каждого напечатанного файла —

```
 * Модуль flang: «Двунаправленные nameA <двенадцать управляющих> Zname».
```

Строковый литерал экранируют обе цели правильно. Течёт ИМЯ МОДУЛЯ, уезжающее в
комментарий.

## Почему это не мелочь

Комментарий не исполняется — значит его читают первым и проверить исполнением не
могут. Это ровно тот случай, ради которого правило написано: «Trojan Source»,
CVE-2021-42574. Файл читается не так, как исполняется.

Правило и раньше называло весь вывод, а не только литерал: «Экранировать обязан
и строковый литерал бэкенда, и весь остальной вывод». Шесть целей из восьми это и
делают.

## Как увидеть

```
bootstrap/flang io scripts/bidi-control-guard.flang
```

Тот же сторож на шести чистых целях отвечает «целей 6, файлов 35, сырых
управляющих 0» и кодом 0 — значит краснеет он от вывода цели, а не сам по себе.
В CI не подключён, пока печать c и python не починена.
