# Рукописный хозяин живёт по правилам напечатанного проекта, а не по своим

Хозяин узла — рукописный файл, который кладётся В ТУ ЖЕ сборку, что и
напечатанный компилятором код. Из этого следует не «рядом лежат два файла», а
«рукописный обязан пройти режим, выбранный для напечатанного». На цели C# это
стоило двух остановок, и обе — класс, а не случай.

**Первая: вторая точка входа.** У напечатанного проекта уже есть `FlangCli.Main`,
и `flang.csproj` называет его в `StartupObject`. Хозяин приносит свой `Main`.
Правкой напечатанного это решать нельзя — его перепечатают, и правка исчезнет.
Решается КЛЮЧОМ СБОРКИ, который перекрывает свойство проекта:

    dotnet build -p:StartupObject=HozyainUzla

Тот же вопрос у Go решён иначе и по той же причине: там два `func main` в одном
пакете не собираются вовсе, поэтому хозяин лежит в своём каталоге
(`go build ./node`). У Python вопроса нет: точка входа — тот файл, который
запустили.

**Вторая: чужой строгий режим.** Напечатанный `flang.csproj` включает
`TreatWarningsAsErrors` и `Nullable`. Рукописный хозяин собирается под ними же —
послаблений для второго файла нет. Конкретно это выглядит так:

    if (u.Gruzy.TryGetValue(nomer, out Value gruz))   // ошибка CS8600

`TryGetValue` объявляет свой выходной параметр как «может быть null», и
`out Value` под включённым nullable-контекстом — ошибка, а не предупреждение.
Лечится либо `out Value?` с последующей проверкой на null (которой по смыслу
нет: ключ только что проверен), либо `ContainsKey` плюс индексатор. Взято
второе: проверки на null, стоящей ради компилятора, а не ради смысла, в хозяине
без решений быть не должно.

**Чему учит.** Прежде чем писать хозяина для новой цели, прочитайте, какой режим
сборки печать выбрала для этой цели, и какие точки входа она уже заняла. Оба
ответа лежат в напечатанных `Makefile` и файле проекта — их печать кладёт рядом
с кодом именно для этого.
