# Компилятор ЧИТАЕТ свои исходники — «прогона по `flang/self/**` не существует» было свойством места, где лежал двоичный, а не свойством дерева

27 августа 2026 записано: прогон по `flang/self/**` снят на 27 файлах из 59,
и **ведомость напечаталась у нуля**; 23 файла отказали
`FLANG_IMPORT_NOT_FOUND` и `FLANG_UNKNOWN_NAME`. Отсюда был сделан вывод:
«двоичный из семени не читает нынешних исходников компилятора», семя и
`flang/self/**` разошлись, и пока не пройдёт перепечатка, всякое число «по всему
дереву» — это число по дереву БЕЗ компилятора.

**Вывод неверен. Дело не в расхождении семени с исходниками, а в том, ГДЕ лежит
двоичный.** Модуль, ввезённый без пути (`использует «Строки»`, без
`из "…"`), ищется «рядом с файлом, выше по каталогам и в библиотеке
компилятора», и последнее — это каталоги РЯДОМ С САМИМ ДВОИЧНЫМ. Двоичный,
собранный в `/srv/tmp/…/bootstrap/`, где нет соседнего `flang/`, библиотеки
компилятора не имеет и ввоз по имени модуля разрешить не может.

**Чем подтверждено.** Два прогона 28 августа 2026, один и тот же файл
`flang/self/lexer.flang`, одни и те же исходники семени (ствол `da47cbdf`),
собранные одной и той же командой `make -C bootstrap -j8`:

| двоичный | рабочий каталог | ответ |
|---|---|---|
| `<дерево>/bootstrap/flang` | корень дерева | `утверждений 100: доказано 94, сетка 6` |
| `<дерево>/bootstrap/flang` | `/srv/tmp` (файл по полному пути) | `утверждений 100: доказано 94, сетка 6` |
| `/srv/tmp/…/sborka/bootstrap/flang` | корень дерева | `FLANG_IMPORT_NOT_FOUND: не найден модуль «Строки»` |

Третья строка — дословно тот отказ, по которому был сделан прежний вывод.
Рабочий каталог не значит НИЧЕГО; значит только место двоичного.

**Что из этого следует.** Компилятор проверяем сегодня, без перепечатки. Прогон
28 августа двоичным `82f9ac40`, собранным в дереве, печатает ведомости по
файлам `flang/self/**` обычным порядком — например, `emit-csharp.flang`,
`sets-oracle.flang`, `carriers.flang`, `commutative.flang`. Это важно не мелочью:
**в `flang/self/**` написано 7199 обязательств из 13 341 по всему дереву, то есть
54 %.** Пока считалось, что компилятор нечем судить, больше половины дерева
числилось непроверяемым — и числилось так по причине, которой не было.

**Чем ограничено — и почему беда не всплывала раньше.** Отказ даёт только ввоз
по ИМЕНИ модуля. Ввоз с путём (`использует «Провод» из "wire.flang"`)
разрешается относительно самого файла и от места двоичного не зависит вовсе.
Посчитано по дереву:

| область | ввозов по имени | ввозов с путём |
|---|---:|---:|
| `flang/self` | **160** | **0** |
| `flang/stdlib` | 8 | 19 |

То есть компилятор ввозит соседей ТОЛЬКО по имени, а библиотека — почти вся по
пути. Поэтому чужой двоичный, лежащий вне дерева, снимал ведомость по библиотеке
как ни в чём не бывало и отказывал по всему компилятору целиком. Расхождение
выглядело как «семя отстало от исходников» ровно потому, что било по одной
области и не било по другой.

**Что делать — два способа, оба проверены прогоном.**

1. Держать двоичный в дереве: `<дерево>/bootstrap/flang`. Сборка в `/srv/tmp`
   годится, только если рядом с `bootstrap/` лежит и остальное дерево, — то есть
   если собирать в клоне.
2. Или назвать библиотеку переменной среды. Тот же двоичный из `/srv/tmp`, с
   `FLANG_MODULE_DIR=<дерево>/flang/stdlib:<дерево>/flang/self:<дерево>/flang/core`,
   печатает по `lexer.flang` ту же ведомость: `утверждений 100: доказано 94,
   сетка 6`. Переменная в дереве не новая — она описана в
   `docs/guide/project-layout.md`.

**Новизна здесь не в правиле поиска, а в выводе, который из него не сделали.**
Само правило — «свой каталог, каждый каталог выше, библиотека компилятора» —
записано и замерено раньше, см. заметку ниже. Не связали одно с другим: что
двоичный, собранный вне дерева и без `FLANG_MODULE_DIR`, теряет ТРЕТЬЕ место
поиска целиком, а `flang/self/**` ввозит соседей только по имени и потому
отказывает весь. Отказ прочли как «семя отстало от исходников» и записали, что
компилятор судить нечем до перепечатки.
