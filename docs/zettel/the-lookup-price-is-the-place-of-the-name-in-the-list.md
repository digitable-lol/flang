# Цена одного поиска описания — это место имени в списке, а не число уже сделанных поисков

Замер 29 августа 2026 на проверке замыкания компилятора показал, что
`«Найти описание»` съедает 26,7 млрд витков из 27,8 млрд, и что средняя цена
одного поиска по ходу прогона растёт: 303 витка на 9,4 млн поисков, 1856 на
14,4 млн.
Пробы давали ровно треугольный итог — 45 150 = 300·301/2 — и он не менялся ни от
числа функций в программе (300 и 1200 давали одно и то же), ни от длины имён.

Отсюда напрашивался вывод, что в поиске что-то НАКАПЛИВАЕТСЯ. Это неверно.
Не накапливается ничего.

## Закон

**Один зов `«Найти описание»` стоит ровно столько витков, каково МЕСТО искомого
имени в списке `«описания»` программы, считая с единицы.** Имени в списке нет —
цена равна длине списка плюс один.

Никакой памяти между зовами нет. Треугольный итог получается тогда и только
тогда, когда k-я по счёту искомая функция стоит в списке на k-м месте, — а
именно так были устроены пробы: они звали `«Звено 1»`, `«Звено 2»`, … в порядке
объявления.

## Откуда закон берётся

Двоичный, которым идёт проверка, собран из семени `bootstrap/compiler_flang.c`.
Там `«Найти описание»` — линейный перебор списка, а не словарь:

```c
static fl_status compiler_flang_nayti_opisanie_body(fl_ctx *ctx, fl_value opisaniya,
                                                    fl_value imya, ...) {
  for (;;) {
    if (fl_chain_empty(opisaniya)) { /* «Нет описания» */ }
    else if (fl_chain_cons(opisaniya)) {
      const fl_value pervoe = fl_chain_head(opisaniya);
      FL_TRY(fl_field_get(ctx, pervoe, "имя", &fl_t45351, error));
      if (/* имя совпало */) { /* «Есть описание» — БЕЗ витка */ }
      else {
        opisaniya = fl_chain_tail(opisaniya);
        FL_TRY(fl_tick(ctx, "Найти описание", error));   /* виток на элемент */
        continue;
      }
    }
  }
}
```

Виток снимается на каждом НЕсовпавшем элементе, на совпавшем — не снимается, а
ещё один виток снимает `fl_enter` у обёртки. Значит имя на месте p стоит
(p − 1) + 1 = p витков.

Отсюда сразу и то, почему цена не зависит от длины имени: сравнение имён идёт
`fl_equal`, а `fl_equal` ни витка, ни заряда не снимает вовсе (у неё нет `ctx` —
единственная названная дыра в списке зарядов у `fl_charge`). И то, почему она не
зависит от числа функций в программе: лишние функции в пробе объявлены ПОСЛЕ
искомых, а перебор до них не доходит.

## Проба: предсказание и снятое

Три программы по 301 функции, у каждой один пример, который зовёт одну и ту же
функцию 300 раз. Меняется только МЕСТО этой функции в списке. Считано двоичным
из того же семени со счётчиком витков (`FLANG_TICKS_OUT`), 29 августа 2026.

| проба | место искомой функции | предсказано | снято |
|---|---:|---:|---:|
| имя первым | 1 из 301 | 300·1 + 301 = **601** | **601** |
| имя последним | 300 из 301 | 300·300 + 301 = **90 301** | **90 301** |
| 900 функций впереди | 901 из 902 | 300·901 + 902 = **271 202** | **271 202** |

Три предсказания, три совпадения знак в знак. Гипотеза «цена растёт с числом уже
сделанных поисков» на этих же пробах предсказывала бы 45 451 во всех трёх
случаях и провалилась.

Число зовов во всех трёх — 301, оно не меняется. Меняется только место.

## Почему цена «росла по ходу прогона»

Список описаний по ходу прогона НЕ растёт, и это видно по той же ведомости
витков. `«Описания программы»` обходит список ровно один раз за подготовку, по
8 витков на функцию, поэтому витки, делённые на входы, называют длину списка:

| прогон | витков у «Описания программы» | входов | на одну подготовку |
|---|---:|---:|---:|
| потолок 20 млрд (замер соседа) | 31 308 079 | 524 | 59 748 |
| потолок 100 млрд (замер соседа) | 114 859 269 | 1 922 | 59 760 |
| мой прогон 29 августа | 21 680 577 | 361 | 60 057 |

Одно и то же число от начала прогона до конца — значит около 7500 функций в
замыкании и ни одной сверх того.

Растёт не список, а МЕСТО тех имён, которые спрашивают. Ведомость идёт по
замыканию сверху вниз, и чем дальше она зашла, тем дальше в списке лежат имена,
о которых она спрашивает. Средняя цена поиска идёт от нуля к длине списка, а
накопленный итог из-за этого выглядит треугольным — по ПРОЙДЕННОЙ доле работы, а
не по числу поисков.

## Почему двоичный до сих пор перебирает

Словарь в `flang/self/interpret.flang` есть с 25–26 августа (`c47a77d6`,
`9b66cbd1`). Семя `bootstrap/` напечатано 23 августа (`58b037c2`), то есть ДО
словаря. Правки в `flang/self/**` доезжают до двоичного только перепечаткой, и
пока её нет, работает перебор.

## Сколько это стоит на самом деле, и в каких единицах

Замер 29 августа 2026: два двоичных из ОДНОГО семени, различающихся только телом
`«Найти описание»` (у второго вместо перебора словарь по имени, ответ тот же —
побеждает первое описание с таким именем). Оба — `check
flang/self/bootstrap/compiler.flang --proof --предел-шагов 100000000000`, оба
остановлены нехваткой памяти на ОДНОМ И ТОМ ЖЕ месте работы (входов 87 562 410
против 87 561 984), поэтому числа сравнимы напрямую.

| | перебор | словарь | во сколько раз |
|---|---:|---:|---:|
| зовов `«Найти описание»` | 6 502 961 | 6 502 914 | — |
| витков в поиске | 989 497 119 | 6 502 914 | **152** |
| витков на один поиск | 152,2 | 1,0 | 152 |
| витков всего | 1 409 288 856 | 426 292 646 | 3,3 |
| заряда всего | 27 393 657 859 | 27 447 758 812 | 1,0 |
| время | 496,91 с | 479,25 с | 1,04 |
| пик памяти | 12 076 760 КБ | 12 055 916 КБ | 1,0 |

**Два прибора отвечают по-разному, и оба правы.** Перебор — это 70 % ВИТКОВ, а
по часам его снятие дало 3,5 %: цикл по массиву, где имя поля берётся сравнением
указателей, процессору почти ничего не стоит. Значит починка дорога не для
часов, а для ПРЕДЕЛА ШАГОВ — она снимает ту самую стену, о которую перепечатка
билась 24 августа (`«Найти описание» исчерпала лимит шагов (4000000000)`).

И отсюда же: стена после починки ПЕРЕЕЗЖАЕТ, а не исчезает. Заряд встроенных
форм не изменился ни на процент, а он в этом прогоне в 19 раз больше витков.
Прямой показ — `flang test flang/self/bootstrap/compiler.flang` обоими
двоичными. Оба упираются в предел 20 млрд шагов на `«Описания программы»`, и
починка поиска не сдвигает ни шага:

| | перебор | словарь |
|---|---:|---:|
| зовов `«Найти описание»` | 19 871 | 19 871 |
| витков в поиске | 858 660 | 19 871 |
| витков всего | 68 111 281 | 67 271 836 |
| заряда всего | 20 154 903 754 | 20 155 746 054 |
| заряда у `«Описания программы»` | 4 294 695 239 | 4 294 388 312 |
| подготовок программы | 146 | 146 |
| время | 226,82 с | 235,71 с |
| чем кончилось | предел шагов на `«Описания программы»` | то же самое |

Прогон примеров даже не доходит до примеров: 146 подготовок программы по
29,4 млн заряда каждая съедают предел раньше.

## Что это значит для перепечатки

Перепечатка — это и есть починка. Проверять на исходниках нечего: словарь
написан, слит и доказан, он просто не доехал.

Но одной её мало, и это надо знать заранее:

* **семя витки считает, а встроенные формы не заряжает вовсе**
  (`grep -c fl_charge bootstrap/flang_runtime.c` → 0). Новое семя будет
  напечатано с нынешним рантаймом, где заряд есть. Значит новый двоичный начнёт
  ПЛАТИТЬ шагами за работу, которую старый делал даром;
* самая дорогая из таких работ уже видна: проверка повтора имени в
  `«Описания программы»` (`«имена» содержит «имя»`) обходит весь накопленный
  список имён, а рантайм заряжает `содержит` числом пройденных элементов. Это
  N·(N−1)/2 заряда на каждую подготовку программы: замер даёт 29,6 млн на
  подготовку и 10 675 490 917 заряда за 361 подготовку — 39 % всего заряда
  прогона;
* подготовок столько потому, что `«Вызвать»` зовёт `«Подготовить»` НА КАЖДЫЙ
  прогон примера, хотя рядом уже лежат `«Подготовить программу»` и
  `«Вызвать готовое исходом»`, сделанные ровно для того, чтобы готовить один
  раз.
