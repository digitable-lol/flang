# Чего не хватает FTS, чтобы искать противоречия

Замысел `fspec` — спеки бизнес-требований на flang и машина, которая ищет
**противоречия** между ними: легаси закрыто спекой, бизнес просит фичу, новая
спека обязана не противоречить старым. Эта заметка отвечает на один вопрос:
**что из этого уже умеет дерево, а чего в нём нет вовсе.** Ответ снят прогонами,
не чтением; каждый прогон воспроизводится командой, которая рядом записана.

Образец, на котором всё меряно, — `docs/спецификации/слой-отказов.flang`.
Сторож — `flang/test/спецификация-слой-отказов.test.mjs`.

## 1. Формат `.fts` мёртв, поверхность FTS жива

```
$ flang check модель.fts
{"error":"…","diagnostics":[{"code":"FLANG_FTS_REMOVED",…}]}
```

Отказ приходит от всех четырёх читающих команд (`check`, `ast`, `run`, `test`) —
`flang/test/fts-ubran.test.mjs` держит это тестом. Мост `flang/src/compat.mjs`
(760 строк) на месте, но `fromFtsDocument` вызывать неоткуда: строить
`FtsDocument` в этом дереве больше нечем.

**Значит спека в файле `.fts` не проверяется ничем** — это текст в другом
синтаксисе. Поэтому образец лежит в `.flang`: разборщик языка сам понимает
`категория`, `объект`, `утилита`, `правило`, `свойство`, `пример`, `морфизм` и
кладёт их в узлы `ftsLegacy`, а файл при этом остаётся живой программой.

## 2. Сколько поверхности FTS доезжает до проверки: одна конструкция из семи

Прогон. Файл с заведомо ЛОЖНЫМ свойством и заведомо ЛОЖНЫМ примером внутри
утилиты FTS:

```
$ flang check проба.flang
{"valid":true,"module":"Проба","functions":[{"name":"Удвоить","total":true}],
 "types":["Покупка"],"diagnostics":[]}
$ flang test проба.flang
{"valid":true,"total":0,"passed":0,"failed":0,"results":[]}
$ flang run проба.flang --function «Рассчитать скидку»
{"error":"не найдена функция «Рассчитать скидку»",…}
```

Ложь принята молча, кодом возврата 0.

| конструкция FTS | куда доезжает | проверяется ли |
|---|---|---|
| `объект` + поля | `types[]` проверки типов | **да** |
| `категория` | `legacy[]` | нет |
| `утилита` | `legacy[]` | нет |
| `правило` | `legacy[]` | нет |
| `свойство` | `legacy[]` | нет |
| `пример` | `legacy[]` | нет |
| `морфизм` | `legacy[]` | нет |

**Одна из семи.** Синтаксис при этом разбирается строго: правило без `если`
даёт `FLANG_PARSE`. То есть FTS сегодня — проверяемая **грамматика** и
непроверяемая **семантика**.

Отсюда устройство образца: таблица правил стоит в поверхности FTS и сводится с
деревом СВОИМ сторожем (`ftsLegacy` машиночитаем, и сторож читает именно его), а
утверждение, которое язык умеет проверить сам, записано обычной тотальной
функцией с постусловием и примерами. Дыра названа отдельным тестом
(«ДЫРА: примеры и свойства внутри утилиты FTS не исполняются ничем»), а не
обойдена.

## 3. Два противоречащих требования: не ловится ничем

Три попытки, от самой слабой к самой сильной.

**(а) Два правила FTS, несовместных на одном входе, плюс два несовместных
свойства** — «постоянному клиенту 10 %» и «в акционный период скидок нет», затем
«результат не меньше 10» и «результат меньше 10»:

```
$ flang check противоречие-fts.flang
{"valid":true,…,"diagnostics":[]}          код возврата 0
$ flang test противоречие-fts.flang
{"valid":true,"total":0,"passed":0,"failed":0}   код возврата 0
```

**(б) Два постусловия настоящей функции языка**, `результат не меньше 10` и
`результат меньше 10` — то есть требование, невыполнимое ни на одном входе:

```
$ flang check противоречие-язык.flang --proof --json
valid: true, диагностик: 0
  declared | требование продаж: скидка не меньше десяти
  declared | требование финансов: скидка меньше десяти
  claims: {total: 2, proved: 0, refused: 0, violated: 0, declared: 2}
```

Ведомость доказательства называет оба утверждения словом `declared` —
«объявлено, не доказано: ни теоремы, ни примеров. Его считает рантайм после
каждого возврата — на тех входах, которые придут». Про то, что вместе они
невыполнимы, не сказано ничего.

**(в) То же под квантором `для всех`** — сильнейшее, что язык умеет высказать о
всех входах:

```
$ flang check противоречие-forall.flang --proof --json
valid: true, диагностик: 0
  claims: {total: 2, proved: 0, declared: 2, refused: 0, violated: 0}
```

Тот же ответ. **Ноль из трёх.**

Единственное, что краснеет, — пример, случайно попавший в противоречивую
область:

```
$ flang test противоречие-язык2.flang
{"valid":false,"failed":1,"results":[{…,"error":
  "нарушено свойство «требование финансов: скидка меньше десяти»",
  "code":"FLANG_PROPERTY"}]}     код возврата 1
```

Но это не находка противоречия, а **совпадение**: краснеет один вход, названо
одно нарушенное свойство, вторая половина пары не упомянута, и без примера
никакого сигнала нет вовсе. Ровно тот случай, про который в этом дереве принято
говорить, что зелёное ничего не значит: противоречие в требованиях сегодня
кончается либо тишиной, либо падением в проде.

## 4. Что придётся достроить в `fspec` — счётом

Считается от того, что измерено выше, а не от общего впечатления.

1. **Исполнять утилиту FTS.** Шесть конструкций из семи сегодня инертны. Обратный
   ход дешевле, чем кажется: переводить надо не из `FtsDocument` чужого ядра, а
   из узла `ftsLegacy`, который разборщик уже строит целиком (правила, свойства,
   примеры — всё внутри). Мост `compat.mjs` держит семантику построчно и годится
   образцом. Без этого шага «спека» остаётся текстом.

2. **Решатель выполнимости.** Ядро сегодня умеет три вердикта — доказано,
   опровергнуто примером, объявлено. Вопрос «существует ли вход, на котором
   выполнены оба требования» не задаётся нигде: `refused` и `violated` в
   ведомости растут только от примеров и сеток. Нужен четвёртый вердикт —
   **невыполнимо** — и решатель над тем фрагментом, в котором пишутся требования:
   сравнения (`не меньше`, `меньше`, `равен`) над числом, строкой и признаком,
   соединённые «и притом». Это линейная арифметика с равенствами — разрешимый
   фрагмент, не общая логика первого порядка. Пары `∀`-требований проверяются
   попарно; при N требованиях это N(N−1)/2 запросов, и для спеки бизнес-размера
   счёт мал.

3. **Противоречие МЕЖДУ спеками, а не внутри одной.** Здесь FTS даёт больше, чем
   язык: функтор наследия
   (`flang/test/fixtures/fts-naslediye/скидки-в-подписки.fts`) — это словарь
   между двумя спеками, который утверждает, что «Заказ» одной и «Подписка»
   другой — одно понятие. Без такого словаря сравнивать правила двух спек не
   имеет права никто, и это ровно та конструкция, которой нет ни в одном другом
   формате требований. Она **разбирается** языком и **не значит** для него
   ничего: перенести по ней требование и проверить пару — работа, которой нет.

4. **Что переиспользуется как есть.** Ядро доказательств, ведомость с честным
   различением «доказано» и «сетка N», коды диагностик, проверка типов,
   `ftsLegacy` как машиночитаемое представление спеки, приём «сторож на
   расхождение спеки с деревом» — образец в этой папке показывает, что приём
   работает и краснеет.

Порядок работ обратный порядку списка: без пункта 1 нечего решать, без пункта 2
нечего сравнивать, без пункта 3 сравнение ограничено одной спекой.
