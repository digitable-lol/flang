# FTS syntax highlighting

Everything needed to get `.fts` syntax highlighting in editors, on GitHub, and
on the Digitable courses site (Hugo/Chroma). Four independent grammars, kept
in sync by hand against the same three sources of truth:

- `docs/language.ru.md` (repo root) - the full language reference.
- `src/natural-parser.ts` (repo root) - the actual keyword list for both the
  Russian and English natural surfaces. If you add/change a keyword there,
  update all four grammars below and re-run the checks in this README.
- `examples/**/*.fts` and `tools/ftsc/stdlib/**/*.fts` (repo root) - the
  regression corpus every grammar is checked against.

FTS files can be in any of three shapes, and every grammar here has to
tolerate all three:

1. **Natural surface** (Russian or English, indentation-significant) -
   `категория «Имя»` / `category Name` followed by an indented body of
   `объект`/`морфизм`/`теорема`/`утилита` blocks. This is the recommended,
   modern surface (see `docs/language.ru.md`).
2. **Legacy brace surface** - `category Name { structure X { a: string } }`,
   kept for backward compatibility (`examples/task-status.fts`,
   `examples/socrates.fts`).
3. **ftsc module/functor-mapping headers** - `модуль`/`module`,
   `использует`/`uses ... from ...`, `экспортирует`/`exports`, and standalone
   functor-mapping files starting with `функтор`/`functor ... from ... to ...`
   (all of `tools/ftsc/stdlib/**`). These are a thin header ftsc strips off
   before handing the rest of the file to the core natural-surface parser
   (see `tools/ftsc/src/parse-module.mjs`), not a separate language.

## What's where

```
editors/
  tree-sitter-fts/   tree-sitter grammar (Neovim, Helix, Zed, GitHub via linguist)
  vscode-fts/        TextMate grammar + minimal VS Code extension
  chroma/            Chroma XML lexer (Hugo `fts` code fences, other Go tools)
  linguist/          github-linguist submission scaffold (languages.yml + samples/)
  README.md          this file
```

`../.gitattributes` (repo root) additionally marks `*.fts linguist-language=FTS`
so GitHub attributes/diffs treat the extension consistently even before the
linguist PR below lands.

## `tree-sitter-fts/`

A single grammar (`grammar.js`) that parses all three surfaces above. The
natural surface's indentation is handled by an external scanner
(`src/scanner.c`, ~150 LOC) that emits `NEWLINE`/`INDENT`/`DEDENT` tokens only
when it actually crosses a line break - modelled on the same technique used by
tree-sitter-python and tree-sitter-yaml. Because of that, the legacy brace
surface (which never asks for those tokens mid-line) is completely unaffected
and parses with ordinary grammar tokens; `\n` is just a normal `extras` token
there, like `;`/`,` are in `src/parser.ts`'s `skipSeparators()`.

Provided:
- `grammar.js` - the grammar.
- `src/scanner.c` - the external scanner.
- `queries/highlights.scm`, `queries/folds.scm`, `queries/indents.scm`.
- `src/parser.c`, `src/grammar.json`, `src/node-types.json` - generated by
  `tree-sitter generate` and checked in, matching the convention of most
  `tree-sitter-*` grammar repos (so consumers only need a C compiler, not the
  tree-sitter CLI, to build the native parser).

### Regenerate / verify locally

```bash
cd editors/tree-sitter-fts
npm i --no-save tree-sitter-cli   # or use a global install
npx tree-sitter generate
npx tree-sitter parse ../../examples/**/*.fts ../../tools/ftsc/stdlib/**/*.fts
```

A clean run prints one line per file with no `(ERROR ...)` / `(MISSING ...)`
nodes. This was run against all 19 files in `examples/**` and
`tools/ftsc/stdlib/**` (plus 27 more `.fts` files found elsewhere in the repo)
with zero parse errors; see the task report for the exact transcript.

### Install locally

**Neovim** (via [nvim-treesitter](https://github.com/nvim-treesitter/nvim-treesitter)):
add a parser config pointing at this directory, e.g. with
[nvim-treesitter's `parser_config`](https://github.com/nvim-treesitter/nvim-treesitter/blob/master/CONTRIBUTING.md#adding-a-parser):

```lua
require('nvim-treesitter.parsers').get_parser_configs().fts = {
  install_info = {
    url = '/absolute/path/to/fts-upstream/editors/tree-sitter-fts', -- or a git URL once published
    files = { 'src/parser.c', 'src/scanner.c' },
  },
  filetype = 'fts',
}
vim.filetype.add({ extension = { fts = 'fts' } })
```
then `:TSInstall fts`, and copy `queries/*.scm` into
`~/.local/share/nvim/lazy/nvim-treesitter/queries/fts/` (or wherever your
plugin manager keeps queries) if `:TSInstall` doesn't already pick them up
from the grammar repo.

**Helix**: add to `languages.toml`:
```toml
[[language]]
name = "fts"
scope = "source.fts"
file-types = ["fts"]
comment-token = "//"

[[grammar]]
name = "fts"
source = { path = "/absolute/path/to/fts-upstream/editors/tree-sitter-fts" } # or a git source once published
```
then `hx --grammar build` and copy `queries/*.scm` into
`~/.config/helix/runtime/queries/fts/`.

**Zed**: Zed loads tree-sitter grammars through its extension system
(`extension.toml` + a `languages/fts/config.toml` pointing `grammar = "fts"`
at this repo, plus the same three query files under `languages/fts/`). See
Zed's [language extension docs](https://zed.dev/docs/extensions/languages)
for the extension scaffold; this directory already has everything the
extension needs to reference.

**GitHub / linguist**: see `linguist/README` below - linguist references this
grammar by git URL once both are published, it doesn't vendor a copy.

### Publish upstream

1. Push `editors/tree-sitter-fts/` as its own repo (e.g.
   `digitable/tree-sitter-fts`), ideally under the
   [tree-sitter GitHub org](https://github.com/tree-sitter) or linked from
   https://github.com/tree-sitter/tree-sitter/blob/master/docs/index.md's
   community grammar list.
2. Tag a release; `nvim-treesitter`, Helix and Zed all install grammars by
   git URL + rev, so any tag/commit works.
3. Optionally open PRs against `nvim-treesitter`'s and Helix's grammar
   registries to make `:TSInstall fts` / the Helix grammar list work out of
   the box, and against `zed-industries/extensions` for a first-party Zed
   extension.

## `vscode-fts/`

`syntaxes/fts.tmLanguage.json` (TextMate grammar) + a minimal extension
(`package.json`, `language-configuration.json`) that associates it with
`.fts` and registers comment/bracket/auto-closing behaviour.

Verified by tokenizing the full regression corpus with `vscode-textmate` +
`vscode-oniguruma` (the same engine VS Code uses) and confirming every
non-blank line produces at least one non-default scope, and spot-checking
that keywords get the expected scope (`keyword.control.declaration.fts`,
`keyword.operator.comparison.fts`, `support.type.builtin.fts`,
`constant.language.boolean.fts`, etc.) - see the task report for the actual
tokenizer output. One real bug this caught and fixed: `is` (the English
`является`/`is` field modality) was shadowing the longer `is at least`/
`is at most` comparison phrases because it was checked first; comparison
operators are now matched before the modality keyword.

### Install locally

```bash
# Symlink into your extensions folder (fastest for local development):
ln -s /absolute/path/to/fts-upstream/editors/vscode-fts ~/.vscode/extensions/fts-language

# Or package + install a VSIX:
npm i -g @vscode/vsce
cd editors/vscode-fts && vsce package
code --install-extension fts-language-0.1.0.vsix
```
Reload VS Code; `.fts` files should highlight immediately.

### Publish upstream

Publish to the VS Code Marketplace with `vsce publish` (needs a publisher
account), or submit the grammar to
[`microsoft/vscode`'s extension gallery / textmate-grammars repositories](https://github.com/microsoft/vscode) if a first-party listing is wanted.
The same `syntaxes/fts.tmLanguage.json` is also what you'd point
`github/linguist`'s `script/add-grammar` at (see `linguist/README` below).

## `chroma/`

`fts.xml` - a [Chroma](https://github.com/alecthomas/chroma) XML lexer, the
format Hugo uses for ` ```fts ` fenced code blocks (currently rendered with no
highlighting on the courses site) and any other Go tool that embeds Chroma.
Modelled on Chroma's own indentation-language lexers (e.g. `python.xml`) but
kept to a single flat `root` state plus small string/comment sub-states,
since Chroma's regex engine (Go's RE2) has no lookahead and highlighting
doesn't need real block nesting the way the TextMate grammar's bracket
matching does.

**Not executed with real Chroma** (no Go toolchain in the environment that
built this). Instead: the XML was checked for well-formedness
(`xmllint --noout`) and the *rule-matching algorithm* was faithfully
reproduced in Python (state list, first-rule-wins-at-position matching, `push`/
`pop`/`include`) and run against the full regression corpus - every
non-whitespace character in all 19 files was consumed by a specific token
rule, zero fallback/unmatched characters. That is not a substitute for a real
`chroma.NewXMLLexer` + `chroma.Tokenise` run, which should be the first thing
done once a Go environment is available.

### Install locally / verify with real Chroma

```bash
go install github.com/alecthomas/chroma/v2/cmd/chroma@latest
chroma --lexer fts.xml path/to/model.fts   # or whatever chroma's CLI calls
              # for "load a lexer from a file" in the installed version
```
For Hugo specifically, Hugo vendors Chroma internally and does not currently
support loading an arbitrary external lexer XML file at build time - shipping
this for Hugo requires the upstream submission below (or a custom Hugo build
that registers it via Chroma's Go API, `lexers.Register(chroma.MustNewXMLLexer(...))`,
from a local module).

### Publish upstream

1. Open a PR against
   [`alecthomas/chroma`](https://github.com/alecthomas/chroma), adding
   `fts.xml` to `lexers/embedded/` (their format, confirmed by fetching a
   sample lexer from that directory during development of this file).
2. Once merged and released, bump Hugo's Chroma dependency (or wait for
   Hugo's next release that picks it up) - Hugo's `highlight` shortcode /
   ` ```fts ` fences will then Just Work without any courses-site changes.

## `linguist/`

Scaffold for a [github-linguist/linguist](https://github.com/github-linguist/linguist)
PR:
- `languages.yml` - the `FTS:` entry to merge into linguist's `languages.yml`
  (alphabetical order), with `color: "#00e5e5"` (Digitable's brand cyan,
  `--digitable-cyan` in the courses repo's `public/css/digitable.tokens.css`
  - confirmed by reading that file, read-only, per instructions).
  `language_id` is deliberately left as a removable placeholder: per
  linguist's `CONTRIBUTING.md`, that field is assigned by the linguist
  maintainers running `script/update-ids` when the PR lands, not chosen by
  the submitter.
- `samples/` - four real (non "hello world") `.fts` files copied verbatim
  from this repo, covering all three surfaces: `discount.fts` /
  `discount.en.fts` (natural RU/EN), `task-status.fts` (legacy brace),
  `http-request.fts` (ftsc module header + natural body). Linguist's
  `CONTRIBUTING.md` asks for "real-world code" and at least two samples per
  extension; add more from `examples/`/`tools/ftsc/stdlib/` before actually
  filing the PR if their reviewers want a larger corpus.

### What to actually submit to linguist

1. Fork `github-linguist/linguist`, copy `languages.yml`'s `FTS:` block into
   their `languages.yml` in alphabetical order, and copy `samples/*.fts` into
   `samples/FTS/` in their repo.
2. Run `script/add-grammar https://github.com/<org>/tree-sitter-fts` (their
   docs currently vendor a TextMate grammar this way for highlighting, not
   the tree-sitter one directly, and only accepts grammars under one of a few
   permissive licenses - this repo's grammars are MIT, so publish
   `tree-sitter-fts` under MIT and point `add-grammar` at
   `editors/vscode-fts`'s TextMate grammar's published repo, or vendor
   `syntaxes/fts.tmLanguage.json` directly per their tool's instructions).
3. Do **not** hand-fill `language_id` - leave it out entirely (delete the
   placeholder line) and let `script/update-ids` assign it.
4. Follow the rest of `CONTRIBUTING.md` (they require `bundler exec rake
   test` to pass, which needs their full Ruby toolchain - not run here).
