# Ядро FTS на flang — контракт

Цель: переписать ядро FTS (сейчас `src/*.ts`, 4904 строк) на flang, чтобы
печатать его в C и получить нативный `fts` без Node — и дальше в остальные
целевые языки.

## Почему это стало возможно только сейчас

В `tools/ftsc/self/meta.fts` записано ограничение, из-за которого ядро нельзя
было написать на самом FTS:

> в ядре FTS строка является типом поля, но не значением, над которым можно
> вычислять

Парсер — это вычисления над строками. flang снимает ровно это ограничение:
строки в нём данные, а `flang/stdlib/strings.flang` уже даёт `Разбить по
символу`, `Позиция подстроки`, `Начинается с`, `Считать символ`.

## Разбиение и границы

Слои пишутся независимо и стыкуются только через типы этого файла. Никакой
слой не разбирает текст повторно и не заглядывает внутрь чужого слоя.

```
текст .fts ──[лексер]──> список «Токен» ──[парсер]──> «Документ»
                                                          │
                                        ┌─────────────────┴───────────────┐
                                   [вычислитель]                     [печать JSON]
                              значение / диагностика            строка, байт в байт
                                                                  как у ядра на TS
```

## 1. Токены — контракт лексера

```flang
тип «Токен»
  вариант ОтступБольше
  вариант ОтступМеньше
  вариант КонецСтроки
  вариант Имя содержит текст: строка
  вариант Строка содержит текст: строка
  вариант Число содержит значение: число
  вариант Знак содержит текст: строка
  вариант Конец
```

Правила:

- `«имя в кавычках»` и `имя без кавычек` дают один и тот же вариант `Имя`;
  кавычки-ёлочки снимаются, внутренние пробелы сохраняются.
- `"имя в обычных кавычках"` даёт вариант `Строка`: кавычки снимаются, пробелы
  и знаки внутри сохраняются целиком. Это не то же самое, что `Имя`, и
  различие обязательное — ядро на TS хранит его тоже (`kind: "identifier"`
  против `kind: "string"`, `src/parser.ts`). Именем считаются оба варианта
  (`isNameToken`), а ключевым словом — только `Имя`: `"structure"` в кавычках
  объявлением не является, `да` — признак, а `"да"` — строка.
- Пунктуация выделяется отдельными токенами `Знак`: `{ } [ ] ( ) < > : ; , ? |
  &` по одному символу и `->` (а также `=>`, которое ядро печатает как `->`).
  Знак не прилипает к соседнему слову: `structure B {` — три токена,
  `Individual.isHuman` — три, `Human -> Mortal` — три.
- **Точка — знак только там, где слово не является числом.** `10.5` остаётся
  одним `Число`, а `1.`, `.5` и `Individual.isHuman` режутся: ровно там же
  останавливается регулярное выражение числа в `tokenize` ядра.
- Комментарий `//` до конца строки выбрасывается лексером; внутри ёлочек и
  кавычек `//` — часть имени.
- Пустая строка не порождает `КонецСтроки`.
- Отступ — только пробелы, шаг фиксируется первым отступом файла; рваный
  отступ — диагностика `FTS_INDENT`. В скобочном диалекте отступ незначим:
  вложенность там задают скобки, и парсер токены отступа пропускает.
- Число — целое или с точкой, минус допустим. Разбор обязан совпадать с
  `Number(...)` ядра.

Одного потока хватает обеим поверхностям ядра — и отступной
(`src/natural-parser.ts`), и скобочной (`src/parser.ts`): первая знаки просто
не использует, вторая на них стоит.

## 2. Документ — контракт парсера

Дословно повторяет `FtsDocument` из `src/model.ts`. Суммы типов вместо
размеченных объединений TypeScript:

```flang
тип «Скаляр»
  вариант Текст содержит значение: строка
  вариант Число содержит значение: число
  вариант Признак содержит значение: признак
  вариант Ничто

тип «Операнд»
  вариант Значение содержит значение: «Скаляр»
  вариант Поле содержит имя: строка
  вариант Процент содержит процент: число, поле: строка
  вариант Результат

тип «Сравнение»
  вариант Равно
  вариант НеРавно
  вариант НеМеньше
  вариант НеБольше
  вариант Больше
  вариант Меньше

объект «Условие»
  поле: строка
  сравнение: «Сравнение»
  операнд: «Операнд»

объект «Правило»
  имя: строка
  условия: список «Условие»
  действие: «Действие»          // Присвоить | Добавить, оба с операндом

объект «Свойство»
  имя: строка
  сравнение: «Сравнение»
  операнд: «Операнд»

объект «Пример»
  имя: строка
  вход: список «Привязка»       // имя поля → скаляр
  ожидается: строка

объект «Утилита»
  имя: строка
  принимает: строка
  возвращает: строка
  начальное: «Скаляр»
  правила: список «Правило»
  свойства: список «Свойство»
  примеры: список «Пример»
```

Соответствие поверхности: `не меньше` → `НеМеньше`, `равен` → `Равно`,
`да`/`нет` → скаляр признака, `N процентов от поля X` → `Процент`.

**Скаляр — сумма типов, а не строка.** В первой редакции этого файла скаляр был
записан как `строка`, и печать JSON это сразу опровергла: `5`, `"5"` и `да` дают
три разные строки JSON, а по текстовому представлению их не различить. Ошибка
контракта, найденная слоем печати; парсер обязан строить именно `«Скаляр»`.

## 3. Семантика вычислителя

Обязана совпадать с `src/utility.ts` и с таблицей в `flang/SPEC.md`:

| Вопрос | Решение |
|---|---|
| проценты | `(процент / 100) * значение` — именно в этом порядке |
| равенство скаляров | `Object.is` |
| порядок правил | сверху вниз, `Добавить` накапливает, `Присвоить` затирает |
| свойство | постусловие на **всей** области входа, проверяется после всех правил |
| нарушено свойство | код `FTS_UTILITY_PROPERTY`, текст ровно как у ядра |
| пример не сошёлся | код `FTS_EXAMPLE_MISMATCH` |

Свойство проверяется и тогда, когда ни одно правило не сработало — именно
из-за этого процентный предел на отрицательной сумме падал.

## 4. Тотальность

Всё ядро обязано лежать в тотальном классе: `fts check` не имеет права
зависнуть. Циклы «пока есть символы» выражаются свёрткой по списку символов —
он структурно убывает. Где тотальность не доказывается, признак `тотальная`
не ставится, а место записывается в этот файл как долг с объяснением.

## 5. Критерий готовности — дифференциальная сверка

Ядро считается верным не тогда, когда проходят его собственные тесты, а когда
на **всех** `.fts` репозитория старое ядро на TS и новое на flang дают
побайтово совпадающий JSON — включая коды и тексты диагностик. Приём уже
отработан в `flang/src/compat.mjs`: 19 593 входа, ноль расхождений.

## Долги

Раздел пополняется по мере написания слоёв. Долг — это либо место, где не
поставлен признак `тотальная`, либо расхождение с ядром на TS, о котором знают
и которое пока оставлено.

### Лексер (`flang/core/lexer.flang`)

Тотальность: долгов нет. Все функции файла помечены `тотальная` и доказаны
`totality.mjs`. Обход строки по символам заменён на «разделить» плюс свёртка
или рекурсия по полученному списку, а стек отступов (список чисел) снял
единственное место, где напрашивалась бы рекурсия по числу: закрытие
нескольких уровней сразу — это рекурсия по хвосту стека.

Расхождения с ядром на TS, оставленные сознательно:

1. **Нормализация NFC не выполняется.** Ядро зовёт `String.prototype.normalize`
   на каждом имени (`natural-parser.ts`, `readName`), а в flang такой встроенной
   формы нет — её нельзя выразить ни через «разделить», ни через «подстрока».
   Пока все модели репозитория записаны в NFC, расхождение ненаблюдаемо; до
   дифференциальной сверки (раздел 5) в `builtins.mjs` нужна встроенная форма
   «нормализовать».

2. **Блочные комментарии `/* … */` лексер не знает.** Контракт раздела 1 их не
   упоминает, а ядро вырезает их в `sourceLines` до разбиения на строки, то
   есть это забота слоя выше. Если решение изменится, вырезание придётся
   выразить свёрткой по разбиению — приём тот же, что и для `//`.

3. **Экспоненциальная запись числа (`1e3`) считается именем.** Раздел 1
   ограничивает число целым или дробным с необязательным минусом, и лексер
   следует ровно этому; регулярное выражение ядра шире
   (`(?:[eE][+-]?\d+)?`). Ни в одной модели репозитория экспонента не
   встречается. Расширять придётся вместе с разделом 1, а не вместо него.

4. **«Внутри кавычек» определяется чётностью, а не автоматом.** Ядро в
   `stripLineComment` держит состояние посимвольно; здесь незакрытая ёлочка —
   это «`«` больше, чем `»`», а незакрытая кавычка — нечётное их число.
   Совпадает всюду, где кавычки не вложены друг в друга, а вложенных кавычек
   поверхность FTS не допускает. Посимвольный автомат стоил бы тотальности.

5. **Диагностика знает номер строки, но не колонку.** Формат ядра —
   `{ code, message, severity, span }`; лексер заполняет только номер строки,
   потому что колонку без обхода символов не получить. Для `FTS_INDENT` этого
   довольно: рваным бывает отступ, а не позиция в нём.

6. **Незакрытая обычная кавычка не диагностируется.** Ядро (`tokenize`,
   `readName`) отвечает `FTS_UNCLOSED_STRING`; здесь литералом становится весь
   остаток строки, а диагностику лексер даёт только на незакрытую ёлочку.
   Причина та же, что у долга 4: «закрыта или нет» здесь считается чётностью, и
   на строке с одной кавычкой это неотличимо от строки с кавычкой внутри имени
   в ёлочках.

7. **Экранирование внутри литерала не разворачивается.** Ядро понимает `\n`,
   `\t`, `\"`, `\\` и `\uXXXX` (`tokenize`); здесь литерал едет как есть.
   Развернуть первые четыре можно было бы таблицей замен (приём из
   `json.flang`), но `\uXXXX` требует формы «символ по коду», которой в языке
   нет, — а закрывать половину долга хуже, чем назвать его целиком. Ни в одной
   модели репозитория экранирование в литерале не встречается.

8. **Апостроф строкой не открывает.** Ядро принимает `'…'` наравне с `"…"`
   (`tokenize`, `readName`); здесь апостроф — обычный символ имени. В моделях
   репозитория его нет, а различать «апостроф-кавычка» и «апостроф внутри
   слова» чётностью нельзя.

9. **Список знаков перечислен, а не выведен.** Ядро объявляет знаком всё, что
   не имя, не число и не строка; здесь знаки заданы списком из четырнадцати
   символов плюс стрелка. Символ вне списка (`+`, `=`, `*`, `%`, `!`) прилипнет
   к соседнему слову. Вывести «всё остальное» без обхода по символам нельзя, а
   поверхность FTS этих знаков не использует.

### Печать JSON (`flang/core/json.flang`)

Тотальность: долгов нет. Все 31 функция файла помечены `тотальная` и доказаны
`totality.mjs`. Экранирование строки не обходит её по символам (такое убывание
анализ не признаёт), а сворачивает по заранее известной таблице из 34 замен,
каждая из которых выражена через «разделить» и «соединить»; рекурсия по
произвольному значению и по вложенному утверждению убывает по полю варианта и
элементу коллекции, то есть доказывается обычным правилом.

Дифференциальная сверка (раздел 5) на всех `.fts` репозитория: **47 моделей из
47**, ноль расхождений с `JSON.stringify(compile(…))`. Это число воспроизводится
на чистом клоне и ни от чего вне репозитория не зависит; подключение внешних
каталогов моделей (`FTS_MODEL_PATH`, см. `flang/test/corpus.mjs`) охват
увеличивает — фактический печатает сам тест, первой же строкой вывода.
Проверка — `flang/test/core-json.test.mjs`.

Расхождения и отступления, оставленные сознательно:

1. **Одинокий суррогат не экранируется.** `JSON.stringify` начиная с ES2019
   печатает непарный суррогат как `\ud800`, а «Экранировать» оставляет его как
   есть. Отличить суррогат от обычного символа нечем: в языке нет формы «код
   символа», а таблицу из 2048 замен вместо неё писать нельзя. Долг закрывается
   не здесь, а в `builtins.mjs` — встроенной формой «код символа»; тест
   `известный долг: одинокий суррогат не экранируется` закреплён именно затем,
   чтобы закрытие долга не прошло молча. Ни одна модель репозитория непарного
   суррогата не содержит.

2. **Запись числа делегирована встроенной «к строке».** `JSON.stringify`
   печатает число по правилу ECMAScript `Number::toString` (кратчайшая запись,
   дающая то же значение при обратном чтении), и `builtins.mjs` определяет
   «к строке» от числа ровно как `String(значение)`. Выразить это правило на
   самом flang нельзя: оно требует работы с битами мантиссы, а язык таких форм
   не даёт. Поэтому «Печать числа» отвечает только за нефинитные значения
   (`NaN` и бесконечности едут как `null`), а всё остальное — обязательство
   слоя: печать в C/Rust/Java обязана реализовать «к строке» от числа как
   Number::toString, иначе побайтовое совпадение сломается на первой же дроби.

3. **Скаляр операнда — сумма типов, а не строка.** Раздел 2 описывает
   `вариант Значение содержит значение: строка` («скаляр в текстовом виде»).
   Для печати этого недостаточно: `{"kind":"value","value":5}`,
   `{"kind":"value","value":"5"}` и `{"kind":"value","value":true}` —
   три разные строки JSON, а текстовый вид у них один. Поэтому в `json.flang`
   стоит `«Скаляр»` (строка | число | признак | ничто), и то же решение
   понадобится парсеру: разбор обязан сохранять, каким был скаляр в исходнике.

4. **Типы документа шире раздела 2.** Раздел 2 описывает только утилиты, а
   печатать нужно весь `FtsDocument` — `category`, `structures`, `functors`,
   `proposition`, `ts_compat`. Эти типы восстановлены по `src/model.ts` и по
   порядку вставки ключей в `src/parser.ts` и `src/natural-parser.ts`. Если
   парсер на flang объявит их иначе, типы придётся сводить — общий контракт
   должен остаться один.

5. **Словарь представлен списком пар.** `ts_compat`, `selector` утверждения и
   вход примера — словари с ключами от автора модели, а словаря в flang нет.
   Список пар хранит порядок (в JS он тоже определяется порядком вставки,
   поэтому печать совпадает), но допускает то, чего объект JS допустить не
   может, — два одинаковых ключа. Проверки на это нет: значения приходят из
   объекта JS, где повтор невозможен по построению.

### Вычислитель (`flang/core/evaluate.flang`)

Тотальность: долгов нет. Все 20 функций файла помечены `тотальная` и доказаны
`totality.mjs`. Рекурсии в файле нет вовсе: правила, свойства, условия и примеры
— это списки, и обход каждого выражен свёрткой. Короткое замыкание `Array.every`
(условия правила) и «первая диагностика прекращает счёт» (правила и свойства)
выражены состоянием свёртки, а не выходом из цикла: сработавший отказ
протаскивается дальше нетронутым, и тела остальных шагов не вычисляются.

Дифференциальная сверка (раздел 5) на всех `.fts` репозитория: 20 документов,
24 утилиты, 11 180 входов, ноль расхождений — совпадают и значения (по
`Object.is`, до последнего бита), и коды диагностик. Проверка —
`flang/test/core-evaluate.test.mjs`.

Расхождения и отступления, оставленные сознательно:

1. **Скаляр — сумма типов, а не строка.** То же отступление и по той же
   причине, что долг 3 печати JSON: текстовый вид не различает `5`, `"5"` и
   `да`, а `Object.is` их различает, и на этом различии стоит вся семантика
   равенства. Поэтому `«Значение операнда»` несёт `«Скаляр»`, а объявления
   типов раздела 2 в `evaluate.flang` и `json.flang` совпадают дословно —
   вычислитель и печать обязаны читать одно значение. Первая версия файла шла
   за буквой раздела 2 и разбирала текст сама (`parseScalar` ядра, включая
   регулярное выражение числа, выраженное вычёркиванием цифр свёрткой по
   десяти литералам); от этого пришлось отказаться, чтобы не заводить второй
   разбор числа рядом с `Похоже на число` лексера. Раздел 2 стоит поправить.

2. **`executeUtility` не реализована — только `evaluateUtility`.** Раздел 3
   описывает семантику вычисления, и она воспроизведена полностью. Проверки
   входа уровня документа (`FTS_UNKNOWN_UTILITY`, отсутствие объявленного поля
   структуры, `FTS_UTILITY_INPUT_TYPE`, `FTS_UTILITY_INPUT_FIELD`) требуют
   типа структуры и списка утилит, а «Утилита» раздела 2 знает только имя
   своего входа (`принимает: строка`). Эти коды остаются за слоем, который
   увидит «Документ» целиком; `FTS_UTILITY_INPUT` для поля, которого нет в
   переданных привязках, здесь есть — его даёт `resolveField`.

3. **Сводка `testUtilities` не реализована.** `FTS_NO_UTILITIES` и
   `FTS_NO_UTILITY_EXAMPLES` — диагностики документа, а не утилиты, и по той же
   причине им здесь не на что смотреть. Прогон примеров одной утилиты есть:
   «Проверить примеры» возвращает список «Итог примера» — тот же набор полей,
   что у `UtilityExampleResult` ядра.

4. **Текст `FTS_EXAMPLE_MISMATCH` выбран здесь.** Кода `FTS_EXAMPLE_MISMATCH` в
   ядре на TS нет вовсе: `testUtilities` возвращает `passed: false` без
   диагностики, а код введён разделом 3 этого контракта. Сообщение —
   `пример «X» утилиты «Y»: ожидалось A, получено B`, значения печатаются как
   «к строке» (признак — `да`/`нет`, ничто — `ничто`). Дословного образца, с
   которым это можно было бы сверить, не существует; если он появится,
   поменять придётся одну строку.

5. **Диагностика без `span`.** Формат ядра — `{ code, message, severity, span }`;
   «Итог» несёт только код и сообщение. Позиции у вычислителя нет и взяться ей
   неоткуда: он работает над «Документом», из которого разметка исходника уже
   ушла. Слой, который печатает диагностику, обязан добавить `span` правила или
   свойства сам.

6. **Стандартная библиотека не переиспользована — нечего переиспользовать.**
   После отказа от разбора текста (долг 1) в файле не осталось ни одного
   действия над строками, кроме склейки сообщений встроенной «соединить»:
   ни `Разбить по символу`, ни `Заменить` из `flang/stdlib/strings.flang` не
   нужны. Импорта нет и по второй причине: `использует … из "…"`
   (`flang/src/link.mjs`) появился одновременно с этим файлом, и завязывать
   слой ядра на связывание, которое ещё меняется, рано.

7. **Свойства не выражены постусловиями функции.** SPEC языка даёт
   `postconditions` с полями `code` и `message`, и `compat.mjs` переводит
   свойства FTS именно в них. Здесь так нельзя: утилита — это данные, а не
   функция, её свойства известны во время вычисления, а не во время разбора
   `evaluate.flang`. Постусловие пригодится генератору кода (утилита → функция),
   а не вычислителю.

### Парсер (`flang/core/parser.flang`)

Тотальность: долгов нет. Все функции файла помечены `тотальная` и доказаны
`totality.mjs`. Рекурсивного спуска по потоку токенов в файле нет вовсе — ни у
одной из двух поверхностей, и по одной и той же причине: «остаток потока стал
короче» анализ завершаемости частью значения не считает.

Отступная поверхность разбирается тремя свёртками: поток режется на строки
(`«КонецСтроки»` закрывает строку, `«ОтступБольше»` и `«ОтступМеньше»` двигают
глубину), строки собираются в группы «заголовок и всё, что глубже», и только
потом каждая строка разбирается по первым словам — это разбор формы
фиксированной длины. Рекурсия остаётся в пяти вспомогательных функциях
(«Пропустить слова», «Взять слова», «Начинается словами», «Позиция слов»,
«Заменить слова»), и всюду это рекурсия по хвосту списка на одной и той же
позиции аргумента.

Скобочная поверхность разбирается спуском, но не по потоку, а по дереву: поток
свёрткой сворачивается в «Узел» (стек открытых скобок, строки режутся тут же),
и дальше поддерево — это поле варианта, а строка группы — элемент списка, то
есть строго меньшая часть того же значения. Взаимная рекурсия там есть —
«Утверждение из узлов» ↔ «Шаг тела утверждения» для вложенных утверждений и три
функции разбора произвольного значения, — и в каждом цикле убывает **первый**
аргумент, то есть одна и та же позиция на каждом ребре, как того требует
`totality.mjs`.

Сквозная сверка (раздел 5) — `текст → лексер → парсер → печать JSON` против
`JSON.stringify(compile(…))`: **47 моделей из 47, ноль расхождений**, обе
поверхности. Число — репозиторное, воспроизводимое на чистом клоне; внешние
каталоги моделей подключаются переменной `FTS_MODEL_PATH` и охват увеличивают,
а фактический охват прогона тест печатает сам.
Диагностики сверены отдельно: на 34 намеренно сломанных моделях
отступной поверхности и на 13 моделях скобочной совпадают и код, и текст
сообщения. Проверка — `flang/test/core-parser.test.mjs`.

Расхождения и отступления, оставленные сознательно:

1. **Документ в записи JSON не разбирается.** `compile` ядра отправляет текст,
   начатый с `{`, `[` или `export default`, в `compileJsonLike` — это не
   поверхность FTS, а чтение готового `FtsDocument`, и парсера JSON здесь нет.
   Такой текст попадает в скобочный разбор и получает `FTS_EXPECTED_KEYWORD`.
   Ни одна модель репозитория так не записана; закрывается отдельным слоем
   (`normalizeDocument`), а не этим файлом.

2. **Незакрытая скобка: код совпадает, текст — не всегда.** Ядро не знает
   такой беды отдельно: оно упирается в конец файла там, где стоял курсор, и
   текст зависит от того, что оно в этот момент читало. Две частые формы
   воспроизведены дословно — незакрытое тело категории даёт
   `unexpected token '<eof>' in category`, незакрытое тело структуры —
   `expected '}', got '<eof>'`. Для более глубоких случаев (незакрытый список
   значения, незакрытое тело утверждения) код остаётся `FTS_UNEXPECTED_TOKEN`,
   а текст — от первой из этих двух форм. Чтобы совпасть и здесь, пришлось бы
   вернуть в разбор курсор, то есть ровно то, от чего этот файл уходит.

   Из того же корня растёт и второе мелкое расхождение: недостающий токен в
   конце строки печатается здесь как `<eof>`, а ядро печатает перевод строки,
   на который наткнулось (`expected value, got '\n'`). Строки в дереве уже
   порезаны, и перевода строки в нём нет. Код при этом совпадает всегда.

   Так же и с лишними словами в заголовке утверждения (`witness A.b.c {`):
   ядро останавливается на первом же неожиданном знаке, а здесь заголовок
   проверяется по числу собранных имён, и в сообщении названо не то слово.
   Код — тот же `FTS_UNEXPECTED_TOKEN` с тем же `expected '{', got …`.

3. **Диагностика не знает номера строки.** Формат ядра —
   `{ code, message, severity, path }`, где `path` для натуральной поверхности
   это `строка N`. Поток токенов раздела 1 позиций не несёт вовсе (у лексера
   номер строки есть только в его собственной диагностике), а восстанавливать
   номера пересчётом значило бы разбирать текст второй раз — то есть завести в
   парсере свой лексер. Закрывается расширением раздела 1: токен обязан нести
   номер строки.

4. **Скобочный диалект знает не всё, что знает `tokenize` ядра.** Обобщённые
   типы (`Array<string>`) приезжают из лексера отдельными знаками и
   склеиваются `«Формат типа»` дословно по правилам `formatType`, но
   `genericDepth` не считается: `;` и перевод строки внутри `<…>` закроют
   объявление поля, а ядро их пропустит. Точно так же не поддержан тип, внутри
   которого стоит скобочная группа (`{ a: number }` как тип поля): группа
   печатается одним знаком. Ни того ни другого в моделях репозитория нет.

5. **`«да»` и `да` неразличимы, `"да"` — различимо.** Ядро читает
   `начинает с да` как признак, `начинает с "да"` — как строку (кавычки видны в
   тексте), и `начинает с «да»` — тоже как строку. Обычные кавычки теперь
   приезжают отдельным вариантом `«Строка»`, и второй случай совпал; ёлочки
   лексер по-прежнему снимает (раздел 1), поэтому третий случай остаётся
   расхождением. Ни одна модель репозитория ключевого слова в ёлочки не
   заключает.

6. **Имя ядра шире слова лексера.** `readName` выделяет имя регулярным
   выражением по `ID_Start`/`ID_Continue` и допускает внутри дефис, поэтому
   `клиент-VIP+1` даёт имя `клиент-VIP` и остаток `+1`; лексер отдаёт одно
   слово целиком. Знаки из списка раздела 1 (в том числе точка) теперь режутся
   правильно, остальные — нет. Закрывается расширением списка знаков, но не
   целиком: «всё, что не буква» без обхода по символам не выразить.

7. **`ts_compat` структуры считается приближённо.** `renderTsCompat` ядра
   решает, идентификатор ли имя, регулярным выражением по свойствам Юникода
   (`\p{ID_Start}`); здесь проверка обратная — имя не начинается с цифры и не
   содержит ни одного знака из списка «чужих». На буквах любых алфавитов ответ
   совпадает. Вторая половина долга серьёзнее: `typescriptAlias` печатает
   имя-неидентификатор как `FTS_` и коды его символов в шестнадцатеричном виде,
   а в этой ветке остаётся один префикс. Здесь стояло, что причина — «формы
   «код символа» в языке нет»; это перестало быть правдой 9 августа 2026.
   Форма есть, и перевод кода в шестнадцатеричную запись на flang **пишется**
   и доказывается тотальным (`код символа`, деление с остатком, `символ N в
   "0123456789abcdef"` — проверено прогоном против эталона на «A», «a», «я»,
   «0»). Долг остаётся долгом, но он теперь «не написано», а не «нельзя». Ни
   одна модель репозитория в эту ветку не заходит: там, где она срабатывает,
   `ts_compat` разойдётся с ядром.

8. **Ошибки копятся, а сообщается первая.** Ядро бросает исключение из середины
   разбора; в flang исключений нет, поэтому каждая функция возвращает пару
   «значение и список ошибок». Порядок накопления совпадает с порядком
   исходника, поэтому первая ошибка списка — та самая, на которой упало бы
   ядро. Расхождение возможно только там, где ядро упало бы раньше, чем дошло
   до строки, которую этот парсер всё-таки разобрал; на корпусе такого нет.

9. **Английская поверхность переписывается по словам, а не по тексту.**
   `normalizeEnglishNaturalSurface` работает регулярными выражениями по строке и
   поэтому заменит `equals` и внутри имени в кавычках; здесь замена идёт по
   списку слов, и имя, склеенное в одно слово, не трогается. Ядро в этом месте
   ведёт себя хуже, а не лучше, но формально это расхождение. Там же: `percent`
   и `percents` — две строки таблицы вместо одной группы `(?:s)?`, поэтому
   строка с обоими написаниями сразу заменилась бы дважды, а не один раз.

10. **24 разбора закрыты `случай любое`, и это снимает проверку
    исчерпывающности с 95 случаев.** Долг записан здесь потому, что AGENTS.md
    требует записывать намеренное расхождение, а не оставлять его в молчании, —
    а этот в списке отсутствовал, хотя он самый крупный в файле по числу
    незакрытых обязательств.

    **Измерено, не оценено.** Джокеры изъяты из копии файла в памяти
    (`случай любое` вместе с телом), копия связана и проверена: ровно **24**
    диагностики `FLANG_MATCH_NOT_EXHAUSTIVE`, и перечисленных в них непокрытых
    вариантов — **95**. Остальные три слоя ядра (`lexer.flang`, `json.flang`,
    `evaluate.flang`) джокеров не имеют вовсе: их разборы перечисляют варианты
    полностью. В `flang/stdlib/*.flang` джокеров ноль.

    **Что именно теряется.** Все 24 стоят на СУММАХ, а не на скалярах, то есть
    ни один из них языком не вынужден (на скалярах `случай любое` обязателен —
    их значения не перечислить). Идиом всюду один: предикат или доступ к полю с
    запасным ответом — `«Это имя»`, `«Слово токена»`, `«Вид узла»`. Худшие пять
    закрывают по 7 вариантов «Токена» каждый.

    **Цена, которую это назначает будущему.** Девятый вариант `«Токен»`
    компилятор не потребует разобрать в 11 местах — он молча уйдёт в запасную
    ветку и вернёт «нет»/пусто. Это не гипотеза: тот же идиом рядом, выписанный
    перечислением, на новом варианте честно краснеет
    `разбор «Токен» не покрывает «Пробел»`. То есть в ядре сегодня работает
    правило «новый вариант — не ошибка», а в остальном корпусе — «новый вариант
    ошибка», и разница ровно в этих 24 строках.

    **Чем закрывается.** Не запретом джокера: предикату действительно нужен
    один ответ на все остальные варианты, и перечисление 7 случаев вместо
    `случай любое` сделало бы файл длиннее без выигрыша в проверяемости. Нужна
    форма, которая говорит «остальные», НЕ теряя обязательства пересмотреть
    место при добавлении варианта, — например `случай остальные из «Токен»`,
    проверяемая против списка вариантов на момент написания. Такой формы в языке
    нет, и это работа по языку, а не по ядру, поэтому долг остаётся долгом.
