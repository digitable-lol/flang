# Ядро FTS на flang — контракт

Цель: переписать ядро FTS (сейчас `src/*.ts`, 3155 строк) на flang, чтобы
печатать его в C и получить нативный `fts` без Node — и дальше в остальные
целевые языки.

## Почему это стало возможно только сейчас

В `tools/ftsc/self/meta.fts` записано ограничение, из-за которого ядро нельзя
было написать на самом FTS:

> в ядре FTS строка является типом поля, но не значением, над которым можно
> вычислять

Парсер — это вычисления над строками. flang снимает ровно это ограничение:
строки в нём данные, а `flang/stdlib/strings.flang` уже даёт `Разбить по
символу`, `Позиция подстроки`, `Начинается с`, `Считать символ`.

## Разбиение и границы

Слои пишутся независимо и стыкуются только через типы этого файла. Никакой
слой не разбирает текст повторно и не заглядывает внутрь чужого слоя.

```
текст .fts ──[лексер]──> список «Токен» ──[парсер]──> «Документ»
                                                          │
                                        ┌─────────────────┴───────────────┐
                                   [вычислитель]                     [печать JSON]
                              значение / диагностика            строка, байт в байт
                                                                  как у ядра на TS
```

## 1. Токены — контракт лексера

```flang
тип «Токен»
  вариант ОтступБольше
  вариант ОтступМеньше
  вариант КонецСтроки
  вариант Имя содержит текст: строка
  вариант Число содержит значение: число
  вариант Конец
```

Правила:

- `«имя в кавычках»` и `имя без кавычек` дают один и тот же вариант `Имя`;
  кавычки-ёлочки снимаются, внутренние пробелы сохраняются. Различать их
  дальше не нужно: ядро на TS этого различия тоже не хранит.
- Комментарий `//` до конца строки выбрасывается лексером.
- Пустая строка не порождает `КонецСтроки`.
- Отступ — только пробелы, шаг фиксируется первым отступом файла; рваный
  отступ — диагностика `FTS_INDENT`.
- Число — целое или с точкой, минус допустим. Разбор обязан совпадать с
  `Number(...)` ядра.

## 2. Документ — контракт парсера

Дословно повторяет `FtsDocument` из `src/model.ts`. Суммы типов вместо
размеченных объединений TypeScript:

```flang
тип «Скаляр»
  вариант Текст содержит значение: строка
  вариант Число содержит значение: число
  вариант Признак содержит значение: признак
  вариант Ничто

тип «Операнд»
  вариант Значение содержит значение: «Скаляр»
  вариант Поле содержит имя: строка
  вариант Процент содержит процент: число, поле: строка
  вариант Результат

тип «Сравнение»
  вариант Равно
  вариант НеРавно
  вариант НеМеньше
  вариант НеБольше
  вариант Больше
  вариант Меньше

объект «Условие»
  поле: строка
  сравнение: «Сравнение»
  операнд: «Операнд»

объект «Правило»
  имя: строка
  условия: список «Условие»
  действие: «Действие»          // Присвоить | Добавить, оба с операндом

объект «Свойство»
  имя: строка
  сравнение: «Сравнение»
  операнд: «Операнд»

объект «Пример»
  имя: строка
  вход: список «Привязка»       // имя поля → скаляр
  ожидается: строка

объект «Утилита»
  имя: строка
  принимает: строка
  возвращает: строка
  начальное: «Скаляр»
  правила: список «Правило»
  свойства: список «Свойство»
  примеры: список «Пример»
```

Соответствие поверхности: `не меньше` → `НеМеньше`, `равен` → `Равно`,
`да`/`нет` → скаляр признака, `N процентов от поля X` → `Процент`.

**Скаляр — сумма типов, а не строка.** В первой редакции этого файла скаляр был
записан как `строка`, и печать JSON это сразу опровергла: `5`, `"5"` и `да` дают
три разные строки JSON, а по текстовому представлению их не различить. Ошибка
контракта, найденная слоем печати; парсер обязан строить именно `«Скаляр»`.

## 3. Семантика вычислителя

Обязана совпадать с `src/utility.ts` и с таблицей в `flang/SPEC.md`:

| Вопрос | Решение |
|---|---|
| проценты | `(процент / 100) * значение` — именно в этом порядке |
| равенство скаляров | `Object.is` |
| порядок правил | сверху вниз, `Добавить` накапливает, `Присвоить` затирает |
| свойство | постусловие на **всей** области входа, проверяется после всех правил |
| нарушено свойство | код `FTS_UTILITY_PROPERTY`, текст ровно как у ядра |
| пример не сошёлся | код `FTS_EXAMPLE_MISMATCH` |

Свойство проверяется и тогда, когда ни одно правило не сработало — именно
из-за этого процентный предел на отрицательной сумме падал.

## 4. Тотальность

Всё ядро обязано лежать в тотальном классе: `fts check` не имеет права
зависнуть. Циклы «пока есть символы» выражаются свёрткой по списку символов —
он структурно убывает. Где тотальность не доказывается, признак `тотальная`
не ставится, а место записывается в этот файл как долг с объяснением.

## 5. Критерий готовности — дифференциальная сверка

Ядро считается верным не тогда, когда проходят его собственные тесты, а когда
на **всех** `.fts` репозитория старое ядро на TS и новое на flang дают
побайтово совпадающий JSON — включая коды и тексты диагностик. Приём уже
отработан в `flang/src/compat.mjs`: 19 593 входа, ноль расхождений.

## Долги

Раздел пополняется по мере написания слоёв. Долг — это либо место, где не
поставлен признак `тотальная`, либо расхождение с ядром на TS, о котором знают
и которое пока оставлено.

### Лексер (`flang/core/lexer.flang`)

Тотальность: долгов нет. Все функции файла помечены `тотальная` и доказаны
`totality.mjs`. Обход строки по символам заменён на «разделить» плюс свёртка
или рекурсия по полученному списку, а стек отступов (список чисел) снял
единственное место, где напрашивалась бы рекурсия по числу: закрытие
нескольких уровней сразу — это рекурсия по хвосту стека.

Расхождения с ядром на TS, оставленные сознательно:

1. **Нормализация NFC не выполняется.** Ядро зовёт `String.prototype.normalize`
   на каждом имени (`natural-parser.ts`, `readName`), а в flang такой встроенной
   формы нет — её нельзя выразить ни через «разделить», ни через «подстрока».
   Пока все модели репозитория записаны в NFC, расхождение ненаблюдаемо; до
   дифференциальной сверки (раздел 5) в `builtins.mjs` нужна встроенная форма
   «нормализовать».

2. **Блочные комментарии `/* … */` лексер не знает.** Контракт раздела 1 их не
   упоминает, а ядро вырезает их в `sourceLines` до разбиения на строки, то
   есть это забота слоя выше. Если решение изменится, вырезание придётся
   выразить свёрткой по разбиению — приём тот же, что и для `//`.

3. **Экспоненциальная запись числа (`1e3`) считается именем.** Раздел 1
   ограничивает число целым или дробным с необязательным минусом, и лексер
   следует ровно этому; регулярное выражение ядра шире
   (`(?:[eE][+-]?\d+)?`). Ни в одной модели репозитория экспонента не
   встречается. Расширять придётся вместе с разделом 1, а не вместо него.

4. **«Внутри кавычек» определяется чётностью, а не автоматом.** Ядро в
   `stripLineComment` держит состояние посимвольно; здесь незакрытая ёлочка —
   это «`«` больше, чем `»`», а незакрытая кавычка — нечётное их число.
   Совпадает всюду, где кавычки не вложены друг в друга, а вложенных кавычек
   поверхность FTS не допускает. Посимвольный автомат стоил бы тотальности.

5. **Диагностика знает номер строки, но не колонку.** Формат ядра —
   `{ code, message, severity, span }`; лексер заполняет только номер строки,
   потому что колонку без обхода символов не получить. Для `FTS_INDENT` этого
   довольно: рваным бывает отступ, а не позиция в нём.

### Печать JSON (`flang/core/json.flang`)

Тотальность: долгов нет. Все 31 функция файла помечены `тотальная` и доказаны
`totality.mjs`. Экранирование строки не обходит её по символам (такое убывание
анализ не признаёт), а сворачивает по заранее известной таблице из 34 замен,
каждая из которых выражена через «разделить» и «соединить»; рекурсия по
произвольному значению и по вложенному утверждению убывает по полю варианта и
элементу коллекции, то есть доказывается обычным правилом.

Дифференциальная сверка (раздел 5) на всех `.fts` репозитория и внешнего
каталога моделей: 56 моделей, ноль расхождений с `JSON.stringify(compile(…))`.
Проверка — `flang/test/core-json.test.mjs`.

Расхождения и отступления, оставленные сознательно:

1. **Одинокий суррогат не экранируется.** `JSON.stringify` начиная с ES2019
   печатает непарный суррогат как `\ud800`, а «Экранировать» оставляет его как
   есть. Отличить суррогат от обычного символа нечем: в языке нет формы «код
   символа», а таблицу из 2048 замен вместо неё писать нельзя. Долг закрывается
   не здесь, а в `builtins.mjs` — встроенной формой «код символа»; тест
   `известный долг: одинокий суррогат не экранируется` закреплён именно затем,
   чтобы закрытие долга не прошло молча. Ни одна модель репозитория непарного
   суррогата не содержит.

2. **Запись числа делегирована встроенной «к строке».** `JSON.stringify`
   печатает число по правилу ECMAScript `Number::toString` (кратчайшая запись,
   дающая то же значение при обратном чтении), и `builtins.mjs` определяет
   «к строке» от числа ровно как `String(значение)`. Выразить это правило на
   самом flang нельзя: оно требует работы с битами мантиссы, а язык таких форм
   не даёт. Поэтому «Печать числа» отвечает только за нефинитные значения
   (`NaN` и бесконечности едут как `null`), а всё остальное — обязательство
   слоя: печать в C/Rust/Java обязана реализовать «к строке» от числа как
   Number::toString, иначе побайтовое совпадение сломается на первой же дроби.

3. **Скаляр операнда — сумма типов, а не строка.** Раздел 2 описывает
   `вариант Значение содержит значение: строка` («скаляр в текстовом виде»).
   Для печати этого недостаточно: `{"kind":"value","value":5}`,
   `{"kind":"value","value":"5"}` и `{"kind":"value","value":true}` —
   три разные строки JSON, а текстовый вид у них один. Поэтому в `json.flang`
   стоит `«Скаляр»` (строка | число | признак | ничто), и то же решение
   понадобится парсеру: разбор обязан сохранять, каким был скаляр в исходнике.

4. **Типы документа шире раздела 2.** Раздел 2 описывает только утилиты, а
   печатать нужно весь `FtsDocument` — `category`, `structures`, `functors`,
   `proposition`, `ts_compat`. Эти типы восстановлены по `src/model.ts` и по
   порядку вставки ключей в `src/parser.ts` и `src/natural-parser.ts`. Если
   парсер на flang объявит их иначе, типы придётся сводить — общий контракт
   должен остаться один.

5. **Словарь представлен списком пар.** `ts_compat`, `selector` утверждения и
   вход примера — словари с ключами от автора модели, а словаря в flang нет.
   Список пар хранит порядок (в JS он тоже определяется порядком вставки,
   поэтому печать совпадает), но допускает то, чего объект JS допустить не
   может, — два одинаковых ключа. Проверки на это нет: значения приходят из
   объекта JS, где повтор невозможен по построению.

### Вычислитель (`flang/core/evaluate.flang`)

Тотальность: долгов нет. Все 20 функций файла помечены `тотальная` и доказаны
`totality.mjs`. Рекурсии в файле нет вовсе: правила, свойства, условия и примеры
— это списки, и обход каждого выражен свёрткой. Короткое замыкание `Array.every`
(условия правила) и «первая диагностика прекращает счёт» (правила и свойства)
выражены состоянием свёртки, а не выходом из цикла: сработавший отказ
протаскивается дальше нетронутым, и тела остальных шагов не вычисляются.

Дифференциальная сверка (раздел 5) на всех `.fts` репозитория: 20 документов,
24 утилиты, 11 180 входов, ноль расхождений — совпадают и значения (по
`Object.is`, до последнего бита), и коды диагностик. Проверка —
`flang/test/core-evaluate.test.mjs`.

Расхождения и отступления, оставленные сознательно:

1. **Скаляр — сумма типов, а не строка.** То же отступление и по той же
   причине, что долг 3 печати JSON: текстовый вид не различает `5`, `"5"` и
   `да`, а `Object.is` их различает, и на этом различии стоит вся семантика
   равенства. Поэтому `«Значение операнда»` несёт `«Скаляр»`, а объявления
   типов раздела 2 в `evaluate.flang` и `json.flang` совпадают дословно —
   вычислитель и печать обязаны читать одно значение. Первая версия файла шла
   за буквой раздела 2 и разбирала текст сама (`parseScalar` ядра, включая
   регулярное выражение числа, выраженное вычёркиванием цифр свёрткой по
   десяти литералам); от этого пришлось отказаться, чтобы не заводить второй
   разбор числа рядом с `Похоже на число` лексера. Раздел 2 стоит поправить.

2. **`executeUtility` не реализована — только `evaluateUtility`.** Раздел 3
   описывает семантику вычисления, и она воспроизведена полностью. Проверки
   входа уровня документа (`FTS_UNKNOWN_UTILITY`, отсутствие объявленного поля
   структуры, `FTS_UTILITY_INPUT_TYPE`, `FTS_UTILITY_INPUT_FIELD`) требуют
   типа структуры и списка утилит, а «Утилита» раздела 2 знает только имя
   своего входа (`принимает: строка`). Эти коды остаются за слоем, который
   увидит «Документ» целиком; `FTS_UTILITY_INPUT` для поля, которого нет в
   переданных привязках, здесь есть — его даёт `resolveField`.

3. **Сводка `testUtilities` не реализована.** `FTS_NO_UTILITIES` и
   `FTS_NO_UTILITY_EXAMPLES` — диагностики документа, а не утилиты, и по той же
   причине им здесь не на что смотреть. Прогон примеров одной утилиты есть:
   «Проверить примеры» возвращает список «Итог примера» — тот же набор полей,
   что у `UtilityExampleResult` ядра.

4. **Текст `FTS_EXAMPLE_MISMATCH` выбран здесь.** Кода `FTS_EXAMPLE_MISMATCH` в
   ядре на TS нет вовсе: `testUtilities` возвращает `passed: false` без
   диагностики, а код введён разделом 3 этого контракта. Сообщение —
   `пример «X» утилиты «Y»: ожидалось A, получено B`, значения печатаются как
   «к строке» (признак — `да`/`нет`, ничто — `ничто`). Дословного образца, с
   которым это можно было бы сверить, не существует; если он появится,
   поменять придётся одну строку.

5. **Диагностика без `span`.** Формат ядра — `{ code, message, severity, span }`;
   «Итог» несёт только код и сообщение. Позиции у вычислителя нет и взяться ей
   неоткуда: он работает над «Документом», из которого разметка исходника уже
   ушла. Слой, который печатает диагностику, обязан добавить `span` правила или
   свойства сам.

6. **Стандартная библиотека не переиспользована — нечего переиспользовать.**
   После отказа от разбора текста (долг 1) в файле не осталось ни одного
   действия над строками, кроме склейки сообщений встроенной «соединить»:
   ни `Разбить по символу`, ни `Заменить` из `flang/stdlib/strings.flang` не
   нужны. Импорта нет и по второй причине: `использует … из "…"`
   (`flang/src/link.mjs`) появился одновременно с этим файлом, и завязывать
   слой ядра на связывание, которое ещё меняется, рано.

7. **Свойства не выражены постусловиями функции.** SPEC языка даёт
   `postconditions` с полями `code` и `message`, и `compat.mjs` переводит
   свойства FTS именно в них. Здесь так нельзя: утилита — это данные, а не
   функция, её свойства известны во время вычисления, а не во время разбора
   `evaluate.flang`. Постусловие пригодится генератору кода (утилита → функция),
   а не вычислителю.
