# 0040. Перепечатка не считает заново то, что не менялось, и раскладывает счёт по ядрам

Замер 24 августа 2026: перепечатка прошла за **5 ч 30 мин, пик 258.9 ГБ, код 0**.
Считала при этом **всё дерево целиком**, хотя со времени прошлой перепечатки
изменились единицы файлов из пятидесяти девяти.

Машина: 256 ядер. Перепечатка заняла **одно** — снято прямо:

```
процессорного времени   296 минут
прошло по часам         296 минут
```

## Что здесь параллелится, а что нет

Печать идёт шестью фазами. Разбирать надо каждую отдельно, а не «распараллелить
перепечатку»:

| фаза | параллелится | почему |
|---|---|---|
| разбор 59 файлов | **да, целиком** | файлы независимы |
| связывание замыкания | частично | таблицы по файлам — да, слияние — нет |
| проверка типов | да, по функциям | нужно общее окружение, но проверки независимы |
| завершаемость | да, по функциям | |
| **суд ядра: 6613 обязательств** | **да, целиком** | каждое сводится со СВОЕЙ функцией отдельно |
| печать в C | да, по функциям | каждая даёт свой кусок текста, склейка в заданном порядке |

**Сверка байт в байт при этом не теряется**, пока порядок склейки задан, а не
зависит от того, кто раньше закончил.

Доля ядра в цене — по замеру из шапки `scripts/raskrutka.sh`:

```
Связать исходники     23 726 585
Проверить типы         3 919 602
Проверить тотальность    222 863
Беды ядра             56 355 645   ← 67 % суммы
```

## Препятствие, которое надо назвать честно — и оно не то, что кажется

Первая редакция этой задачи говорила «потоков у языка нет». **Это неверно.**
`flang/src/emit/c/flang_conc.c` — настоящий планировщик на потоках ОС:
`pthread_create` на артель, число работников берётся у машины
(`sysconf(_SC_NPROCESSORS_ONLN)`), склады с подворовыванием, и настраивали его
по замерам — «шестнадцать потоков давали 1,15× при пятнадцати занятых ядрах»
записано прямо в коде.

**Но воспользоваться им сегодня нельзя, и это проверено прогоном 24 августа 2026.**

Опыт: восемь процессов, каждому тяжёлый счёт. Проверка прошла. Печать в C:

```
$ ls c/
Makefile  flang_cli.c  flang_runtime.c  flang_runtime.h  veer.c  veer.h
$ grep -c flang_conc c/veer.c c/Makefile
0   0
```

То же самое на ШТАТНОМ примере дерева `flang/conc/examples/counter.flang`: движка
в выводе нет. И компилятор сам называет причину:

> НАПЕЧАТАНО, НО ПРОВЕРЕНО НЕ ВСЁ: в программе объявлено то, чего бинарник не
> судит вовсе — processes, supervisors, runs… Судья этих объявлений написан на
> flang — `setoid.flang` и `setoid-oracle.flang`, 1092 функции, — но в замыкание
> двоичного не вшит, и сегодня его не запускает ничто.

`flang_conc.c` нет и в семени: там четыре файла, и его среди них нет. Даже
закоммиченный `flang/conc/bin/node.c` — «полный узел: таблица процессов,
планировщик и связь» — содержит `flang_conc` ноль раз: он несёт свой планировщик
внутри, а не подключает движок.

**Вывод: раскладывать суд ядра по процессам flang сегодня НЕЛЬЗЯ** — цепочка
«объявил процесс → получил многоядерную программу» разорвана в двоичном.
Разрыв разобран отдельной задачей 0041.

Значит из трёх ходов ниже остаются первый и третий, а второй ждёт 0041.

## Основание уже лежит в дереве

`scripts/otpechatok-semeni` **уже хранит SHA-256 каждого файла замыкания**:

```
предел-шагов 1000000000
вход flang/self/bootstrap/compiler.flang
52e9d5b3…  flang/core/evaluate.flang
58dace2c…  flang/core/json.flang
0c162989…  flang/self/bootstrap/compiler.flang
…
```

Это готовый ключ кэша. Сейчас он используется только для `--bystro` — сверить за
секунды, те ли входы у печати. Пропускать работу по нему никто не пробовал.

## Три хода, от самого дешёвого

### 1. Кэш по отпечатку — наибольшая отдача на повторной печати

Файл и всё, от чего он зависит, не менялись → взять прошлый результат. Ключ —
хеш содержимого плюс хеши зависимостей, то есть ровно то, что уже снимается.

**Мерить надо на настоящем случае:** внести правку в один файл и сравнить время
перепечатки с полной. Если из 59 файлов меняются два, отдача видна сразу.

### 2. Веер по обязательствам — ЖДЁТ ЗАДАЧУ 0041

6613 независимых сведений на 256 ядрах. Пока конкурентность недоступна из
двоичного (см. выше), это делается только процессами ОС из оболочки: каждый
считает свою долю, вердикты — в общий каталог, сборка после. Своим планировщиком
это станет тогда, когда закроется 0041.

### 3. Печать по кускам

Каждая функция печатает свой текст, склейка в порядке, заданном списком, а не
временем возврата. Проверка та же: результат обязан совпасть байт в байт с
однопроцессной печатью.

## Чего делать НЕ надо

**Не вводить потоки в рантайм ради этой задачи.** Процессы и общий каталог
достаточны, а потоки тянут за собой гонки в арене, которая на них не рассчитана.

**Не жертвовать сверкой байт в байт.** Она единственное, чем держится
раскрутка: flang₁ печатает flang₂, и они обязаны совпасть.

## Как понять, что сделано

```sh
sh scripts/raskrutka.sh          # после правки ОДНОГО файла
```

идёт заметно меньше полной печати, а результат совпадает с ней **байт в байт**.
Оба числа сняты и названы: полная печать и печать после правки.

# Разбор 26 августа 2026: кэш по отпечатку не окупается, и это снято прогонами

Ветка `u/reprint-reuses-unchanged`. Прогоны — через ворота (`PAMYAT=45G`),
двоичным `/srv/flang-rabota/w-predely/bootstrap/flang`; по правилу `AGENTS.md`
каждое снятое им число читается как **снято 26 августа двоичным от 23 августа
16:00 UTC (дерево не установлено, не новее `883fe9a9`)**. Время и память — GNU
`time -v`, не счётчик витков: задача 0060 показала, что счётчик витков не видит
фильтров и мерой работы не является.

**Перепечатка не запускалась.** Всё это время на машине шла чужая
(`emit flang/self/bootstrap/compiler.flang` в списке процессов), а вторая
одновременная кладёт машину на шесть часов.

**Вторая половина задачи — раскладка по ядрам — закрыта отрицательно задачей
0033 и здесь не повторяется.** Механизм назван там поимённо:
`flang/self/emit-c.flang` включает конкурентность по условию
`«конкурентно» = (processes > 0)`, объявлений `процесс` в `flang/self/**` ноль,
отсюда в `bootstrap/` нет `flang_conc.c`, и перепечатка напечатает то же самое.

## 1. Посылка задачи опровергнута замером: меняются не единицы файлов, а все

В шапке стоит «со времени прошлой перепечатки изменились единицы файлов из
пятидесяти девяти». Снято `sha256` по тем же правилам, по каким его снимает
`stamp_now` в `scripts/raskrutka.sh`, и сверено с `scripts/otpechatok-semeni`:

```
входов печати (замыкание 40 файлов + 4 файла рантайма)      44
изменены после последней перепечатки                        41
вошли новые (flang/stdlib/hashmap.flang, numbers.flang)      2
НЕ МЕНЯЛСЯ ОДИН: flang/self/bootstrap/corpus.flang (763 строки)
```

**43 входа из 44.** Отпечаток снят коммитом `58b037c2` 23 августа 00:20; после
него в замыкание печати въехало **503 коммита**.

И этого мало: у отпечатка разошлась ещё и **мета**. В нём записано
`предел-шагов 1000000000`, а в `scripts/raskrutka.sh` сегодня
`MAX_STEPS=4000000000`. Предел уезжает в напечатанный байт
(`#define FL_MAX_STEPS`), то есть даже при полном совпадении всех сорока четырёх
файлов ни одна прошлая запись кэша не была бы годной.

Доля входов печати, НЕ тронутых за окно (то есть потолок попадания кэша):

| окно | тронуто входов | кэш попал бы в |
|---|---:|---:|
| 4 часа | 5 из 44 | 88,6 % |
| 12 часов | 25 из 44 | 43,2 % |
| 24 часа | 30 из 44 | 31,8 % |
| 48 часов | 41 из 44 | 6,8 % |
| **с последней перепечатки** | **43 из 44** | **2,3 %** |

По заходам перепечатки:

| промежуток | тронуто входов | кэш попал бы в |
|---|---:|---:|
| между удачной 24-го и заходом 25-го | 38 из 44 | 13,6 % |
| **пока шёл заход 25–26-го (845 минут)** | **22 из 44** | **50,0 %** |
| после смерти 26-го и до сейчас | 4 из 44 | 90,9 % |

Средняя строка — главная. **Пока перепечатка считает, половина её входов
успевает устареть.** Дерево движется быстрее, чем идёт печать: за трое суток

Отдельная правка одного файла — случай из шапки задачи — в дереве бывает, но
перепечатку по ней не гоняют: её гоняют раз в несколько суток, и к этому часу
меняется всё.

## 3. Кэшировать нечего: единицы «файл» у печати нет ни на входе, ни на выходе

Перепечатка — **один вызов** (`scripts/raskrutka.sh`):

```
"$BINARY" emit "$INPUT" --target c --out "$TMP" --cli --repl --runtime … 
```

Печать в C даёт **один** файл на всю программу, а не файл на исходник. Снято:

```
семя: bootstrap/compiler_flang.c   21 374 208 байт   на все 40 исходников
      bootstrap/compiler_flang.h    4 295 116 байт
проба: emit flang/self/lexer.flang → lekser_flang.c 397 100 байт,
       и функции ОБОИХ файлов замыкания (lexer.flang и stdlib/strings.flang)
       лежат в нём вперемешку
```

Значит «взять прошлый результат файла» нечего взять: результата файла не
существует. Пришлось бы резать по функциям внутри одного файла на 21 МБ,
который потом сверяется побайтово.

## 4. Почему ключ «хеш файла плюс хеши зависимостей» НЕВЕРЕН, а не просто редко попадает

Это главное, и это не рассуждение о вкусах: **направление зависимости у печати
обратное тому, которое такой ключ умеет выразить.**

Напечатанные байты функции зависят от вердикта ядра о ней:
`«Суд ядра о программе»` возвращает `«снятые»`, и
`«Программа без снятых постусловий»` **вычёркивает доказанные сторожа из
напечатанного кода** (`flang/self/bootstrap/compiler.flang`). В семени это
видно числом: на 21 МБ напечатанного осталось **77 строк `fl_post` и одна
`fl_pre`** — остальные сняты решением ядра.

А вердикт считается о ВСЕЙ программе разом, и вот места, где он выходит за
границы файла и его зависимостей:

* **`«Снять предусловия» от «программа»`** (`proofterm.flang:3459`) собирает
  места вызова по всей программе и отдаёт список `«неоплаченные»` — имена
  функций, чьё `требует` где-то не оплачено. Седьмой ход отказывается
  пользоваться постусловием такой функции (`proofterm.flang:2408`). **Место
  вызова функции F лежит в файлах, которые зависят ОТ F, а не в тех, от которых
  зависит F.** Ключ «F и зависимости F» их не видит вовсе.
* **`«Закрыть без теорем»`** — неподвижная точка: каждая попытка читает уже
  накопленное `«закрытые»` по всем обязательствам программы.
* **`«Пометить условные»` и `«Твёрдые ключи»`** — послепроход по ВСЕМ вердиктам
  сразу; вердикт переименовывается из-за посылки, доказанной в другом файле.
* **`«Свести теоремы»`** (`obligations.flang`) — свёртка: вторая теорема того же
  имени видит первую закрытой и отвергается.
* **`«По свойству»`** ищет постусловие вызванной функции ПО ИМЕНИ во всей
  программе (`«Найти постусловие» от «программа» и «имя»`).

Четыре из этих пяти мест уже названы задачей 0033 в разделе «НЕ НЕЗАВИСИМО» —
там они мешали вееру по ядрам, здесь они ломают ключ кэша.

**Отсюда механизм тихой поломки.** Файл `A.flang` не менялся, ни один файл, от
которого он зависит, не менялся — ключ совпал, кэш отдал вчерашние байты. А
правка в `B.flang`, который ввозит `A`, добавила неоплаченный вызов, и сторож у
функции из `A` обязан был вернуться в код. Кэш этого не увидит: `B` не входит в
его ключ ни одним битом.

**Ключ, который был бы верен, — хеш всей программы целиком. Он уже есть, и он
уже отвечает.** Это `sh scripts/raskrutka.sh --bystro`, он стоит секунды, и
сегодня его ответ — «43 из 44 разошлись». То есть верный кэш попадает в 2,3 %
входов, а неверный попадает часто и молчит.

## 5. Ловля показана прогоном: ключ совпал, а ответ изменился

Опыт — три файла в `/srv/tmp/u-reprint-cache2/proba`, двоичный тот же, один слот
ворот. `nizh.flang` (модуль «Низ пробы») **не ввозит ничего**, значит его ключ по
предложению задачи — хеш его самого и больше ничего.

```
nizh.flang            «Вычесть» с требует и обеспечивает и примером;
                      «Разность через вычитание» — зовёт «Вычесть»
verh-payer.flang      ввозит «Низ пробы», зовёт «Вычесть», предусловие ОПЛАЧЕНО
verh-debtor.flang     ввозит «Низ пробы», зовёт «Вычесть», НЕ оплачено
```

`nizh.flang` в обоих прогонах побайтово один и тот же — `md5`
`a92597019297e59b64d76b5badf490f6`. Прогон:

```
check --proof verh-payer.flang    код 0   утверждений 2: сетка 2
emit        verh-payer.flang      код 0   напечатан verh_platyaschiy.c, 9453 байта
check --proof verh-debtor.flang   код 1   FLANG_PRECONDITION_CALL, строка 9
emit        verh-debtor.flang     код 1   каталог печати ПУСТ
```

Функции `nizh.flang` при этом лежат внутри `verh_platyaschiy.c` — файла,
названного по ВХОДУ печати, а не по исходнику:

```
13: * Функция flang «Вычесть».
26:  FL_TRY(fl_post(ctx, …, "разность не больше уменьшаемого", "Вычесть", …));
35: * Функция flang «Разность через вычитание».
84:  FL_TRY(fl_pre(ctx, …, "вычитаемое не больше уменьшаемого", "Вычесть", …));
```

**Что здесь показано.** Ключ `nizh.flang` совпал знак в знак, зависимостей у него
нет ни одной — а правильный ответ о нём сменился с «вот его напечатанные байты»
на «эту программу печатать нельзя». Причина лежит в файле, которого нет и не
может быть в ключе: `verh-debtor.flang` ввозит `nizh.flang`, а не наоборот.

Кэш, отдавший здесь вчерашние байты, выдал бы напечатанный C там, где печать
обязана отмениться.

**Одна хорошая новость, и её надо назвать честно:** конкретно неоплаченное
предусловие ловится ГРОМКО — `FLANG_PRECONDITION_CALL` и код 1, а не тихая
подмена байтов. Тихой эта беда становится ровно тогда, когда кэш начинает
отвечать вместо ядра: диагностику ядра о непересчитанном файле выдавать некому.

## 6. Кэш не чинит ни одну из пяти смертей перепечатки

Перепечатка за двое суток умерла пять раз (задачи 0003 и 0059), и вот от чего:

```
24 авг  FLANG_RECURSION_LIMIT «Найти описание», предел ШАГОВ 4·10⁹    180 мин
25 авг  FLANG_MEMORY на 95-й минуте, PAMYAT=150G при занятых 116,7 ГБ
25–26   FLANG_RECURSION_LIMIT «Описания программы», ГЛУБИНА 20 000    845 мин
26 авг  та же «Описания программы», глубина поднята до 80 000          9 часов
```

Ни одна из трёх стен — шаги, глубина, память — кэшем не отодвигается. Все три
стоят на РАЗМЕРЕ СВЯЗАННОЙ ПРОГРАММЫ, а связывать приходится всё: глубина спуска
`«Описания программы»` — два кадра на КАЖДУЮ функцию замыкания, сколько бы файлов
ни было взято из кэша. Кэш убирает счёт по функции, но не саму функцию из
программы.

## 7. Кэш нельзя построить, не заплатив сперва полную перепечатку

Перепечатка — один вызов `emit`, и «пропустить непеременившееся» жить может
только в трёх местах:

* **`flang/self/**`** — тогда правка попадёт в двоичный **только перепечаткой**,
  то есть цену кэша платят один раз ПОЛНОСТЬЮ и вслепую, а первая отдача
  приходится на следующую перепечатку;
* **`flang/src/emit/c/*.c`** — то же самое: файл уезжает в вывод дословно и в
  семя попадает перепечаткой;
* **`scripts/raskrutka.sh`** — резать нечего: `emit` печатает замыкание одним
  файлом, ключа «напечатай только этот исходник» у него нет.

То есть чтобы получить кэш, надо сперва провести ту самую перепечатку, которая
пять раз подряд не дошла до конца.

## 8. Сравнение с тремя соседними правками — числами

Что уже снято (числа чужие, снятые их авторами прогонами):

| правка | работа | было | стало |
|---|---|---|---|
| **0046** сравнение записей | `emit lexer.flang --target c` | 462,41 с | **14,35 с** (в 32,2 раза) |
| **0033** обязательства | 6139 обязательств, `«Слить»` | не досчитывает под 45 ГиБ, `FLANG_MEMORY` | **4,10 с, 972 МиБ, код 0** |
| **0052** связывание | слияние, n=800 | 13 047 724 КиБ | **5 770 996 КиБ** (−55,8 %), рост памяти из ×2,31 в ×1,96 на удвоении |

Мой собственный замер закрывает круг. Та же работа
`emit flang/self/lexer.flang --target c`, ворота `PAMYAT=45G`, GNU `time -v`:

```
двоичный w-predely (23 августа)   ЦП 7,00 с (6,09 + 0,91), пик 549 МиБ, код 0
                                  напечатано 6 файлов, 789 043 байта, снято 60 проверок
```

Дерево о ТОЙ ЖЕ команде на сегодняшнем печатнике: **462,41 с** (0046) —
в 66 раз дороже. После 0046 та же работа стоит **14,35 с**, то есть **2,05
от уровня 23 августа**. Иначе говоря: за трое суток проверка подорожала в
66 раз, и одна правка в девять строк почти всё это вернула.

**Потолок кэша, посчитанный из моих же замеров и при самых щедрых допущениях**
(кэш верен, пропуск бесплатен, вся работа делится по файлам):

```
на перепечатке, которая стоит СЕЙЧАС    43 входа из 44 изменены →  1,02×
на самом удачном замеренном окне (12 ч) 25 входов из 44         →  1,76×
```

И это потолок, а не ожидание: связывание и послепроходы ядра
(`«Закрыть без теорем»`, `«Твёрдые ключи»`) считаются о всей программе и в долю
«пропущенных файлов» не входят вовсе.

**1,02× против 32,2×.** Отвечать на задачу кэшем сегодня значит взять худший из
доступных ходов и заплатить за него полной перепечаткой.
