# 0052. Связывание перестало быть квадратом от размера замыкания

Замер записан в шапке `scripts/raskrutka.sh` и снят отдельно:

```
Связать исходники     23 726 585 витков   59 % предела
показатель роста      2,04                то есть КВАДРАТ
```

Вывод оттуда же, дословно: «Убрать ядро из проверки перед печатью НЕ СПАСЛО БЫ.
Связывание — шаг, к ядру отношения не имеющий, — уже съедает 59 % предела…
следующий рост той же величины умножает на 2,3».

## Почему квадрат

Та же причина, что у поиска функции по имени (задача 0020): **перебор списка по
имени, повторённый для каждого имени**. Образец из печатника:

```flang
тотальная функция «Найти функцию»
  «Первая из функций» от (отфильтровать «функции» где «функция» → («функция».«имя») равен «имя»)
```

`отфильтровать` проходит ВЕСЬ список и не останавливается на найденном. Соседняя
`«Есть функция с именем»` строит новый список из всех имён на каждый вызов.

**Таких функций в компиляторе 217**, и «Найти функцию» есть отдельно в каждом
печатнике: C, JS, Java, C#, Elixir, Rust (ввозит из C), плюс `factcheck`.

## Что уже известно про починку

Задача 0020 сделана: словарь в вычислителе дал **в 59 раз меньше витков в
поиске** (874 млн → 14,7 млн на `proof-kernel.flang`).

**И там же названа ловушка:** словарь становится быстрым только после того, как
доказаны его обещания. Первая попытка провалилась именно на этом — недоказанные
обещания едут в код проверками, и вставка обходила весь словарь.
`hashmap.flang` теперь доказан (задача 0035), значит ловушка снята.

## Порядок

По одному месту, каждый раз с замером витков до и после и сверкой вывода **байт
в байт**. Оснастка со счётчиками готова: `/srv/flang-rabota/u-slovar-podklyuchenie`.

Показатель роста снят заново и назван числом. Витки связывания до и после.

# Замер 26 августа 2026: показатель 2,04 по виткам НЕ подтверждается

Ветка `u/linking-not-quadratic`. Всё ниже снято прогонами через ворота
(`PAMYAT=45G`), двоичным `/srv/flang-rabota/w-predely/bootstrap/flang`.

## Чем мерено, раз перепечатку запускать нельзя

Правка в `flang/self/link.flang` в собранном двоичном не появится без
перепечатки, поэтому сторона «до» снята НАСТОЯЩИМ двоичным на синтетике, а
стороны «до» и «после» сравниваются вычислителем на том же самом файле
`link.flang`, который правится.

**Витки шага названы самим двоичным.** `repl_call` печатает строку «ЗАПАС ШАГОВ
НА ИСХОДЕ: «Связать исходники» съел N витков из L», как только шаг съедает
больше половины предела, и счётчик витков у каждого шага СВОЙ
(`repl_ctx.steps = 0` перед вызовом). Значит достаточно удваивать
`--предел-шагов`, пока прогон не пройдёт: на первой же удаче строка называет
цену связывания и ТОЛЬКО связывания — ни типов, ни завершаемости, ни ядра в
этом числе нет.

Синтетика: входной файл из n тотальных функций и один ввозимый модуль. Ввоз
есть, значит работает и второй проход — тот, ради которого файл перечитывается.

## Почему счётчик витков не видит квадрата

Квадрат в коде ЕСТЬ, и он там, где названо в задаче: `«Есть в таблице»` зовёт
`«Найти в таблице»`, а та делает `отфильтровать «таблица» где …` — проход по
ВСЕМУ списку пар, и делается он на каждом объявлении (`«Слить функцию»`,
`flang/self/link.flang`), да ещё второй раз внутри `«Положить в таблицу»`.

Но **`отфильтровать` печатается в C циклом с встроенным телом, а не вызовом**:
`fl_tick` стоит только на входе в функцию (`fl_enter`) и на витке хвостового
цикла (`«Хвостовой цикл»`, `flang/self/emit-c.flang`). Проход по элементам
списка не тикает НИ РАЗУ. Поэтому счётчик витков считает вызовы, а не работу, и
квадратичный обход для него невидим.

**Зато он видим памяти, и вот чем.** `«Печать цикла дальше»` печатает перед
циклом строку

    FL_TRY(fl_list_alloc(ctx, <список>.as.list.count, &<массив>, error));

то есть КАЖДЫЙ `отфильтровать` заводит массив длиной во ВЕСЬ вход, сколько бы
элементов ни отобралось. У `«Есть в таблице»` отбирается ноль или один, а
заводится n. Арена не отдаёт этого до закрытия области, значит слияние n
объявлений заводит порядка n² ячеек: на 6000 функциях это 6000 × 2 × 6000
значений — гигабайты, которых никто не просил.

А чем тогда заняты 390 витков на функцию? Разбором: `«Связать исходники»`
разбирает файлы САМА (`отобразить «файлы» как «файл» → «Разобрать файл»`) и
файлы с ввозом разбирает второй раз (`«Переразобрать файл»`). Разбор линеен, и
именно он составляет почти всю ту цену, которую видит предел шагов.

**Следствие для перепечатки.** 23 726 585 витков связывания — это в основном
разбор 110 849 строк, и растёт он ЛИНЕЙНО. Рост дерева в полтора раза даст не
×2,3, а ×1,5: около 35 миллионов из 200 000 000, то есть 18 % предела вместо
59 % сегодняшних. По ШАГАМ связывание перепечатку не уронит.
