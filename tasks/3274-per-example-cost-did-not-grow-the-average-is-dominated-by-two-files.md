# 3274 — «в семнадцать раз» не подтвердилось

## Что утверждалось

Задача 6163 (поправка) вывела из двух чисел, что подорожал сам прогон
примера:

```
было   53 с / 1445 = 37 мс на пример
стало 3386 с / 5302 = 639 мс на пример    «в семнадцать раз»
```

и заключила: искать надо общее для всех, а не отдельный тяжёлый файл.

## Замер этого не подтверждает

**Опыт на одну переменную**: те же четыре малых файла, два двоичных —
семя `638a0853` (`flang 0.6.2`, до обеих сентябрьских перепечаток) и
нынешнее дерево (`flang 0.7.0`). Одна машина, подряд.

```
файл          СТАРОЕ семя      НОВОЕ семя
logic          15 мс/пример     17 мс/пример
numbers        50 мс            57 мс
dictionary     42 мс            44 мс
optional       37 мс            54 мс
```

Разница в пределах шума машины, которая в это время держала перепечатку.
**Прогон примера не подорожал ни в семнадцать раз, ни вдвое.**

## Настоящая причина — разброс между файлами, а не общий сдвиг

```
файл          мс всего   примеров   мс/пример
logic              314        20         15
optional          1005        27         37
dictionary        1154        27         42
numbers           1723        34         50
base64           22429        61        367
automaton        23542       104        226
crl             180037       ~59      ~3000
aes             362376      ~151      ~2400
```

**Разброс двухсоткратный.** Среднее 639 мс не описывает ни один файл: оно
получается делением суммы, в которой `aes` и `crl` дают больше половины
всего времени, на общее число примеров, из которых те же два файла дают
около четырёх процентов.

Это ровно та ошибка, от которой предостерегает сам критерий: среднее по
разнородному — не число, а его видимость. Форма распределения, названная
задачей 3841 («семь файлов дают почти всё время»), верна; вывод 6163 о
«семнадцати разах» из тех же данных — нет.

## Побочно: примеры ввезённых файлов гоняются заново

Отсюда и второе расхождение, которое 6163 оставила открытым: строк
`пример` в `flang/stdlib/*.flang` — **2713**, а прогон каталога называет
**5302**.

Проверено на одну переменную:

```
файл         своих примеров   ввозов   прогон насчитал
logic               20           0            20
optional            27           0            27
numbers             34           0            34
dictionary          27           0            27
hashmap             61           1            67    ← +6
```

У файла без ввозов счёт совпадает знак в знак; у `hashmap` с одним ввозом
прогон насчитывает на шесть больше — ровно примеры ввезённого. Значит
примеры ввезённого модуля прогоняются заново на каждом файле, который его
ввозит, и 5302 − 2713 = 2589 прогонов приходятся на повторы.

**Это не беда сама по себе** — проверять пример в новом окружении
осмысленно. Но при счёте цены это надо знать: «5302 примера» и «2713
примеров в дереве» — разные величины, и делить время на первую, а
сравнивать со второй нельзя.

## Чего замер НЕ говорит

* **Почему `aes` и `crl` дороги поштучно.** Названо в 3841 как догадка
  (поиск по таблице на 517 чисел через `элемент` плюс шесть постусловий на
  вызов) и здесь не проверялось: профилировщика в дереве нет.
* **Не выросла ли цена этих двух файлов со временем.** Старым семенем они
  не мерены — прогон каждого около шести минут, а замер на одну переменную
  требует обоих семян. Работа названа, не сделана.
* Числа сняты на машине под перепечаткой; сравнение между файлами и между
  семенами честное (одна машина, подряд), абсолютные величины завышены.

## Как это чинить

Не «искать общее замедление» — его нет. Либо разбирать `aes` и `crl`
поштучно, либо признать их цену и поставить шагу CI срок, чтобы рост был
виден. Прибор `примеров-в` (задача 3841) нужен по-прежнему, но считать он
должен то же, что и прогон, иначе приметы разойдутся с ним, как разошлись
2713 и 5302.
