# 3841 — сорок четыре минуты из пятидесяти, и виноват не тот, на кого думали

## Как найдено

Владелец спросил прямо: «какого хрена там идет сборка двоичного 49m».
Работник HH1 (задача 6163) разобрал прогон `33895656055` по шагам и
опроверг постановку — **сборка ни при чём**:

```
Собрать точку раскрутки       4 мин 18 с
Проверки на flang (180 штук)      35 с
Примеры stdlib и ядра        44 мин 07 с   ← шапка того же файла обещает 53 с
Опись дерева по языкам            22 с
```

Сорок четыре минуты из пятидесяти даёт один шаг — `binary.yml:318`,
`./bootstrap/flang test flang/stdlib/` и `flang/core/`.

## Обещание датировано, и это решает вопрос

`binary.yml` в шапке (строки 15-16, 37):

```
flang/stdlib   42 файла, 1216 примеров, прошли все    40 с
СНЯТО 2026-08-31 файлов flang/stdlib/*.flang = 42
примеры stdlib и ядра, 1445 штук                      53 с
```

Замер снят **31 августа**. Значит искать надо то, что менялось после.

## Исходники ни при чём — проверено историей

**В `flang/stdlib/` с 31 августа ровно ОДИН коммит**, и тот про
комментарии:

```
49ae5fbb  2026-09-02  чистка(stdlib): журнал вынесен из комментариев, кода не тронуто
```

Первый подозреваемый — `aes.flang`, самый медленный по обходу. Его правки
все **старше** замера:

```
412d0e9a  2026-08-30  proof(aes): тег GCM обеих длин ключа доказан
900f98ef  2026-08-30  proof(aes): двенадцать обещаний о длине доказаны
326dce24  2026-08-26  test(aes): все 209 доказанных обещаний снимают проверку при работе
91ab7281  2026-08-24  proof(aes): AES-128 и AES-256 доказаны 209 обещаниями из 337
```

То есть замер в 40 секунд ЭТОТ ЖЕ ФАЙЛ в этом же виде уже включал.

## Семя менялось дважды — и ОКАЗАЛОСЬ НИ ПРИ ЧЁМ

```
f692bab6  2026-09-03  Семя bootstrap/ обновлено перепечаткой с 30 августа на 3 сентября
659d4779  2026-09-04  chore(bootstrap): семя обновлено перепечаткой с 3 сентября 04:06
```

Гипотеза была: замедлило семя. **Опровергнута замером A/B** — собрано
семя, каким оно было ДО обеих перепечаток (`638a0853`, `flang 0.6.2`), и
те же файлы прогнаны обоими двоичными на одной машине, в одну минуту:

```
файл             СТАРОЕ семя (0.6.2)   НОВОЕ семя (dev)
base64.flang            20 с                 23 с
aes.flang           медленный, >300 с    300 с, код 124
```

Обычный файл идёт одинаково. `aes.flang` медленный на ОБОИХ. Значит
регресса в двоичном нет, и чинить `flang/self/**` не за что.

## Что это значит на самом деле

`aes.flang` — выброс, и он был выбросом всегда. А обещание «42 файла, 1216
примеров, 40 с» **не воспроизводится ни на одном семени**: рядовой файл
берёт двадцать с лишним секунд, и сорока на все сорок два не хватит при
любом двоичном.

То есть беда не «стало медленно», а **«число 40 с в шапке не отвечало
дереву»** — порода, которую в этом дереве ловят весь день: примета,
которую никто не переснимал.

## Замеры

Обход по одному файлу, срок каждому 300 с. **Машина под чужой нагрузкой**
(`hugo` чужого пользователя брал 32 ядра, load average 80), поэтому
абсолютные числа завышены; сравнение файлов между собой честное — все в
одних условиях.

```
секунд  код  файл                    секунд  код  файл
   300  124  json.flang    ← срок        8    0  der.flang
   300  124  datetime.flang             6    0  hashmap.flang
   300  124  aes.flang     ← 373 при 900 5    0  higher-order.flang
   214    0  postgres.flang             4    0  lists.flang
   193    0  kdf.flang                  2    0  optional.flang
   171    0  crl.flang                  2    0  numbers.flang
   102    0  hmac.flang                 2    0  math-classics.flang
    40    0  http.flang                 1    0  numtree.flang
    25    0  base64.flang               1    0  math-classics-lists.flang
    25    0  automaton.flang            1    0  dictionary.flang
    11    0  ecdsa.flang                0    0  logic.flang
```

**Двадцать два файла из 42 берут 1713 секунд = 28,6 минуты**, и три из них
оборваны сроком (настоящие числа больше). Оставшиеся двадцать — в том
числе `sqlite`, `tls`, `tls-handshake`, `trust-store`, `x509`, — по чужому
замеру (задача 3099) тоже медленные: 86–393 секунды. Сорок четыре минуты
CI этими числами объясняются полностью.

**Форма беды видна окончательно: семь файлов дают почти всё время, а
пятнадцать идут за секунды.** Медленные — все криптографические либо
разбирающие: `aes`, `json`, `datetime`, `postgres`, `kdf`, `crl`, `hmac`.

Двенадцать файлов из 42 берут вместе **994 секунды (16,6 минуты)**, и это
при том, что два из них оборваны сроком. Известно ещё про `json.flang`:
по A/B он берёт 269 секунд. Итог по всей папке в 44 минуты этими числами
объясняется полностью — считать остальные тридцать не нужно, чтобы понять
форму.

`flang/core/` — **все быстрые**, по одной-две секунды:

```
     2    0  flang/core/evaluate.flang
     2    0  flang/core/json.flang
     1    0  flang/core/lexer.flang
    10    0  flang/core/parser.flang
```

**Форма беды: несколько выбросов, а не общее замедление.** Рядовой файл
идёт секунды, а два не укладываются и в пять минут.

A/B двух семян на одном дереве, в одну минуту:

```
файл             СТАРОЕ семя (0.6.2)   НОВОЕ семя (dev)   срок
base64.flang            20 с                 23 с          100/200
aes.flang              393 с, код 0         373 с, код 0    900/900
json.flang             269 с, код 0          —              900
```

**Оба семени досчитали `aes.flang`, и новое даже на 5 % БЫСТРЕЕ: 373
против 393 секунд.** Прежнее «300 с, код 124» было коротким сроком
замера, а не замедлением — при равном сроке оба доходят до конца.

**Гипотеза «замедлило семя» опровергнута начисто.** Рядовой файл идёт
одинаково (20 против 23 с), выброс идёт одинаково (393 против 373 с).
Регресса в двоичном нет ни в какую сторону.

`json.flang` старым семенем — 269 секунд, тоже досчитал. То есть четыре с
половиной минуты этот файл брал и до перепечаток.

## И ГЛАВНОЕ: примеров стало вдвое больше, а число в шапке от 24 августа

```
                    в шапке   в дереве сегодня
файлов stdlib          42            42        ← ПРИМЕТА ЕСТЬ, сторож её проверяет
примеров stdlib      1216          2713        ← приметы нет
примеров всего       1445          2897        ← приметы нет
время шага            53 с      44 мин 07 с    ← приметы нет
```

Числа «1216 примеров» и «1445» написаны коммитом `27156b21` от **24
августа**. Примета `СНЯТО 2026-08-31 … = 42` стоит только у числа ФАЙЛОВ —
его сторож чисел прозы и переснимает. Числа примеров и времени примет не
имеют, и потому не проверялись никем **двенадцать дней**.

За те же двенадцать дней примеров стало вдвое больше. Одно это удваивает
работу шага, и удвоение было законным: примеры дописывали, доказывая
обещания (`326dce24`, `91ab7281`, `900f98ef`, `412d0e9a` — всё про AES).

**То есть шаг не «сломался». Он вырос, а числа рядом остались от
24 августа, потому что сторожить их было нечем.**

## Врезка: завести приметы числам, у которых их нет

Это и есть настоящая починка, а не срок шагу. Три числа в шапке
`binary.yml` надо снабдить приметами, как уже сделано у числа файлов —
тогда следующий рост увидят в тот же день, а не через двенадцать:

```
#   flang/stdlib   42 файла, 2713 примеров, прошли все
#   СНЯТО 2026-09-05 файлов flang/stdlib/*.flang = 42
#   СНЯТО 2026-09-05 примеров-в flang/stdlib/*.flang = 2713
#   примеры stdlib и ядра, 2897 штук
#   СНЯТО 2026-09-05 примеров-в flang/stdlib/*.flang,flang/core/*.flang = 2897
```

**Сторож считать примеры НЕ УМЕЕТ — проверено.** У
`scripts/prose-numbers-guard.sh` ровно два прибора: `файлов` и `строк-в`.
Прибора `примеров-в` нет, и завести его — часть этой работы, без которой
приметы выше не поставить.

Это, кстати, объясняет и почему число файлов переснимали, а числа примеров
и времени нет: **сторожили ровно то, что он умел посчитать**, а остальное
осталось прозой без присмотра.

## Подозреваемый в `aes.flang`, названный, но НЕ доказанный

Таблицы подстановки — списки на 517 чисел (прямая и обратная вместе).
Поиск по ним идёт через `«Байт по номеру»`, а та берёт `элемент номер в
байты` — то есть **обращение по номеру к списку**.

У дерева уже есть замер ровно этой породы:
`docs/zettel/a-hash-dictionary-cheapens-the-lookup-and-the-building-costs.md`
и предшествующий ему `linear-lookup-of-a-declaration-eats-88-percent-of-check-loops.md`
— линейный перебор в `«Найти описание»` съедал **88 % витков** проверки, и
чинили его словарём `flang/stdlib/hashmap.flang`.

Плюс `«Байт по номеру»` несёт **шесть постусловий**, и непроказанные из них
проверяются при каждом вызове.

**Почему не чиню.** Гипотеза не доказана: профилировщика у меня нет, а
переписывать криптографический примитив, у которого 209 доказанных
обещаний из 337, ради непроверенной догадки — риск больше выигрыша. Все
209 доказательств пришлось бы проводить заново.

Чтобы гипотезу проверить, нужен замер шагов на одном вызове поиска против
одного вызова без поиска. Это отдельная работа.

## Что делать с шагом CI, пока не починено

Шаг `binary.yml:318` идёт 44 минуты и **не имеет своего срока**. Пока
причина не найдена, предлагаю не прятать беду, а сделать её видимой и
ограниченной. Врезка (файл не мой, ставит координатор):

```yaml
      - name: Примеры stdlib и ядра
        # ЦЕНА ЭТОГО ШАГА ИЗМЕРЕНА И ОНА ВЕЛИКА: 44 мин из 50 у всей работы
        # (задача 6163), при обещанных шапкой 53 с. Обещание не
        # воспроизводится ни на нынешнем семени, ни на семени до перепечаток
        # сентября (задача 3841) — то есть примета в шапке была неверна, а не
        # дерево замедлилось. Срок поставлен, чтобы работа падала по сроку с
        # понятной причиной, а не висела час.
        timeout-minutes: 55
        run: |
          set -eu
          ./bootstrap/flang test flang/stdlib/
          ./bootstrap/flang test flang/core/
```

**Разбивать шаг на файлы не предлагаю**: это спрячет цену в двадцати
строках вместо одной, а суммарные минуты раннера не изменит.

**Исключать медленные файлы НЕЛЬЗЯ.** `aes.flang` — 151 пример на 105
функций, и это единственная проверка криптографии в дереве. Убрать его из
шага значит перестать проверять AES вовсе, а выигрыш — те же минуты, что
уйдут в следующий раз.

## Не сделано

* **Обход не досчитан до конца.** Замерены 11 файлов `stdlib` из 42 и все
  4 файла `core`. Прогон каждого файла по 300 с, а медленных в дереве
  несколько — полный обход берёт около часа, и я его оборвала. Форма беды
  из измеренного видна: рядовой файл идёт секунды, выбросов несколько.
  Досчитать стоит, но вывода это не изменит.
* **Причина медленности `aes.flang` не доказана.** Подозреваемый назван
  выше (поиск по списку на 517 чисел, шесть постусловий на вызов), но
  профилировщика нет, а без него это догадка.
* **Ничего не чинилось.** Правка в `flang/stdlib/` бессмысленна, пока не
  доказано, ЧТО именно дорого; а числа в шапке `binary.yml` — не мой файл.
* **Прибор «примеров-в» не написан** — без него приметы к числам примеров
  не поставить, а это и есть настоящая починка.
