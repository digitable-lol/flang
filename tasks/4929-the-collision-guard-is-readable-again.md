**Потому что он краснеет пятьюдесятью пятью столкновениями, из которых
настоящее — одно.**

программой** (43 модуля). В такой склейке сталкиваются модули, которые ни в
одной настоящей программе не встречаются: `ecdsa` с `rsa`, `ecdsa` с `x25519`,
`lists` с `math-classics-lists`, `tls` с `образцы`.

Настоящих ровно две программы:

* `flang/self/bootstrap/compiler.flang` — функция `«В ёлочках»` (та самая);

## Отдельно: файл, невидимый поиску глазами

Сторож читает файлы сам и слепым не был. **Слепым был обзор руками.**

`flang/self/link.flang` содержит байт `0x00` — в строковом литерале на строке
1005, разделителем составного ключа:

```
пусть «ключ» равно (соединить [(«к».«поле»), "<0x00>", («к».«имя»)] по "")
```

Из-за него файл считается двоичным всеми поисковыми средствами:

* `ugrep -I` и `rg` пропускают файл ЦЕЛИКОМ и молча;
* GNU `grep` без `-a` печатает совпадения ДО байта и глушит все, что после,
  отвечая «binary file matches» вместо строк.

Это единственный такой файл в дереве: 858 файлов с `модуль` у `grep -a` против
857 у поиска с пропуском двоичных. Именно поэтому обзор руками насчитал шесть
объявлений `«В ёлочках»` вместо семи и решил, что `link.flang` имени не
объявляет вовсе.

Отсюда две строки в `AGENTS.md` (или в наставление по поиску): **искать по
дереву только с `grep -a`**, и знать, что `rg`/`ugrep` этот файл не видят.
Заменять сам разделитель вслепую НЕЛЬЗЯ: он уезжает в ключи связывания, и
замена обязана быть сверена перепечаткой.

### Байт 0x00: менять его не нужно, нужно писать его иначе

**Разделитель обязан быть таким, какого нет в значениях `«поле»`, и нулевой
байт этому отвечает — но он не обязан быть СЫРЫМ БАЙТОМ в исходнике.**

Дерево уже умеет писать его escape-последовательностью, и делает это рядом:
`flang/self/proofterm.flang:2367` строит такой же составной ключ —
`соединить [«кого», "\u0000", «имя»] по ""` — и сырого нулевого байта в файле
НЕТ (проверено побайтово). Комментарий там объясняет ту же причину: имена
пишутся русскими словами, пробелы в них законны, склейка через пробел дала бы
двум разным парам один ключ.

Что оба написания дают одно и то же — снято двумя прогонами, а не рассуждением:

* `bootstrap/flang tokens` на двух копиях `link.flang` (сырой байт против
  `"\u0000"`) отдаёт **один и тот же токен** `1005:48 строка <0x00>`; различаются
  только НОМЕРА СТОЛБЦОВ после него, потому что escape занимает восемь знаков
  вместо одного. Родов и значений токенов различий нет;
* напечатанное семя это уже подтверждает: обе записи схлопнулись в ОДНУ
  константу. `bootstrap/compiler_flang.c:630` —
  `compiler_flang_text_618 = { FL_STRING, { .string = { "\000", 1, 1 } } }`, и на
  неё ссылаются обе склейки: строка 277490 (`[кого, sep, имя]` из
  `proofterm.flang`) и строка 294444 (`[поле, sep, имя]` из `link.flang`).

Отсюда цена замены: **одна строка в `flang/self/link.flang`, и перепечатка,
которая напечатает БАЙТ В БАЙТ то же самое** — значение ключа не меняется,
меняется только его написание в исходнике. Сам разделитель трогать не нужно и
не следует.

Правка СДЕЛАНА — отдельной работой, задачей 9350 того же дня: в
`link.flang:1005` теперь escape-последовательность, сырого байта в дереве не
осталось ни одного. Дерево разбора до и после совпало во всём, кроме трёх
номеров столбцов на этой строке. В двоичном появится только перепечаткой.

### Слепым был не сторож, а поиск — и не тот, на который думали

Сторож читает `readFileSync` и видит в `link.flang` все **178 объявлений**, из
них **56 после строки 1005**. Слеп он не был никогда.

Средства поиска ведут себя ПО-РАЗНОМУ, и заявленное в этой задаче верно лишь
наполовину:

| средство | что делает с `link.flang` |
|---|---|
| обёртка `grep` в оболочке Claude Code (ugrep с `-I`) | **пропускает целиком и молча**, код 1. Это и увело предыдущего исполнителя |
| GNU `grep -n` без `-a` | печатает до байта и глушит после: 89 строк из 122 по образцу `тотальная функция`, вместо остальных «binary file matches» |
| GNU `grep -c` | **честен и без `-a`**: 122 и там и там. Обрезается печать строк, а не счёт. Значит `grep -c` не врёт, а `grep … \| wc -l` врёт |
| `rg` на явном файле | **честен**: все 122 строки, код 0 |
| `rg` рекурсивно | **слеп**: `rg -n … .` — пусто, `rg -an … .` — находит. Задача называла `rg` слепым; он слеп только в обходе |
| `git grep` без `-I` | **честен**: нюх двоичности у git — первые 8000 байт, а нуль лежит на 100 226 |

Ключ `-a` чинит обоих виноватых: обёртке он отменяет `-I` (проверено —
`grep -na 'функция «В ёлочках»'` находит строку 281, без `-a` код 1 и пусто).
Правило записано в `AGENTS.md` разделом «Поиск по дереву слепнет на одном
файле».

Отдельно: `«В ёлочках»` стояла в `link.flang` на строке **281**, то есть
ЗАДОЛГО до нулевого байта, — GNU grep её находил. Не находила обёртка, которая
роняет файл целиком независимо от того, где в нём байт.
