# 6551 — сторож работал только там, где каталог остался от прошлого раза

## Как найдено

Работник R1 (задача 9220) прогонял восемь незваных сторожей и получил на
`занятые:проверка` **код 1** в свежем клоне:

```
cannot open output/storozh-zanyatogo.json: No such file
```

После `mkdir -p output` — код 0. R1 починку не делал, передал дальше.

Задача 9028 записала этого сторожа зелёным. Почти наверняка мерила в клоне,
где `output/` остался от прошлых прогонов. **Тот же род ошибки, что задача
3740 поймала у себя с кодом 127: прибор мерил не то, что думал.**

Для CI это решающе — выкладка там всегда свежая.

## Бед оказалось ДВЕ, а не одна

### Беда 1 — каталог никто не заводит

Сторож пишет пачку вопросов в `../output/storozh-zanyatogo.json`
(`«Файл пачки»`) и заново зовёт двоичный прочесть её
(`«Команда прогонщика»`: `cd .. && exec bootstrap/flang < output/…`).

`output/` стоит в `.gitignore` (строка 11), в свежем клоне его нет, а
поручение `«Записать файл»` каталогов не заводит.

**Починено:** `mkdir -p output` добавлен в `«Команда корпуса»` — это первая
оболочка, которую сторож запускает, и единственное место ДО записи, где можно
завести каталог, не добавляя шага в доказанный обход. Оба постусловия
команды корпуса («два довода», «идёт через ключ -c») сохранены, пример
обновлён.

### Беда 2 — неудачная запись не проверялась вовсе

Обработчик `«Ждём запись»` **не смотрел отклик**: он безусловно запускал
прогонщика, что бы хозяин ни вернул. Сравнить с соседним `«Ждём корпус»` — у
того есть `разбор отклик` и `случай любое → Провал`.

Поэтому провал записи выглядел как провал ЧТЕНИЯ, и сообщение винило не того:

```
прогонщик ответил 0 раз на 1 вопросов о цели c — смотреть нечем
```

Читающий пошёл бы чинить прогонщика.

**Починено:** `«Ждём запись»` разбирает отклик — `«Записано»` ведёт дальше,
всё прочее даёт `«Провал»` с названной причиной и местом.

## Проверено прогонами, в клоне БЕЗ каталога output

```
до починки           код 1, «cannot open output/… No such file»
после починки        код 0 за 33 с, каталога не было
```

Проба на беду 2, одна переменная — `mkdir` убран, проверка отклика
оставлена:

```
код 1, и сообщение теперь своё:
  «пачка вопросов не записалась в ../output/storozh-zanyatogo.json —
   прогонщику нечего читать; каталог output заводит «Команда корпуса»,
   проверить его»
прежнего «смотреть нечем» в выводе больше нет (0 вхождений)
```

То есть беда 2 чинит не поведение, а ДИАГНОЗ: сторож перестал винить
исправную часть себя.

`flang check scripts/occupied-names-guard.flang` — «функций 39, из них с
доказанным завершением 39; типов 10; замечаний нет».
