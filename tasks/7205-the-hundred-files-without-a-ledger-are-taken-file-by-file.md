# 7205. Файлы без ведомости: работа, которая делится на многих

**Это самая делимая работа дерева.** Файлы независимы: один файл — один прогон —
один приговор. Двадцать человек возьмут двадцать файлов и не помешают друг
другу ничем, кроме мест у ворот.

## Чем это снимается

Приёмом из задачи **6128** и никаким другим. Общий двоичный дерево ядра
прочесть не может вовсе (`FLANG_TYPE_ARGS`). Приём собран и лежит готовым:

* двоичный — `/srv/flang-rabota/m-kernel-ledger/build-kernel/flang` (14 МБ):
  `compiler_flang.c` из семени **дословно**, `flang_runtime.c`/`.h` из
  `flang/src/emit/c/` **дословно**, `flang_repl.c` из дерева плюс заплата ключа
  предела;
* **блок настроек из шапки семени переносить обязательно.** Без него
  `FL_MAX_TAIL_ARGS` падает с 9 до 4 и первый же `check` бьёт стек — записано в
  `docs/zettel/a-seed-with-tree-runtime-smashes-the-stack-without-its-limits-block.md`;
* ключ — `--предел-шагов 400000000000`. Он **задаёт** предел, а не поднимает:
  поставить «с запасом» 400000000 значит опустить его вдесятеро;
* ворота — `env PAMYAT=45G /srv/flang-rabota/vorota/flang-vorota -- …`.

## Как делить работу

По файлам, а не по кучам. Каждый берёт список файлов, объявляет доли
(`/srv/priyom/claim взять <ветка> <файл>…` — доли нужны на **выходы**, а не на
исходники: исходники никто не правит) и пускает по одному-двум прогонам, а не
веером: один прогон берёт 45–60 ГиБ на десятки минут.

Порядок — по возрастанию цены, чтобы дешёвое не ждало дорогого. Цена
определяется **замыканием ввоза**, а не числом обязательств: ядро при 44
обязательствах шло 52 мин при пике 9,65 ГиБ.

**Срок ставить не 150 секунд.** Семьдесят одному файлу из девяноста шести его
не хватило, и это единственное, что их остановило.

## Как понять, что сделано

Для каждого взятого файла есть выход `check --proof` и приговор **по самому
файлу**, посчитанный отдельно от ввезённого:

```sh
python3 <приём>/dolya-fajla.py <файл>.flang <выход>.out
# ДВА СЧЁТА СОШЛИСЬ. Доказано N из M = …
```

Строка «итог:» в счёт **не идёт**: она берёт замыкание и завышает — на ядре в
34,2 раза, на `proofterm` в 12,9.

Задача считается сделанной, когда **число файлов без ведомости равно нулю**, а
каждый файл, который не дался и с приёмом, переехал в другую кучу с названной
причиной — не остался в этой.

### 1. «Семьдесят один файл из девяноста шести остановил `SROK=150`» — неправда

Проверено на ТРЁХ срезах из трёх, и ни на одном срок не остановил ни одного
файла. Останавливало другое, и у каждой причины своё имя:

| причина | сколько | как выглядит |
|---|---|---|
| объявление `процесс`/`надзор`/`прогон` в файле | **18 файлов, 68 обязательств** | код 2, «ведомость не печатается: в программе объявлено то, чьи законы бинарник не считает — processes, supervisors, runs»; отказ приходит за 0,07–4,00 с при пике 10–37 МБ |
| подделка, обязанная быть отвергнутой по типам | 1 файл, 2 обязательства | `FLANG_TYPE`, код 1; у программы с замечаниями ведомости не бывает и не будет — это не долг |
| вшитая в семя константа предела витков ПРИМЕРОВ | 1 файл | `FLANG_RECURSION_LIMIT` у примера; ключом не поднимается вовсе |
| стек хозяина проверяющего | 3 файла, 53 обязательства | глубина 2 074 970 — см. задачу 2469 |

Совпадение по срезу `core`+`conc` полное: у всех 18 отказавших объявление есть,
ни у одного из 11 остальных — нет. **Срок был назван виновным по совпадению:
второй заход шёл с `SROK=150`, и всё, что не далось, списали на него.**

В опись заведён знак **`×`** — «мерено приёмом 6128, двоичный ведомости не
напечатал». Прочерк по-прежнему значит «не мерено». Это разные вещи, и путать
их — ровно та беда, ради которой задача заведена.

### 2. Ключ `--предел-шагов 400000000000` из рецепта сегодня ОПУСКАЕТ потолок

Вшитое умолчание выросло: `bootstrap/flang_runtime.h:11` — `FL_MAX_STEPS`
**1 400 000 000 000**, а не миллиард. Снято не чтением файла, а сборкой того же
заголовка, которым собран двоичный (`cc -I bootstrap`), и подтверждено строкой
хода живого прогона: «шагов 9 224 184 469 из 1 400 000 000 000 (0 %)».

Значит рецепт этой задачи просит **в 3,5 раза меньше вшитого**. Ключ ЗАДАЁТ
предел, а не поднимает — правило известное, но здесь оно сработало против нас же.
Ставить ключ наугад опаснее, чем не ставить.

### 3. Приём 6128 берёт не всё, и это надо знать до прогона

У двоичного `/srv/flang-rabota/m-kernel-ledger/build-kernel/flang` в справке
`check` есть `--предел-шагов` и **НЕТ `--предел-глубины`** (снято `check --help`,
код 0). Файл, упирающийся в глубину, он взять не может — там нужен ствольный
двоичный. Три файла задачи 2469 именно поэтому не снялись.

Зато сам двоичный **воспроизведён побайтово**: `cmp` код 0, md5
`f32d89f599dd6b9f740f42a752dff1ff`, 14 065 960 байт; дерево его найдено —
коммит `4a26cf05`, все семь файлов из одного коммита. Рецепт лёг в
`scripts/build-ledger-binary.sh`, снятие — в `scripts/take-proof-ledger.sh`.

### 4. Память: 45 ГиБ не нужны, и просьба на них стоит очереди

Замеры этого захода: обычный модуль библиотеки берёт **0,36–3,6 ГиБ**.
`scram`, о котором дерево пишет «пик 28,7 ГиБ и четверть часа», занял
**0,36 ГиБ** — число устарело в 78 раз, оно взято из верхней таблицы
`docs/memory-and-fan-out.md`, которую тот же файл сотней строк ниже сам
опровергает (`28,36 → 1,18 ГиБ`), и повторено в `docs/proof-goal-map.md:323`.

Пока просили по 45 ГиБ, ворота показывали «роздано 294 из 299» при 353 ГиБ
свободной памяти на машине: **очередь стояла на бухгалтерии, а не на железе.**
Честная просьба — `PIK=2G PAMYAT=8G` на модуль библиотеки.
