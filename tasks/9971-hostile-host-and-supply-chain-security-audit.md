# 9971 — защищены ли мы от хакинга и грязного хоста

Владелец: «Защищены ли мы от любого хакинга и грязного хоста?»

## Находка координатора, уже подтверждена грепом — начать отсюда

**Все сторонние действия GitHub Actions закреплены плавающим тегом
major-версии, ни одно — неизменяемым коммитом (SHA):**

```
actions/checkout@v4        (все семь workflow-файлов)
actions/setup-node@v4      (install-path.yml, pages.yml, build-macos.yml, release.yml)
actions/configure-pages@v5, actions/upload-pages-artifact@v3, actions/deploy-pages@v4  (pages.yml)
```

Это известный класс уязвимости цепочки поставки: тег `@v4` — не
неизменяемая ссылка, его может подвинуть либо сам автор действия, либо
тот, кто получил контроль над его репозиторием, — и все, кто следует
`@v4`, молча получат другой код на следующем прогоне. Официальная
рекомендация GitHub по укреплению CI — закреплять `uses:` полным
коммит-хешем (`actions/checkout@<sha>`), а не тегом. Сегодня этого
нигде нет.

## Что ещё проверить

1. **Секреты — где именно и с какой областью действия.** Только
   `release.yml` использует секреты (`NPM_TOKEN` через `setup-node`,
   `GH_TOKEN`) — проверить, что они НЕ доступны никаким другим
   workflow-файлам и что `release.yml` не запускается на
   `pull_request` от чужого форка (классическая дыра: PR из чужого
   форка получает доступ к секретам через `pull_request_target` или
   похожий триггер — свериться, что нигде такого нет,
   `grep -n "pull_request_target"` по всем workflow).
2. **Внедрение через недоверенный ввод.** Проверить каждый `run:` во
   всех `.github/workflows/*.yml` на прямую подстановку
   `${{ github.event.* }}`/`${{ github.head_ref }}` и подобного
   недоверенного контекста в тело shell-команды без `env:`-прослойки —
   это классический вектор внедрения команд через PR-заголовок, имя
   ветки и т.п.
3. **Отравление кеша.** Сегодня вечером кеш приговоров ядра (задача
   9391/влито в dev, `FLANG_KESH_PRIGOVOROV`) перенесён на dev.
   `AGENTS.md` уже документирует правило «Кешу верят для СКОРОСТИ, для
   ИСТИНЫ — проверяльщику» и заслон `release-without-cache`,
   принудённый составным действием, — проверить прогоном (не чтением),
   что заслон реально ловит попытку выпуска с заданной переменной кеша
   (`mode: self-test` у сторожа, восемь пар подделок, уже упомянут в
   `AGENTS.md` — прогнать его и убедиться, что он сам не разучился
   краснеть).
4. **Ken Thompson / trusting trust с другой стороны.** Задача 9970
   спрашивает, достаточно ли МАЛЕНЬКОГО компилятора для доверия. Эта
   задача — про ДРУГУЮ половину того же вопроса: если машина, на
   которой печатается ПЕРВОЕ семя (bootstrap), уже скомпрометирована —
   может ли она внести подмену, которая переживёт самоприменение и
   останется невидимой независимому чекеру? Не решать это полностью
   (это открытая исследовательская проблема даже для больших языков) —
   но честно ответить: что СЕГОДНЯ в дереве обнаруживает такую подмену,
   а что нет, и назвать явно, где граница.
5. **Права токенов.** `permissions:` в каждом workflow-файле — сверить,
   что каждый несёт МИНИМАЛЬНО нужное (например, `contents: read` там,
   где не создаётся релиз/страница, `contents: write` только в
   `release.yml`, `pages: write`/`id-token: write` только в
   `pages.yml`) — уже похоже на верно устроено, проверить прогоном
   реального грепа, не на глаз.

## Порог

- Список действий с плавающими тегами — полный, по всем workflow-файлам,
  с точным местом (`grep -n`).
- Рекомендация: закрепить все `uses:` по коммит-хешу, с реальными
  хешами для текущих `@v4`/`@v3`/`@v5` (не просто «надо закрепить», а
  готовая правка, если время позволяет).
- `pull_request_target` и подстановка недоверенного контекста в
  `run:` — проверены прогоном грепа по всем файлам, каждое найденное
  место разобрано: опасно или нет.
- Заслон `release-without-cache` проверен собственным self-test
  прогоном, не на слово документации.
- Честно названа граница: что в дереве СЕГОДНЯ обнаруживает
  скомпрометированный сборочный хост, а что нет — без преувеличения
  защищённости, которой пока нет.

## Не входит

Полный аудит безопасности инфраструктуры GitHub (аккаунты, MFA,
организационные права) — вне досягаемости ячейки, у которой нет к этому
доступа. Эта задача — про дерево кода и конфигурацию CI, которые видны
и проверяемы прогоном.
