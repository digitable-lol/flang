# 9984 — «по предположению» проверяется текстом, не смыслом

Найдено расследованием Ч409 (4 сентября, продолжение цепочки Ч405→Ч406→Ч408
по задаче 9616), не реализовано — намеренно, см. «Порог».

## Находка

`sverit_shagi` (`flang/proof/чекер/сверщик.c:1829`) для шагов «по
предположению» (обращение к индукционной гипотезе внутри разбора по
случаям) проверяет ТОЛЬКО, что текст шага в записи совпадает с текстом
шага в исходнике (`strcmp`/`soderzhit`). Он НИКОГДА не проверяет, что сам
шаг математически состоятелен — запись может звать «по предположению» для
любого утверждения, на любом подтерме, и пройдёт, пока слова совпадают.

Это ТОТ ЖЕ КЛАСС уязвимости, что снял Г2 31 августа и что чинила Ч392
вечером 3 сентября — только в другом маршруте чекера.

**Масштаб:** 29 вхождений `по предположению` в 15+ файлах корпуса
(списки, деревья, стеки, факториал, доказательства предусловий) — это
ОСНОВНОЙ механизм закрытия структурной индукции в корпусе, не редкий
случай. Задача 9616 сама называла этот маршрут только мимоходом (33 «шага
допущением» одной ячейкой) — реальный охват органа шире, чем виделось.

## Как ядро на самом деле это доказывает

`flang/self/proofterm.flang:2899` («Индукция по разбору») и сосед
«Сведение посылки допущением» (~2960): ядро строит РОВНО ОДНУ гипотезу на
рекурсивно убывающее поле совпавшего конструктора (например, `хвост` в
`случай голова и хвост`), подставляет её в цель. Шаг, зовущий не тот
подтерм, «не совпадёт с гипотезой — сравнение синтаксическое, и вердикта
не будет» (комментарий самого ядра). Реальные шаги (`corpus-lists.flang`
«длина неотрицательна») пишут голое `то по предположению` БЕЗ видимой
формулы — ядро само выводит связь гипотезы с целью перезаписью выражений
(теми же правилами, что «неотрицательность по построению» в
`proof-kernel.flang`), а НЕ из того, что говорит запись.

## Почему не реализовано этим же вечером

Честный, независимый чекер шага потребовал бы РЕАЛЬНОГО повтора вывода на
уровне выражений (подставить механически построенную гипотезу в тело
случая, подтвердить, что она влечёт цель) — не простого повтора терма, как
у `proigrat_uzel` для других видов шагов. Два честных пути:

(а) переписать значимый срез собственных правил перезаписи ядра в чекере
на C — дорого и само по себе рискованно (чекер снова растёт, снова может
ошибиться в том же классе);

(б) вероятно более дешёвый путь — тот же архитектурный пробел, что уже
назван задачей 9616 для маршрута «по объявлению»: ядро вычисляет
подстановку/влечение по-настоящему и ВЫБРАСЫВАЕТ результат при печати
записи. Прокинуть эту же цепочку (proofterm.flang → zapis.flang →
сверщик.c) для маршрута «по предположению» позволила бы чекеру сверять
НАПЕЧАТАННУЮ цепочку синтаксически, не выводя её заново, — вероятно,
намного меньше строк C, чем (а).

## Порог

- Каждое из 29 мест доказано РЕАЛЬНЫМ прогоном на настоящей корпусной
  записи, не выводом из чтения кода.
- До того, как хоть одно место засчитано: сконструирована минимум одна

- Полный набор проб чекера остаётся зелёным (228+ на сегодня, проверить
  текущее число) без единой регрессии.
- Честно: НОЛЬ мест за один присест — приемлемый исход, если дизайн при
  этом доведён до состояния «следующая ячейка может реализовать, не
  передумывая заново» (эта задача уже там, но реализация — нет).

## ⚑ ПРИМЕР НАЙДЕН 4 сентября: 7 настоящих `kind:"step"`+`by:"reduction"` в flang/stdlib/tree.flang

Полный обход, не догадка. `check --proof --json` прогнан на всех 16
файлах `flang/proof/examples/*.flang`, чей исходник содержит «по
предположению» (список см. `grep -l 'по предположению'
flang/proof/examples/`, ровно те 15+, что называет находка задачи), плюс
два файла, которые Ч415 не досчитала за 200 млн шагов —
`flang/stdlib/tree.flang` (657 строк) и `flang/stdlib/hashmap.flang`
(1016 строк). Для последних двух хватило бюджета `--предел-шагов
3000000000` (3 млрд) — оба досчитались за секунды, 200 млн оказалось
малым бюджетом, не признаком дороговизны файла.

**Свод `(kind, by)` по всем 18 файлам:**

| kind | by | штук |
|---|---|---:|
| step | term | 19 |
| постусловие | declaration | 71 |
| base | term | 16 |
| base | reduction | 15 |
| **step** | **reduction** | **7** |

Все 7 — в `flang/stdlib/tree.flang`, ноль в `hashmap.flang` и ноль в
остальных 16 файлах `flang/proof/examples`. Ч415 не нашла ни одного,
потому что искала среди `flang/proof/examples` (где их и правда нет) и
не досчитала единственные два файла, где они есть.

**Семь настоящих мест**, все `variant:"Узел"` (структурный случай-шаг
дерева), все `"verdict":"доказано"`, все `"steps":0` — то есть именно
та форма, которую, по находке Ч412, `sverit_polya_posylok` сегодня
принимает по одному учёту «шагов == 0», а не доводом:

| obligations[N] | теорема/обязательство |
|---:|---|
| 21 | узел без левого ребёнка не меняет приоритета корня |
| 28 | узел без правого ребёнка не меняет приоритета корня |
| 43 | размер неотрицателен |
| 44 | дерево с ненулевым приоритетом корня — не пустое |
| 48 | есть ключи — глубина не меньше одного |
| 49 | глубина неотрицательна |
| 52 | у узла глубина — глубже обоих поддеревьев |

**Как повторить, дёшево (секунды, не часы):**

```
make -C bootstrap
./bootstrap/flang check flang/stdlib/tree.flang --proof --json \
  --предел-шагов 3000000000 > tree.json
python3 -c '
import json
d = json.load(open("tree.json", encoding="utf-8"))
for i, ob in enumerate(d["obligations"]):
    s = json.dumps(ob)
    if "\"kind\": \"step\"" in s and "\"by\": \"reduction\"" in s:
        print(i, ob.get("name") or ob.get("says"))
'
```

**Чего это НЕ делает.** Не проба порчи (её всё ещё нет — «Порог» задачи
требует заведомо поддельную запись на этом же примере ДО того, как
место засчитано) и не реализация починки (пути (а)/(б) выше). Только
находка: РЕАЛЬНЫЙ, живой, не выдуманный пример существует, назван
поимённо, воспроизводится за секунды. Следующая ячейка может сразу
строить пробу порчи на `obligations[49]` («глубина неотрицательна» —
самый простой из семи по структуре цели) вместо повторного поиска.
