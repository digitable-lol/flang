# 0046. Сравнение записей на равенство перестало быть квадратом

Профиль живой перепечатки 25 августа 2026, 100-я минута:

```
51.95%  fl_fields_equal    сравнение полей записи
40.21%  fl_equal
 3.65%  __strcmp_avx2
```

**Девяносто два процента времени — сравнение значений на равенство.**

Это четвёртая сверхлинейность, найденная за неделю, и она вскрылась ровно тогда,
когда убрали предыдущую: пока память копилась, её не было видно.

```
перебор по имени       снят словарём (0020)     87 % витков ядра
связывание             квадратично, показатель 2,04
цена ядра              проход на факт, ×16 к сумме частей
СРАВНЕНИЕ ЗАПИСЕЙ      квадрат по числу полей   ← эта
```

## Половина уже сделана

В дереве `fl_fields_equal` **уже пробует диагональ**:

```c
if (left[index].name == right[index].name) {
  found = fl_equal(left[index].value, right[index].value);
} else {
  for (other = 0; other < right_count; other += 1) { … }
}
```

Правка влита 25 августа (`u/runtime-polya`). До двоичного она доедет
перепечаткой — той самой, чей профиль снят выше: печатник её ещё не несёт.

## Что осталось

**Померить, что диагональ даёт на самом деле.** Если записи сравниваются с
переставленными полями — диагональ промахивается, и квадрат остаётся. Снять
профиль ПОСЛЕ перепечатки и сравнить с числами выше.

Если 52 % не упали — думать дальше: порядок полей у записи наблюдаем и
детерминирован, значит сравнение можно свести к одному проходу без поиска вовсе,
а расхождение порядка считать неравенством и ловить отдельно.

## Профиль снят заново — и не perf'ом

**`perf` на этой машине недоступен, и это надо было сказать вслух.**
`/proc/sys/kernel/perf_event_paranoid` равен **4** (запрещает даже программные
события непривилегированному пользователю), `sudo` нет, а сама перепечатка идёт
под пользователем `u`, тогда как исполнитель — `m`: два запрета, каждого из
которых хватило бы. Дословно:

```
$ perf record -F 99 -p 122289 -- sleep 5
>= 2: Disallow kernel profiling
Error:
Failure to open any events for recording.
```

Поэтому мерено **счётчиками, врезанными прямо в рантайм** — тем же способом,
каким мерена задача 0020. Двоичный для замера — не «похожий», а ДВОЙНИК
работающего печатника: исходники `/srv/flang-rabota/u-semya5/bootstrap-pechatnyy`
скопированы дословно (`md5` рантайма сошёлся), собраны теми же флагами, и
изменён в них ровно раздел равенства.

Работа: `emit flang/self/lexer.flang --target c` — та же операция, что и у
перепечатки, только на одном модуле. Код 0, 8 мин 50 с, пик 383 МиБ.

## Причина названа по коду, и она НЕ ТА, что стояла в задаче

Задача предполагала: поля ищутся перебором, и сравнение двух записей по n полей
стоит n². Перебор действительно есть — 134 млрд витков, — но **он не главный**.

**Главная причина: `fl_equal` не сверяет указатели.** Значения flang неизменяемы
и живут в арене; `равен` над записью, вариантом и списком в 99,9 % случаев
зовётся на ОДНОМ И ТОМ ЖЕ значении — и до этой правки каждый такой зов обходил
всё дерево до листьев вместо одного сравнения указателей. У строк такой отсев
уже был (`fl_bytes_same` начинается со сверки указателей), у записи, варианта и
списка — не было.

Отсюда и профиль: 71 % всех зовов `fl_equal` (34,9 млрд из 49,1) — сверка
значения с самим собой.

**Вторая причина, уже снятая деревом:** диагональ (влита 25 августа,
`u/runtime-polya`) промахивается НОЛЬ раз на 41 миллиарде полей. Значит она
снимает все 134 млрд витков перебора и все зовы `fl_name_same` вместе с ними —
это и есть `__strcmp_avx2` из профиля. До двоичного она не доехала: печатник,
который сейчас печатает семя, несёт ещё перебор (проверено чтением его
`flang_runtime.c`).

## Как понять, что сделано

Профиль перепечатки, снятый тем же способом (`perf record -F 99 -p <pid>`), и
доля `fl_fields_equal` названа числом до и после.

## Чем закрыта

Ветка `u/record-equality-not-quadratic`. Правка — девять строк кода в
`flang/src/emit/c/flang_runtime.c`: три сверки указателей в `fl_equal` — у
записи, у варианта и у списка (у списка вместе с длиной). Диагональ поиска поля
оставлена как была: замер показал, что она промахивается ноль раз.

⚠ **Файл уезжает в напечатанный вывод ДОСЛОВНО** — правка меняет поведение всех
напечатанных в C программ, а не только компилятора. В собранном компиляторе она
появится только после перепечатки семени.

### Замер

Одна работа, три двоичных, отличие ровно в разделе равенства. Двоичные собраны
из исходников работающего печатника (`u-semya5/bootstrap-pechatnyy`), теми же
флагами. Работа: `emit flang/self/lexer.flang --target c`, код 0 у всех.

### Чем доказано, что вывод не поехал

* `diff -r` напечатанного C — **пуст на всех трёх парах**, 824 937 байт у всех
  трёх;
* ведомость `check --proof` — один md5 `5a98fd7198ddffab67a06f8a1bbc586b` у всех
  трёх, 6889 байт;
* проба края `/srv/tmp/u-record-equality/equality-probe.flang`, 22 примера:
  порядок полей прямой и обратный, вложенные записи, списки внутри записей,
  списки записей, `содержит` по записи, `не число` внутри записи, минус ноль
  против нуля, значение равное самому себе по ссылке. **Прошло 22 из 22 у всех
  трёх двоичных.**

Правка до двоичного доедет только перепечаткой. Отпечаток входов
`scripts/otpechatok-semeni` теперь разойдётся с деревом — это верно и ожидаемо,
снимет его та же перепечатка. Руками он не правится.
