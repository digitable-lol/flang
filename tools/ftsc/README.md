# ftsc — компилятор проекта на FTS

Ядро FTS компилирует один файл. `ftsc` собирает **проект**: дерево `.fts`-модулей,
импорты между категориями, функторы между предметными областями — и печатает всё
это на одном из восьми языков.

Инструмент живёт в этом репозитории и работает поверх собранного ядра, поэтому
перед первым запуском нужен `npm run build` — он кладёт компилятор в `dist/src`.
Все команды ниже запускаются из корня репозитория.

```bash
npm run build

node tools/ftsc/bin/ftsc.mjs check tools/ftsc/stdlib
node tools/ftsc/bin/ftsc.mjs build tools/ftsc/stdlib --target rust --out generated
node tools/ftsc/bin/ftsc.mjs build tools/ftsc/stdlib --all --out generated
node tools/ftsc/bin/ftsc.mjs graph tools/ftsc/stdlib
node tools/ftsc/bin/ftsc.mjs targets
```

Спецификация синтаксиса, IR и контракта бэкендов — в [SPEC.md](./SPEC.md).

## Что добавлено к языку

Ровно три вещи; сам язык не изменён, и любой существующий `.fts` остаётся
валидным модулем без единой правки.

1. **Заголовок модуля** — `модуль`, `использует`, `экспортирует` (и `module`,
   `uses`, `exports`). Строки до `категория` снимает `ftsc`, тело дословно
   уходит компилятору ядра.
2. **Функтор между категориями** — отдельный файл, отображающий объекты, поля и
   морфизмы одной предметной области в другую. В ядре есть только морфизмы
   *внутри* категории; это второй этаж.
3. **Кодогенерация на восемь языков** — C, Rust, C#, Java, Elixir, Go, Python,
   TypeScript.

## Что проверяется

| Проверка | Код |
|---|---|
| импорт указывает на существующий модуль и ту категорию, что заявлена | `FTSC_IMPORT_NOT_FOUND`, `FTSC_IMPORT_CATEGORY` |
| экспортируется только то, что в модуле есть | `FTSC_EXPORT_UNKNOWN` |
| нет циклов импорта | `FTSC_MODULE_CYCLE` |
| функтор тотален на объектах и полях домена | `FTSC_FUNCTOR_OBJECT_MISSING`, `FTSC_FUNCTOR_FIELD_MISSING` |
| образ существует в категории-кодомене | `FTSC_FUNCTOR_TARGET_UNKNOWN` |
| форма данных сохраняется, состояние переименовывается согласованно | `FTSC_FUNCTOR_FIELD_TYPE`, `FTSC_FUNCTOR_STATE_CONFLICT` |
| `F(f): F(a) → F(b)` | `FTSC_FUNCTOR_MORPHISM_SHAPE` |
| композиция морфизмов сохраняется | `FTSC_FUNCTOR_COMPOSITION` |

**Состояния переименовываются намеренно.** Поле `является состоянием «Запрос
проверен»` в другой категории становится `«Условие проверено»` — ради этого
функтор и нужен. Карта состояний выводится из отображения полей; два разных
образа одного состояния — ошибка.

Чего проверка **не** делает: она не подтверждает, что отображение верно по
смыслу. Проверяется форма, а не намерение — ровно как с законом морфизма в ядре.

## Допуск к сборке решает сам FTS

Перед кодогенерацией `ftsc` считает факты о проекте и отдаёт их моделям из
[`self/`](./self/README.md): сколько утилит без примеров, сколько несходящихся
примеров, сколько непокрытых полей функтора. Решение «собирать или нет»
принимает утилита FTS, а не JavaScript. Проверено тестом: правка порога в `.fts`
меняет вердикт на тех же данных.

Полный self-hosting невозможен — в ядре нет строк как данных, коллекций и
рекурсии, поэтому лексер и парсер на FTS не напишешь. Подробности и список
того, чего языку не хватает, — в `self/README.md`.

## Бэкенды

Добавить язык — это положить один файл в `src/emit/` с контрактом из SPEC.md;
ядро править не нужно, реестр строится чтением каталога.

Каждый бэкенд обязан: печатать нативные типы, сохранять порядок правил
(выполняются **все** правила с истинными условиями — это не `if/else`),
превращать свойства в ошибку способом, родным для языка, а примеры — в тесты
штатного фреймворка, и обходиться стандартной библиотекой.

## Стандартная библиотека

[`stdlib/`](./stdlib/README.md) — переиспользуемые словари: HTTP, хранилище,
репозиторий, политики повтора, идемпотентности, ограничения частоты и надзора.
Ни одного HTTP-вызова и ни одной SQL-строки: библиотека описывает контракты и
чистые расчёты, эффекты остаются приложению.

## Тесты

```bash
npm run test:ftsc                                # весь ftsc целиком
npm test                                         # ядро репозитория и все инструменты

node --test tools/ftsc/test/core.test.mjs        # разбор, резолвер, линковка, функторы
node --test "tools/ftsc/test/emit-*.test.mjs"    # бэкенды: генерация + компиляция настоящим тулчейном
node --test tools/ftsc/test/self-check.test.mjs  # допуск, принимаемый моделями FTS
```

Тулчейн целевого языка ищется в `PATH`, а затем в каталогах из переменной
`FTS_TOOLCHAIN_PATH` (разделитель — как в `PATH`) и в общеизвестных местах
установки. Так проверяется, например, Go, поставленный мимо `PATH`:

```bash
FTS_TOOLCHAIN_PATH=/opt/go/bin npm run test:ftsc
```

Тест бэкенда, у которого нет тулчейна в системе, пропускается явным `skip` с
причиной — а не притворяется пройденным.

Но пропущенный тест — не пройденный тест, и там, где тулчейн обязан стоять
(CI, машина релиза), пропуск недопустим. За это отвечает `FTS_REQUIRE_TOOLCHAINS`:

```bash
FTS_REQUIRE_TOOLCHAINS=1        node --test "tools/ftsc/test/emit-*.test.mjs"  # обязательны все бэкенды
FTS_REQUIRE_TOOLCHAINS=rust,go  node --test "tools/ftsc/test/emit-*.test.mjs"  # обязательны только эти
```

С заданной переменной отсутствие компилятора — падение с именем языка и
подсказкой, а не «skipped» (см. `test/toolchain-guard.mjs`). В CI по джобе на
язык: джоба ставит один тулчейн и требует ровно его.
