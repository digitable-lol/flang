# ftsc — спецификация

`ftsc` — компилятор проекта на FTS: он собирает дерево `.fts`-модулей в одну
проверенную программу и печатает её на целевом языке.

Ядро языка не меняется. `ftsc` добавляет ровно то, чего у одиночного файла нет:

1. **модульность** — проект из многих файлов и каталогов;
2. **функторы между категориями** — проверяемое отображение одной предметной
   области в другую (в ядре есть только морфизмы *внутри* категории);
3. **много целевых языков** — C, Rust, C#, Java, Elixir, Go, Python, TypeScript.

Границы честности остаются прежними: FTS описывает данные, чистые вычисления и
допуски. Ни `ftsc`, ни его stdlib не выполняют HTTP-запрос, SQL-транзакцию или
запись в файл — они печатают типы, чистые функции и точки, куда приложение
подставляет свои эффекты.

## 1. Структура проекта

```
project/
  ftsc.json              # манифест проекта (необязателен)
  sales/
    purchase.fts         # модуль: одна категория в одном файле
  billing/
    invoice.fts
  mapping/
    sales-to-billing.fts # модуль только с функтором
```

Каталог не имеет значения для семантики: имя модуля задаётся в файле. Каталоги
нужны людям и относительным путям в `использует`.

`ftsc.json` (все поля необязательны):

```json
{
  "name": "shop",
  "root": ".",
  "targets": ["typescript", "rust"],
  "out": "generated"
}
```

## 2. Заголовок модуля

Файл модуля состоит из **заголовка** и обычного тела FTS. Заголовок — строки до
первой строки `категория`/`category`, начинающиеся с ключевых слов `модуль`,
`использует`, `экспортирует`. Заголовок разбирает `ftsc`; всё остальное дословно
передаётся компилятору ядра, поэтому любой существующий `.fts` остаётся
валидным модулем без единой правки.

```fts
модуль «Продажи»
  использует «Каталог» из «../catalog/product.fts»
  экспортирует «Покупка», «Рассчитать скидку»

категория «Продажи»

  объект Покупка
    сумма является деньгами
    ...
```

Правила:

- `модуль «Имя»` — необязателен; по умолчанию имя модуля равно имени категории.
- `использует «Категория» из «путь»` — путь относительно текущего файла;
  указывать можно как файл, так и каталог с одним `.fts`.
- `экспортирует ...` — список имён объектов и утилит через запятую. Если строки
  нет, экспортируется всё. Импорт неэкспортированного имени — ошибка
  `FTSC_NOT_EXPORTED`.
- Английские синонимы: `module`, `uses`, `exports`, `from`.

Заголовок и функторы — единственное, что `ftsc` добавляет к синтаксису. Внутри
категории язык неизменен: те же объекты, утилиты, правила, свойства, примеры,
морфизмы и теоремы.

## 3. Функтор между категориями

Функтор — отдельный модуль без категории:

```fts
функтор «Заказ в счёт» из «Продажи» в «Биллинг»
  использует «Продажи» из «../sales/purchase.fts»
  использует «Биллинг» из «../billing/invoice.fts»

  объект Покупка отображается в «Счёт»
    поле сумма отображается в поле «сумма без НДС»
    поле «постоянный клиент» отображается в поле «лояльный»

  морфизм «Готовый заказ можно отгрузить» отображается в морфизм «Счёт можно выставить»
```

Что проверяет `ftsc` (и что осмысленно проверить машиной):

| Закон | Проверка | Код ошибки |
|---|---|---|
| тотальность на объектах | каждый объект домена имеет образ | `FTSC_FUNCTOR_OBJECT_MISSING` |
| существование образа | образ есть в категории-кодомене | `FTSC_FUNCTOR_TARGET_UNKNOWN` |
| тотальность на полях | каждое поле объекта отображено | `FTSC_FUNCTOR_FIELD_MISSING` |
| согласованность типов | тип поля-образа совместим с исходным | `FTSC_FUNCTOR_FIELD_TYPE` |
| согласованность морфизма | `F(f): F(a) → F(b)` | `FTSC_FUNCTOR_MORPHISM_SHAPE` |
| сохранение композиции | образ композиции = композиция образов | `FTSC_FUNCTOR_COMPOSITION` |

Чего функтор **не** доказывает: что бизнес-смысл отображения верен. Он
проверяет форму, а не намерение — ровно как теорема в ядре.

## 4. IR

Единственный контракт между фронтендом и бэкендами. Стабилен; бэкенд не читает
`.fts` и не знает про пути.

```jsonc
{
  "ir": 1,
  "project": "shop",
  "modules": [
    {
      "name": "Продажи",
      "category": "Продажи",
      "source": "sales/purchase.fts",     // путь от корня проекта, для комментариев
      "imports": [{ "category": "Каталог", "module": "Каталог" }],
      "exports": { "structures": ["Покупка"], "utilities": ["Рассчитать скидку"] },
      "document": { /* канонический FtsDocument компилятора ядра */ }
    }
  ],
  "functors": [
    {
      "name": "Заказ в счёт",
      "from": "Продажи",
      "to": "Биллинг",
      "objects": [
        { "from": "Покупка", "to": "Счёт",
          "fields": [{ "from": "сумма", "to": "сумма без НДС" }] }
      ],
      "morphisms": [{ "from": "Готовый заказ можно отгрузить", "to": "Счёт можно выставить" }]
    }
  ],
  "order": ["Каталог", "Продажи", "Биллинг"]   // топологический порядок модулей
}
```

`document` — ровно то, что возвращает `compile()` ядра: `category`,
`structures`, `functors` (морфизмы, историческое имя поля), `proposition`,
`utilities`, `ts_compat`.

## 5. Контракт бэкенда

Файл `tools/ftsc/src/emit/<id>.mjs`:

```js
export const target = {
  id: 'rust',                    // имя для --target
  name: 'Rust',
  extension: '.rs',
  // как проверить сгенерированное, если тулчейн доступен
  toolchain: { probe: ['rustc', '--version'], test: ['cargo', 'test'] },
};

/**
 * @param {object} program — IR
 * @param {{ projectName: string }} options
 * @returns {Array<{ path: string, content: string }>} пути относительно --out
 */
export function emit(program, options) { /* ... */ }
```

Требования к любому бэкенду:

1. **Типы объектов.** Каждая структура — нативный тип целевого языка
   (`struct`, `class`, `record`, `type`, `dataclass`). Опциональное поле
   (`иногда является`) — нативная опциональность (`Option`, `nullable`,
   `| undefined`, `*T`).
2. **Утилиты — чистые функции.** Порядок правил сохранён: выполняются **все**
   правила с истинным условием, в порядке объявления. Никаких `else`.
3. **Свойства — постусловия.** Нарушение прекращает выполнение способом, родным
   для языка: исключение, `panic!`, `Result::Err`, возврат кода ошибки в C.
4. **Примеры — тесты.** Каждый `пример` превращается в тест на штатном
   фреймворке языка (`#[test]`, JUnit, ExUnit, `unittest`, `node:test`,
   `assert.h`). Тесты обязаны реально проходить.
5. **Ноль зависимостей.** Только стандартная библиотека целевого языка.
6. **Детерминированность.** Один и тот же IR даёт побайтово одинаковый вывод:
   без дат, случайных имён и порядка из хеш-таблиц.
7. **Идентификаторы.** Имена в FTS кириллические и с пробелами. Каждый бэкенд
   транслитерирует их в допустимые идентификаторы и **обязан** сохранить
   исходное имя в комментарии или атрибуте. Коллизии транслитерации — ошибка
   сборки, а не молчаливое переименование.
8. **Двунаправленные управляющие.** Сохранённое имя (п. 7) уезжает и в
   комментарий, и в строковый литерал, а имя в FTS вправе содержать любой
   символ Unicode. Поэтому ни один бэкенд не печатает двунаправленные
   управляющие (U+061C, U+200E, U+200F, U+202A…U+202E, U+2066…U+2069) сырыми:
   места они не занимают, а раскладку текста меняют, и файл читается не так,
   как исполняется («Trojan Source», CVE-2021-42574). Для rustc и elixirc это
   не придирка, а отказ сборки — и в литерале, и в комментарии. Набор кодовых
   точек общий (`src/bidi.mjs`), форма записи своя у каждого языка (`\uXXXX`,
   `\u{X…}`, восьмеричные байты UTF-8 в C), место — последний шаг `emit()`
   (`escapeBidiInFiles`). Значение при этом не меняется: те же кодовые точки и
   те же байты. Проверяет это общий тест `test/emit-bidi.test.mjs` перебором по
   реестру целей — девятый бэкенд попадает под правило тем, что он появился.
9. **Функторы.** Для каждого функтора печатается функция преобразования
   `F: A → B` на целевом языке (объект домена → объект кодомена).

## 6. CLI

```bash
ftsc check <dir>                 # разобрать, слинковать, проверить функторы и допуск
ftsc build <dir> --target rust --out generated
ftsc build <dir> --all --out generated
ftsc targets                     # список бэкендов и доступность тулчейнов
ftsc graph <dir>                 # категории и функторы диаграммой mermaid
ftsc ir <dir>                    # напечатать IR (для отладки бэкенда)

ftsc build <dir> --all --skip-self-check   # не спрашивать модели допуска из self/
```

Контракт вывода тот же, что у ядра: результат — JSON в stdout, диагностики — в
stderr, ненулевой код возврата при ошибке.

Пакет объявляет `ftsc` в `bin`, поэтому после установки команда доступна прямо
по имени. В самом репозитории она запускается как
`node tools/ftsc/bin/ftsc.mjs <команда>` поверх собранного ядра (`npm run build`).

Что генерируется и как это проверяется настоящим тулчейном — тесты бэкендов
(`npm run test:ftsc`); отдельной команды `ftsc test` нет.

## 7. Что уже написано на самом FTS

`tools/ftsc/self/` — часть компилятора, выраженная моделями FTS и исполняемая
движком FTS во время работы `ftsc`:

- метамодель языка (объекты «Модуль», «Категория», «Утилита», «Правило»);
- правила допуска проекта к сборке (утилиты, чьи примеры — тесты компилятора).

Честная граница: полный self-hosting сегодня невозможен — в ядре нет строк как
данных, рекурсии, коллекций и ввода-вывода, поэтому лексер и парсер написать на
FTS нельзя. На FTS выражена та часть, которая является чистым решением по
проверенным фактам: допускать ли проект к кодогенерации. Остальное — JavaScript.
