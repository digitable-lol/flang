# Часть компилятора, написанная на FTS

Здесь лежит не документация о компиляторе, а сам компилятор — точнее, та его
часть, которую честно удалось выразить на FTS и которая **исполняется движком
FTS во время работы `ftsc`**. Если модель говорит «нет», кодогенерации не будет.

| Файл | Что это |
|---|---|
| `meta.fts` | метамодель: язык описывает структуру собственного IR своими средствами |
| `admission.fts` | правила допуска проекта к кодогенерации |
| `../src/self-check.mjs` | мост: считает факты по IR и исполняет модели |
| `../test/self-check.test.mjs` | тесты моста и моделей |

```bash
node --test tools/ftsc/test/self-check.test.mjs
```

## Граница: что решает FTS, а что JavaScript

```
.fts файлы ──► [ JavaScript ] ──► IR ──► [ JavaScript ] ──► факты ──► [ FTS ] ──► решение
              чтение, лексер,           подсчёт фактов              допуск к
              парсер, линковка          (сбор данных)               кодогенерации
```

**JavaScript** делает всё, что требует ввода-вывода, работы со строками и обхода
структур переменного размера:

- читает файлы и разбирает их (лексер, парсер, заголовки модулей);
- строит IR и линкует модули;
- **считает факты**: сколько утилит без примеров, сколько примеров не сошлось,
  сколько полей функтора осталось без образа, сколько объектов нужно функтору,
  но не экспортировано;
- складывает оценки по модулям (в ядре FTS нет свёртки по списку — см. ниже);
- переводит 1 и 0 из вердикта модели в `allowed: true | false`.

**FTS** делает единственное, но решающее:

- `«Оценить готовность модуля»` — сколько блокирующих проблем в модуле;
- `«Оценить готовность функтора»` — сколько блокирующих проблем в функторе;
- `«Решить о допуске проекта»` — 1 допустить, 0 отказать;
- `«Посчитать элементы модуля»`, `«Оценить самоописание модуля»` — наблюдения
  метамодели для отчёта (ничего не запрещают).

Ни одного порога и ни одного «если проблема, то запретить» в
`src/self-check.mjs` нет. Это не обещание, а проверяемое утверждение: тест
*«решение принимает модель FTS: изменение порога в .fts меняет вердикт»*
подставляет во временный каталог копию `admission.fts`, в которой порог
`больше 0` заменён на `больше 5`, и требует, чтобы на **том же самом IR** и с
тем же JavaScript вердикт изменился с «сборка запрещена» на «проект допущен».
Тест дополнительно проверяет, что факты при этом остались прежними: изменилось
именно решение, а не данные. Если однажды порог переедет в мост, тест покраснеет.

Отчёт о причинах блокировки тоже не дублирует правила. Чтобы назвать факт,
давший блокировку, мост спрашивает ту же модель: подставляет факты, в которых
обнулено всё, кроме одного счётчика, и смотрит, что вернёт FTS. Удалённое из
`.fts` правило автоматически перестаёт появляться в отчёте.

## Почему полный self-hosting сегодня невозможен

Это не осторожная формулировка, а вывод из устройства ядра
(`docs/language.md`, `src/model.ts`, `src/utility.ts`):

1. **Строк как данных нет.** `является строкой` — это *тип поля*. Значение
   строки можно сравнить на равенство (`eq`, `neq`), и на этом всё: в языке нет
   длины, среза, символа по индексу, конкатенации и упорядоченного сравнения
   строк (`compare` требует чисел для `gt`/`lt`/`gte`/`lte`). Лексер, который
   обязан читать исходник посимвольно, написать не на чем.
2. **Коллекций нет.** Вход утилиты — `Record<string, FtsScalar>`, плоская
   запись скаляров. Ни списка, ни отображения, ни итерации по ним. Дерево
   разбора представлять нечем.
3. **Рекурсии и вызова утилиты из утилиты нет.** Операнды правила исчерпываются
   четырьмя видами: литерал, поле, результат, процент от поля. Вызвать другую
   утилиту нельзя даже без рекурсии. Разбор вложенных конструкций невыразим.
4. **Ввода-вывода нет и не планируется.** Это осознанное свойство: FTS печатает
   типы, чистые функции и точки, куда приложение подставляет свои эффекты
   (SPEC.md, вступление). Компилятор обязан читать файлы — значит, фронтенд
   остаётся на языке хозяина.
5. **Динамических структур нет.** Утилита начинает со скаляра и возвращает
   скаляр; накопить в ней таблицу символов невозможно.

Поэтому на FTS выражена та часть, которая является **чистым решением по уже
добытым фактам**. Это не декоративный bootstrap: решение действительно
принимается моделью, и это доказано тестом. Но это и не «компилятор FTS на
FTS» — называть его так было бы неправдой.

## Что нужно добавить в язык, чтобы граница сдвинулась

Список отсортирован по отношению «польза для компилятора / ущерб для языка».

| Возможность | Что даст компилятору | Оценка |
|---|---|---|
| **Свёртка по коллекции** (`для каждого ... суммировать`) над списком однотипных объектов | Сумму блокирующих проблем по модулям считал бы FTS, а не мост. Сегодня это единственное арифметическое действие, которое пришлось отдать JavaScript. | **Нужно.** Свёртка по конечным данным остаётся тотальной и завершающейся, то есть примеры-тесты и свойства-постусловия продолжают работать. Наибольшая польза при наименьшем ущербе. |
| **Вызов утилиты из утилиты** (ациклический, без рекурсии) | Правила допуска собирались бы из именованных частей вместо плоского списка; метамодель могла бы переиспользовать «Посчитать элементы модуля». | **Нужно.** Дёшево, проверяется статически (запрет циклов), тотальность не страдает. |
| **Результат-объект вместо скаляра** | Утилита возвращала бы вердикт вместе с причиной, и мост перестал бы декодировать 1 и 0. | **Полезно.** Затрагивает восемь бэкендов кодогенерации — цена заметная. |
| **Несколько теорем в документе** (сейчас `FTS_MULTIPLE_PROPOSITIONS`) | Модуль допуска мог бы доказывать несколько утверждений о себе. | **Полезно, но не срочно.** К допуску отношения не имеет. |
| **Строки как данные** (длина, срез, символ, конкатенация) | Лексер на FTS. | **Не нужно.** Ради одной задачи язык превратился бы в универсальный, и исчезло бы главное свойство: любую модель можно целиком проверить примерами и напечатать на восьми целевых языках. |
| **Рекурсия** | Парсер вложенных конструкций на FTS. | **Не нужно и вредно.** Тотальность — то, что делает «свойство» постусловием, а «пример» тестом. Ограниченных свёрток компилятору достаточно. |
| **Ввод-вывод** | Чтение `.fts` из самого FTS. | **Не нужно никогда.** Это прямо противоречит объявленной границе честности языка. |

Вывод: сдвинуть границу стоит ровно на два пункта — свёртки и вызов утилиты из
утилиты. После них решением модели станет и сумма по проекту, а JavaScript
останется тем, чем и должен быть: фронтендом, который читает файлы и добывает
факты.

## Метамодель

`meta.fts` описывает форму IR (SPEC.md, раздел 4) объектами «Модуль»,
«Категория», «Объект», «Утилита», «Правило», «Пример». Поля — только числа и
признаки: метамодель говорит «сколько» и «есть ли», но не «как называется»,
потому что имён как данных в языке нет.

Примеры утилит метамодели — не выдумка: `«Модуль скидки» → 7 объявлений`
соответствует фикстуре `test/fixtures/discount.ir.json`, а `«Модуль отгрузки»`
— `shipment.ir.json`. Метамодель проверяется теми же фикстурами, на которых
работает компилятор.

## Правила допуска

`admission.fts` — категория «Допуск к сборке» с тремя объектами фактов и тремя
утилитами. Каждое поле фактов — счётчик проблем: ноль означает «в порядке».
Каждое правило читает ровно одно поле — именно поэтому мост умеет спросить
модель о причине блокировки, не повторяя решение на JavaScript.

Блокирует сборку:

- утилита без единого примера;
- пример, который не сходится (включая нарушение свойства);
- поле объекта без типа;
- объект, который нужен функтору проекта, но не перечислен в `экспортирует`;
- функтор, ссылающийся на несуществующую категорию;
- объект домена без образа, образ вне кодомена, поле без образа;
- морфизм, образа которого нет в категории-кодомене;
- проект без единого модуля.

Не блокирует: модуль без утилит. Описание данных, морфизмов и теоремы —
законный модуль, а не незавершённая работа; фикстура `shipment` именно такова.
