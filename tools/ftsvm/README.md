# ftsvm — исполнитель программ FTS с JIT

`ftsvm` исполняет утилиты FTS по IR компилятора `ftsc` двумя способами:
интерпретацией и компиляцией в JavaScript в рантайме. Рядом лежит
`tools/ftsc/stdlib/supervision` — политики отказоустойчивости, выраженные
моделями FTS: то, что в Erlang/OTP зашито в код супервизора.

## Сначала — рамка, и её не надо размывать

Это **не** альтернатива BEAM и не шаг к ней.

BEAM — это вытесняющий планировщик, изоляция процессов, куча и сборщик мусора
на каждый процесс, ссылки и мониторы, почтовые ящики, супервизоры, горячая
замена кода, распределённость. Всё перечисленное — управление **эффектами и
временем**.

В FTS нет ни того, ни другого, и это видно из языка, а не из общих
соображений (`docs/rukovodstvo/language.ru.md`, `src/natural-parser.ts`, `src/utility.ts`):

- значения — только скаляры: строка, число, дата, деньги, признак, состояние
  (`docs/rukovodstvo/language.ru.md`, «Значения» и таблица встроенных форм). Коллекций нет;
- строка есть тип, но не данные, которыми можно оперировать: над строками
  доступны только `равен`/`не равен`, ни конкатенации, ни длины, ни разбора;
- утилита состоит из `принимает / возвращает / начинает с / правило / свойство
  / пример` — и всё (`parseUtility` в `natural-parser.ts`). Нет циклов, нет
  вызова одной утилиты из другой, нет рекурсии;
- правило — это одно условие над **плоскими полями одного объекта** и одно
  действие `добавить` или `результат равен`. Обращения к другому объекту,
  к вложенному объекту или к списку в правиле выразить нечем;
- ввода-вывода, времени, параллелизма в языке нет вовсе: `executeUtility` —
  чистая функция от документа и входа.

Виртуальную машину на FTS написать нельзя — не хватает даже байтового массива,
чтобы хранить состояние. Утверждать обратное было бы враньём.

Что можно и что действительно полезно:

1. **быстрый исполнитель** чистых правил FTS — он ускоряет и песочницу,
   и сервисы, которые считают правила на каждом запросе;
2. **политики отказоустойчивости, выраженные на FTS** — стратегия перезапуска,
   бюджет рестартов, эскалация, выдержка. Это чистые решения по фактам,
   идеальный случай для FTS. Выполняет решения всё равно рантайм.

Итог: ftsvm — исполнитель плюс проверяемые политики надёжности. Ни один
процесс здесь не запускается, не убивается и не перезапускается.

## Что внутри

```
tools/ftsvm/
  src/errors.mjs        диагностики: коды и тексты совпадают с ядром
  src/program.mjs       навигация по IR и проверка входа
  src/interpreter.mjs   исполнение прямо по IR, шаг за шагом
  src/jit.mjs           генерация JS + new Function + кэш
  src/load-fts.mjs      .fts → IR (только для тестов и бенчмарка)
  src/index.mjs         публичная поверхность
  bin/ftsvm.mjs         CLI: list / run / bench
  bench.mjs             ядро / интерпретатор / JIT
  test/*.test.mjs       эквивалентность, свойства, supervision, бенчмарк
```

Внешних зависимостей нет. Компилятор ядра (`dist/src/index.js`, собирается
`npm run build`) нужен только `load-fts.mjs`, CLI, тестам и бенчмарку; сам
исполнитель работает с готовым IR и о `.fts` ничего не знает.

```js
import { run, compileUtility, listUtilities } from './tools/ftsvm/src/index.mjs';

run(program, 'Продажи', 'Рассчитать скидку', { сумма: 20000, 'постоянный клиент': true });
// 3000

const скидка = compileUtility(program, 'Продажи', 'Рассчитать скидку');
скидка({ сумма: 20000, 'постоянный клиент': true }); // 3000
```

Всё запускается из корня репозитория; ядро должно быть собрано (`npm run build`).

```bash
npm run test:ftsvm                            # тесты исполнителя
npm run benchmark:ftsvm                       # полный прогон, 10³–10⁵ вызовов

node tools/ftsvm/bin/ftsvm.mjs bench --quick  # короткий прогон
node tools/ftsvm/bin/ftsvm.mjs bench --json   # машинный отчёт
node tools/ftsvm/bin/ftsvm.mjs list tools/ftsc/stdlib/supervision/supervision.fts
node tools/ftsvm/bin/ftsvm.mjs run tools/ftsc/stdlib/supervision/supervision.fts \
  --utility «Решение о перезапуске» --input процесс.json
```

CLI держит тот же контракт вывода, что ядро, `ftsc` и `ftspec`: результат — JSON
в stdout, диагностики — в stderr, ненулевой код возврата при ошибке.

## Интерпретатор

`run(program, module, utility, input)` находит утилиту в IR, проверяет вход и
исполняет правила, обходя структуру данных на каждый вызов: массив правил →
массив условий → объект-операнд, по полю `kind` которого ветвится `switch`.

Семантика — ровно ядерная, и это не пожелание, а то, что проверяет тест:

- выполняются **все** правила с истинным условием, в порядке объявления;
  никакого `else`, никакого выхода после первого срабатывания;
- условия одного правила соединены «и» с коротким замыканием — как `every`
  в ядре: второе условие не вычисляется, если первое ложно;
- свойства проверяются **после** всех правил. Нарушение — ошибка
  `FTS_UTILITY_PROPERTY`, а не «поправить результат до допустимого».
  Свойство здесь постусловие, а не корректор;
- `равен`/`не равен` сравниваются через `Object.is`, а не `===`: иначе `0`
  и `-0` слились бы, а `NaN` не был бы равен сам себе — и три движка
  разошлись бы ровно там, где это труднее всего заметить.

Интерпретатор полезен там, где утилиту вызывают один раз (проверка примеров
при сборке, разовый расчёт в CLI): у него нет фазы компиляции. И он служит
эталоном, с которым сверяется сгенерированный код.

## JIT

`compileUtility(program, module, utility)` собирает исходник функции из правил
и создаёт её через `new Function`, возвращая замыкание `(input) => результат`.
Результат кэшируется по паре «модуль + утилита» в `WeakMap`, ключом которого
служит сама программа: отпустил программу — освободился и кэш.

Что именно даёт выигрыш:

1. **Обхода IR не остаётся.** Вся работа, зависящая только от программы —
   разбор операндов, ветвление по `kind`, поиск утилиты в документе, — сделана
   один раз при компиляции. В горячем пути остаётся линейная цепочка `if`.
2. **Специализация по типам.** Из объявления структуры известно, что поле
   «сумма» имеет тип «Деньги», а вход уже проверен — значит там конечное
   число. Поэтому сравнение печатается как `f0 >= 10000`, а не как вызов
   общего `compare`, обязанного проверять типы. Там, где тип доказать нельзя
   (необязательное поле, поле чужого типа, результат неопределённого типа),
   печатается вызов помощника с **той же** проверкой и той же диагностикой,
   что в ядре. Специализация убирает заведомо лишние проверки и не имеет
   права менять поведение.
3. **Обязательные поля читаются один раз** в локальные переменные: после
   проверки входа они гарантированно на месте, дальше это доступ к слоту,
   а не поиск свойства.
4. **`Object.is` заменяется на `===`,** только когда хотя бы одна сторона
   доказуемо не число. Это тождество, а не догадка: `Object.is` отличается
   от `===` исключительно на `NaN` и `±0`.

Так выглядит результат для `discount` (`sourceOf` печатает его целиком):

```js
"use strict";
const { field, percent, cmp, add, fail, missing, badType, extra } = rt;
const { allowed, structureName, utilityName } = meta;
/* утилита «Рассчитать скидку» из объекта «Покупка» */
return function ftsvmCompiled(input) {
  /* проверка входа */
  if (!("сумма" in input)) missing("сумма");
  const f0 = input["сумма"];
  if (typeof f0 !== "number" || !Number.isFinite(f0) || Object.is(f0, -0)) badType("сумма", "Деньги");
  if (!("постоянный клиент" in input)) missing("постоянный клиент");
  const f1 = input["постоянный клиент"];
  if (typeof f1 !== "boolean") badType("постоянный клиент", "Признак");
  for (const key of Object.keys(input)) if (!allowed.has(key)) extra(structureName, key);
  /* правила: выполняются все, у кого истинно условие */
  let result = 0;
  /* правило «Большая покупка» */
  if (f0 >= 10000) {
    result += ((10 / 100) * f0);
  }
  /* правило «Постоянный клиент» */
  if (f1 === true) {
    result += ((5 / 100) * f0);
  }
  /* свойства */
  if (!(result <= ((20 / 100) * f0))) fail("Скидка ограничена", utilityName);
  return result;
};
```

Проверка входа тоже развёрнута в прямой код — иначе JIT считал бы не то же
самое, что ядро, и сравнение движков было бы нечестным.

### Почему `new Function` здесь безопасен

Это единственное место во всём ftsvm, где код собирается в рантайме, и вход
у него — не пользовательская строка, а IR: разобранный и проверенный документ.
В позицию кода не попадает ни один фрагмент внешнего текста:

- имена полей и все скалярные литералы печатаются через `JSON.stringify`
  и дополнительно сверяются обратным разбором. Если строка не восстанавливается
  в исходное значение, генерация прекращается ошибкой `FTSVM_CODEGEN`, а не
  «как-нибудь» экранируется;
- имена правил, свойств и утилит попадают только внутрь строковых литералов
  сообщений — тем же путём; в комментариях они дополнительно чистятся от
  последовательности, закрывающей комментарий, и от переводов строк;
- операторы, порядок правил и структура кода берутся из фиксированных
  `switch`, а не из данных.

Иначе говоря, генератор печатает код по типизированному дереву, а не склеивает
строки от пользователя. **Если бы источником IR был непроверенный ввод, JIT
надо было бы выключать:** тогда `new Function` стал бы обычным `eval` над
чужими данными. Поэтому `load-fts.mjs` прогоняет `validate` и отказывается
собирать программу из документа, не прошедшего проверку.

## Эквивалентность — главное требование

Интерпретатор, JIT и ядро (`executeUtility`) обязаны давать одинаковый
результат на одинаковых входах, включая нарушения свойств и отказы по входу.
Проверяется это на детерминированных сетках, без random:

- `discount` — 65 входов: 13 значений суммы (границы правил, ноль,
  отрицательная, `-0`, `NaN`, `Infinity`, строка) × 5 значений признака
  (`true`, `false`, строка, число, `null`);
- `delivery` — 160 входов (декартово произведение по четырём полям, значения
  ровно на порогах правил) плюс чужие типы и испорченные входы;
- «непроверенный IR» — 5 утилит × 80 входов на документе, который намеренно
  **не** проходит `validate` (процент от признака, порядок на строке,
  сложение с признаком, чтение отсутствующего необязательного поля,
  удвоение результата с нарушением свойства). Он нужен, чтобы убедиться:
  где ядро ломается, там ломаются и оба движка ftsvm — тем же кодом
  и тем же текстом;
- испорченные входы строятся автоматически: из корректного входа удаляется
  каждое поле по очереди и добавляется постороннее.

Сравнивается не только значение, но и исход целиком: `{код диагностики,
текст}`. Тест требует, чтобы сетка задела все интересные отказы
(`FTS_UTILITY_ADD_TYPE`, `FTS_UTILITY_COMPARE_TYPE`, `FTS_UTILITY_INPUT`,
`FTS_UTILITY_PERCENT_TYPE`, `FTS_UTILITY_PROPERTY`) — иначе «совпало»
означало бы лишь, что ничего не проверили.

Отдельно проверено, что `shipment` — модель из морфизмов и теоремы, без единой
утилиты — не роняет исполнитель: `listUtilities` возвращает пустой список,
а попытка исполнить несуществующую утилиту даёт `FTS_UNKNOWN_UTILITY`.

## Бенчмарк

Методика взята из `examples/fts/benchmark/measure.mjs`, а не придумана заново:
прогрев перед замером, медиана по повторам (одна пауза GC тянет среднее на
себя, а медиану почти нет), p95 и min/max для разброса, окружение печатается
вместе с числами. Отличия два, оба вынужденные:

- размер батча задан условием задачи (10³, 10⁴, 10⁵ вызовов), а не подбирается
  под порог таймера;
- движки меряются **чередуясь**: повтор 1 — ядро, интерпретатор, JIT; повтор
  2 — снова все трое. Если мерить их подряд блоками, пауза GC или смена
  частоты процессора попадает целиком в один блок, и сравниваются моменты
  времени, а не движки.

Вход — цикл из четырёх наборов, иначе V8 вправе свернуть весь цикл в
константу. По всем вызовам считается контрольная сумма, и она обязана
совпасть у трёх движков — иначе сравнивать нечего.

Замер: node v24.18.0, linux/x64, AMD EPYC 9354 32-Core Processor, 8 ядер.
Цифры ниже — из одного прогона `node tools/ftsvm/bench.mjs`, не усреднённые
между прогонами.

| сценарий | правил | движок | нс/вызов (10⁵) | опс/с |
|---|---|---|---|---|
| discount / Рассчитать скидку | 2 | ядро | 1131.7 | 883 600 |
| discount / Рассчитать скидку | 2 | интерпретатор | 1197.3 | 835 231 |
| discount / Рассчитать скидку | 2 | **JIT** | **55.8** | **17 916 905** |
| delivery / Рассчитать доставку | 4 | ядро | 1240.5 | 806 131 |
| delivery / Рассчитать доставку | 4 | интерпретатор | 1502.8 | 665 420 |
| delivery / Рассчитать доставку | 4 | **JIT** | **94.7** | **10 563 961** |
| supervision / Рассчитать задержку | 9 | ядро | 1450.8 | 689 268 |
| supervision / Рассчитать задержку | 9 | интерпретатор | 1498.8 | 667 217 |
| supervision / Рассчитать задержку | 9 | **JIT** | **67.6** | **14 795 863** |

Ускорение на 10⁵ вызовах (тот же прогон):

| сценарий | JIT / ядро | JIT / интерпретатор | интерпретатор / ядро |
|---|---|---|---|
| discount | 20.28 | 21.45 | 0.95 |
| delivery | 13.10 | 15.88 | 0.83 |
| supervision | 21.47 | 22.18 | 0.97 |

Стоимость компиляции (генерация исходника + `new Function`, медиана):

| сценарий | правил | байт кода | мкс/компиляцию |
|---|---|---|---|
| discount | 2 | 1345 | 15.2 |
| delivery | 4 | 2043 | 17.9 |
| supervision | 9 | 4148 | 27.0 |

Что из этого следует честно читать:

- **JIT быстрее ядра на порядок.** Повторный прогон на той же машине дал
  13–29× вместо 13–21× — разброс между прогонами заметный, поэтому «в
  двадцать раз» здесь значит «на порядок», а не «в 20.28 раза».
- **Интерпретатор ядру не проигрывает и не выигрывает** (0.83–1.34 на 10⁵
  вызовах в двух прогонах). Так и должно быть: он делает ту же работу тем же
  способом — обход IR на каждый вызов, проверка входа, поиск утилиты.
  Заявлять его как достижение производительности нельзя — он нужен как
  эталон и как исполнитель без фазы компиляции.
- **Компиляция окупается за 15–30 вызовов** (27 мкс против экономии
  ~1.4 мкс на вызов для supervision). Для утилиты, которую вызывают один
  раз, JIT бессмысленен; для правил на каждом HTTP-запросе — окупается
  на первой же секунде.
- **Батчи по 10³ вызовов ненадёжны** на этой машине: там медианы прыгают
  (от 4× до 58× в разных прогонах), потому что один батч длится доли
  миллисекунды и любая пауза сдвигает его целиком. Верить стоит строке 10⁵.

## Политики надёжности на FTS

`tools/ftsc/stdlib/supervision/supervision.fts` — категория «Надзор»:
объект «Наблюдаемый процесс» и три утилиты. Модель проходит `compile` →
`validate` (`valid: true`) → `testUtilities` (11 примеров из 11 сходятся),
и то же самое проверяется исполнением через ftsvm.

Объект — снимок фактов, снятый рантаймом на момент падения ребёнка:
`перезапусков за окно`, `лимит перезапусков`, `окно секунд`,
`секунд с первого перезапуска`, `критичный`, `номер попытки`,
`базовая задержка`, `потолок задержки`, а также необязательное состояние
`бюджет исчерпан`, к которому привязаны морфизмы эскалации.

**«Оценить бюджет рестартов»** → признак. Бюджет считается превышенным,
только если сами перезапуски уложились в окно: если с первого перезапуска
прошло больше `max_seconds`, счётчик рантайм обязан обнулить. Сравнение
строгое, как в OTP: интенсивность — число разрешённых рестартов, супервизор
падает на превышении, а не на достижении.

**«Решить о перезапуске»** → число. Строк как данных в языке нет, поэтому
решение кодируется числом — это ограничение языка, а не недосмотр модели:

| код | решение | аналог в OTP |
|---|---|---|
| 0 | перезапустить | обычный рестарт ребёнка |
| 1 | эскалировать | интенсивность превышена, супервизор падает сам |
| 2 | не перезапускать | `temporary`-ребёнок остаётся остановленным |

Правила исполняются все и по порядку: сначала общий случай (перезапустить),
затем частные, которые его перекрывают. Инварианты — «решение неотрицательно»
и «решение из известного множества» (не больше 2).

**«Рассчитать задержку перезапуска»** → число: экспоненциальная выдержка
`база × 2^(попытка−1)`, срезанная потолком. Умножения в языке нет, поэтому
удвоение выражено действием `то добавить результат` — это и есть `×2`,
а лестница из восьми правил задаёт показатель степени. Ограничение честное:
после восьмой попытки выдержка сама не растёт и держится потолком.
Инварианты: «задержка неотрицательна» и «задержка не превышает потолок».

Проверка `база = −100` показывает, что инвариант работает: все три движка
дают одну и ту же ошибку `FTS_UTILITY_PROPERTY` и **не** возвращают
исправленное значение.

### Какие стратегии Erlang выразимы, а какие нет

Разделять надо две вещи: **решение** («что полагается сделать с этим
ребёнком») и **квантор по детям** («к кому это применить»).

| стратегия OTP | решение | квантор | итог |
|---|---|---|---|
| `one_for_one` | выражается полностью | не нужен: один ребёнок — одно решение | **выразима** |
| `simple_one_for_one` | то же, что `one_for_one` | дети динамические, их список — коллекция | решение выразимо, состав детей — нет |
| `rest_for_one` | выражается, если рантайм передаст фактами «мой порядковый номер» и «номер упавшего»: правило `если «мой номер» не меньше поле «номер упавшего» то результат равен 0` | обход братьев — нет | **наполовину**: предикат да, перебор нет |
| `one_for_all` | тривиально («перезапустить всех») | обход братьев — нет | **наполовину** |

Причина ровно одна и она не обходится приёмами: **в FTS нет коллекций и нет
рекурсии**. Утилита принимает один объект с плоскими полями и возвращает один
скаляр. Ни «для каждого ребёнка», ни «поднимись на уровень выше по дереву»
записать нечем. Поэтому в FTS выражается предикат на одного ребёнка, а
перебор детей и обход дерева остаются рантайму — и это не временное
положение дел, а следствие устройства языка.

Не выражается вовсе:

- **само дерево супервизоров** — рекурсивная структура;
- **эскалация как процесс** («упал супервизор → его супервизор считает это
  падением ребёнка → …») — это обход дерева. Выражается лишь одно звено:
  решение «эскалировать» на текущем уровне;
- **`transient`** (перезапускать только при ненормальном завершении) — сам
  предикат выразим, стоит рантайму передать признак «завершился нормально»,
  но в текущей модели такого поля нет;
- **shutdown-таймауты, порядок остановки, `brutal_kill`** — это действия
  во времени, а не решения;
- **счётчики.** Модель не считает ни рестарты, ни секунды: и то и другое
  приходит фактами. Часы и память — снаружи.

## Связка: как политика исполняется ftsvm

Полностью — в `test/supervision.test.mjs`, тест «связка: факты о процессе →
решение → действие рантайма». Схема:

```js
const решить   = compileUtility(program, 'Надзор', 'Решить о перезапуске');
const задержка = compileUtility(program, 'Надзор', 'Рассчитать задержку перезапуска');

function надзор(факты) {                    // ← рантайм, не FTS
  switch (решить(факты)) {                  // ← чистое решение по фактам
    case 0: return запланировать_перезапуск(задержка(факты)); // ← эффект
    case 1: return эскалировать_супервизору();                 // ← эффект
    default: return оставить_остановленным();                  // ← эффект
  }
}
```

В тесте вместо эффектов — журнал: на пяти наборах фактов он получается
таким, и это проверяется точным сравнением.

| факты | решение | действие рантайма |
|---|---|---|
| 1 падение, лимит 3, попытка 1 | 0 | перезапустить через 100 мс |
| 2 падения, попытка 4 | 0 | перезапустить через 800 мс |
| 4 падения за 4 с при лимите 3, критичный | 1 | эскалировать |
| то же, некритичный | 2 | оставить остановленным |
| 9 падений, но окно истекло 600 с назад | 0 | перезапустить через 5000 мс (потолок) |

Граница проходит ровно по `switch`: до него — чистое решение, исполненное
ftsvm и одинаковое у интерпретатора и JIT (тест проверяет и это); после него —
эффект, которого в FTS нет. Сам перезапуск ftsvm не делает и делать не будет.

## Насколько это близко к BEAM

Не близко. Совпадает одна деталь: логика решения супервизора о рестарте —
и та не целиком, а без обхода дерева детей.

Если раскладывать по частям, то из того, что делает BEAM, здесь нет ничего:
ни процессов, ни планировщика, ни изоляции памяти, ни сборщика мусора на
процесс, ни ссылок и мониторов, ни почтовых ящиков, ни горячей замены кода,
ни распределённости. Есть чистые вычисления над скалярами и проверяемые
постусловия. ftsvm ускоряет эти вычисления примерно на порядок относительно
эталонного рантайма — это полезно для песочницы и сервисов, но к
отказоустойчивости отношения не имеет: отказоустойчивость создаётся
изоляцией и вытеснением, а их даёт ОС или BEAM, а не язык описания правил.

Ценность связки другая и её не надо подменять: политику перезапуска можно
записать так, что она **проверяема до запуска** — с инвариантами, примерами
и доказательством, что три независимых исполнителя понимают её одинаково.
В Erlang эта же политика живёт параметрами `#{intensity => 3, period => 5}`
и кодом супервизора, который тестируют вместе с эффектами. Заменить BEAM это
не может и не пытается; дополнить — может, если рантайм согласен спрашивать
решение снаружи.
