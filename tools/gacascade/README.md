# gacascade — каскад GA0 → GA1 → GA2

Реализация каскадного двухуровневого генетического алгоритма планирования
итерации по материалам диссертации: **GA2** ищет план назначений, **GA1**
выбирает конфигурацию поиска, **GA0** управляет вычислительным бюджетом и
ранней остановкой.

Смысл разделения — в том, что поиск допустимого плана, настройка параметров
поиска и управление бюджетом обычно смешаны в одном цикле. Смешанный цикл
работает, но по нему нельзя сказать, чему обязан результат: удачной
конфигурации, удачному лимиту поколений или самому поиску. Каскад разносит эти
три функции по уровням, и вклад каждого становится измеримым — что и делает
стенд эксперимента.

```bash
node tools/gacascade/bin/gacascade.mjs check
node tools/gacascade/bin/gacascade.mjs run --mode cascade --seed 42
node tools/gacascade/bin/gacascade.mjs experiment --runs 30 --out таблица.md
node --test tools/gacascade/test/*.test.mjs
```

Фактические результаты прогона — в [`results/experiment.md`](results/experiment.md),
полные данные — в `results/experiment.json`.

## 1. Устройство уровней

### GA2 — поиск плана (раздел 2.4.1)

Хромосома `A = (a_1,…,a_n)`: исполнитель каждой задачи. По ней
детерминированно строится расписание `S(X)` (топологический порядок
зависимостей, доступная ёмкость, оценки трудоёмкости) и вычисляется `J_p`.

Поколение: турнирная селекция, сохранение не менее двух лучших назначений,
масочный (либо одноточечный) кроссовер, мутация исполнителя. Начальная
популяция содержит случайные и конструктивные назначения: особь 0 — жадный
план, особь 1 — действующий план `X_0`, остальные случайны.

Число оценок растёт **ровно на размер новой популяции** за поколение. Это
делает бюджет сопоставимым между конфигурациями и не зависящим от
быстродействия среды и от удачливости кэша.

Файл: `src/ga2.mjs`.

### GA1 — выбор конфигурации (раздел 2.4.2)

Три заранее определённые конфигурации `θ = (N_pop, p_mut, p_cross)`:

| Конфигурация | `N_pop` | `p_mut` | `p_cross` |
| --- | ---: | ---: | ---: |
| `compact` | 32 | 0,06 | 0,80 |
| `balanced` | 48 | 0,10 | 0,82 |
| `exploratory` | 64 | 0,18 | 0,85 |

Каждой выделяется пилот: **не менее 128 оценок и около 8% общего бюджета**.
Выбор `θ* = argmin_θ J_p(X_pilot(θ))`, при равенстве — меньшая популяция.
Оставшийся бюджет уходит финальному GA2. Стоимость пилота входит в общий
`N_max` и не скрывается при сравнении.

Файл: `src/cascade.mjs`.

### GA0 — управление бюджетом (раздел 2.4.3)

После каждого поколения финального GA2 проверяется показатель готовности:

```
N* = min{ N ≤ N_max | c(N) ≥ c_min }
```

Если множество пусто, расчёт завершается при `N_max`. Пилотные оценки GA1
входят в `N*` — каскад не получает скрытого бюджета. Условие проверяется
только после заполнения окна устойчивости из пяти поколений.

Файлы: `src/readiness.mjs`, `src/budget.mjs`, `src/cascade.mjs`.

## 2. Модель и метрики

### Целевая функция

Вектор качества плана (раздел 2.3):

```
Q(X) = (Δ, T, B, R_ms, H)
Δ     = 0,70·V_skill + 0,30·V_over
J_p   = 0,45·Δ + 0,25·T + 0,15·B + 0,10·R_ms + 0,05·H
```

План допустим, если `V_skill = 0` и `V_over ≤ 0,05`.

**Свёртка записана на FTS** — `models/assignment.fts`, объект `Назначение` и
три утилиты: `Штраф ограничений` (Δ), `Оценить назначение` (J_p),
`Назначение допустимо` (признак). Модель компилируется, проходит `validate` и
15 примеров; примеры прогоняются перед каждым поиском, а не по флагу.

Граница проведена так: расписание и компоненты `Q` считаются в JS
(`src/plan.mjs`), а веса скаляризации и коэффициенты штрафа живут в модели
FTS. Причина — в разделе 2.3: веса и коэффициенты фиксируются в протоколе,
то есть являются предметом договорённости и обязаны быть читаемыми и
проверяемыми примерами. Топологическая сортировка — обычный алгоритм,
доказывать её примерами незачем. Вектор переменной длины в объекте FTS
выразить нечем: объект состоит из скалярных полей.

Компоненты передаются в FTS **целыми числами в десятитысячных долях**
(0…10000). Примеры FTS сравниваются через `Object.is`, то есть побитово, и
дробные входы сделали бы их зависимыми от последней цифры мантиссы.

### Метрики эксперимента

| Обозначение | Что это | Направление |
| --- | --- | --- |
| `c` | вычислительная готовность рекомендации | больше — лучше |
| `τ` | фактическое время расчёта, мс | меньше — лучше |
| `σ` | нормированная дисперсия загрузки исполнителей | меньше — лучше |
| `Δ` | штраф нарушений компетенций и ёмкости | меньше — лучше |
| `J_p` | итоговый функционал | меньше — лучше |
| `N` | число оценок целевой функции | меньше — лучше |

Показатель готовности (разделы 2.3 и 3.3.1):

```
c = clip[0,1]( 0,25·C + 0,35·S + 0,30·I + 0,10·Q_s )
C = 1 − Δ
I = clip( (J_p(X_0) − J_p(X_t)) / max(0,02; 0,25·|J_p(X_0)|) )
S = 1 − clip( (max W_t − min W_t) / (0,02 + 0,15·|W̄_t|) ),  |W_t| = 5
```

`c_min` даёт только право ранней остановки: он не гарантирует оптимальности и
не означает допустимости плана.

## 3. Сравниваемые режимы

| Режим CLI | Обозначение | Поиск | Выбор параметров | Ранняя остановка |
| --- | --- | --- | --- | --- |
| `heuristic` | `greedy` | конструктивный | нет | нет |
| `single` | `ga_single` | GA2 | фиксированная `balanced` | нет |
| `two-level` | `ga1_ga2` | GA2 | пилот GA1 | нет |
| `cascade` | `ga0_ga1_ga2` | GA2 | пилот GA1 | по `c_min` |

Все эволюционные режимы имеют одинаковый `N_max`.

### Условие честности сравнения

Корневой поток случайности форкается от строки `"прогон"`, **без имени
режима**. Следствие: `cascade` — это в точности `two-level`, оборванный
правилом `c ≥ c_min`; до момента остановки обе траектории совпадают до бита.
А когда GA1 выбирает `balanced`, финальный GA2 двухуровневого режима идёт по
тому же потоку, что одноуровневый, отличаясь только доступным бюджетом.

Если бы поток зависел от имени режима, разница в таблице складывалась бы из
вклада уровня и из вклада другого жребия, и разделить их было бы нечем.
Проверяется тестом «каскад — это двухуровневый режим, оборванный правилом
c ≥ c_min».

## 4. Что переиспользовано из `tools/gasearch`

Импортируется, не копируется:

| Что | Откуда | Зачем |
| --- | --- | --- |
| `createStream` — PRNG с именованными подпотоками | `src/random.mjs` | воспроизводимость, не зависящая от порядка вычислений |
| `tournamentSelection`, `better`, `rankPopulation` | `src/operators.mjs` | отбор по минимальному `J_p` |
| `CROSSOVERS` (одноточечный, равномерный) | `src/operators.mjs` | «одноточечный или масочный кроссовер» раздела 2.4.1 |
| `randomIndividual`, `cloneIndividual`, `individualKey` | `src/population.mjs` | популяция и ключ кэша |
| `createEvaluator` — мост к утилите FTS | `src/fitness.mjs` | обработка нарушенных свойств и диагностик |

Дисциплина имён потоков скопирована из `gasearch/src/evolve.mjs` дословно:

```
корень
  └ "начальная популяция" ─ "особь:i"
  └ "поколение:g"
       └ "пара:j"
            ├ "родитель:1" / "родитель:2"
            ├ "кроссовер"
            └ "мутация:1" / "мутация:2"
```

**Что не переиспользовано и почему.**

*Мутация.* В `gasearch` числовой ген мутируется гауссовым сдвигом с зажимом в
границы — это верно для «размера пула» и «таймаута», где соседние значения
близки по смыслу. Номер исполнителя — величина **номинальная**: исполнитель 3
не находится «между» исполнителями 2 и 4, и гауссов сдвиг означал бы
выдуманное отношение соседства. Автор пишет «мутация исполнителя», то есть
замена на другого исполнителя; она реализована в `src/ga2.mjs` с той же
дисциплиной потоков.

*Цикл `evolve`.* В `gasearch` останов бывает только по числу поколений или по
стагнации. GA2 обязан останавливаться по исчерпанию **бюджета оценок** и
допускать вмешательство GA0 после каждого поколения.

*Режим `admissibility` у `createEvaluator`.* Он схлопнул бы все недопустимые
планы в одну константу и уничтожил градиент штрафа: поиск перестал бы
отличать план с одним нарушением компетенций от плана с двадцатью. Раздел 2.3
требует обратного — поиск идёт по множеству `X⁺`, включающему почти
допустимые назначения, а недопустимость наказывается величиной Δ внутри
`J_p`. Допустимость здесь — признак для отчёта, а не фильтр отбора.

## 5. Расхождения между редакциями и достройки

Задание требует брать редакцию `4.0`. Расхождения, которые пришлось разрешать:

**5.1. `σ` против `B`.** Файл `4.0/04-chapter3-experiment-plan.md` в списке
метрик называет дисперсию загрузки `σ`; финальная редакция главы 2
(`4.0/chapter2-03-multiobjective-model.md`) обозначает ту же величину `B` в
векторе `Q = (Δ, T, B, R_ms, H)`. Это одна величина — нормированная дисперсия
загрузок. В коде поле называется «дисбаланс загрузки», в отчётах сохранено
обозначение задания `σ`.

**5.2. Repair-процедуры.** Черновик `4.0/03-chapter2-model-plan.md` описывает
у GA2 repair-оператор («восстановление ресурсных и зависимостных
ограничений») и хромосому `z = (A, π, ρ)` из трёх частей: матрица назначений,
порядок обработки задач, локальные приоритеты. Финальная редакция
`4.0/chapter2-04-cascade-ga.md` от обоих отказалась: хромосома там —
`A = (a_1,…,a_n)`, а поколение состоит из «турнирной селекции, сохранения
элиты, одноточечного или масочного кроссовера и мутации исполнителя», без
repair. **Реализована финальная редакция.** Порядок обработки задач задан
топологически и детерминирован, локальные приоритеты не вводились.

**5.3. Параметрический вектор GA1.** Черновик `03-chapter2-model-plan.md`
предлагает GA1, оптимизирующий вектор из десяти величин
`θ = (N_pop, g_max, p_cross, p_mut, ρ_1..ρ_3, ω_1..ω_4)` с учётом стоимости
`μ·C(θ)`. Финальная редакция сузила задачу до **выбора из трёх заранее
заданных конфигураций** `θ = (N_pop, p_mut, p_cross)` по минимальному
наблюдаемому `J_p`. Реализована финальная редакция. Веса `ω_k` и коэффициенты
штрафа `ρ_i` в основной серии фиксированы и одинаковы у всех режимов
(раздел 2.3), поэтому настраивать их означало бы менять целевую функцию между
сравниваемыми режимами.

**5.4. Статистический критерий.** `04-chapter3-experiment-plan.md` и задание
называют Манна — Уитни или Уилкоксона при α = 0,05. Финальная редакция
`4.0/chapter3-03-experiment-methodology.md` (раздел 3.3.2) предписывает более
строгую процедуру: **парный рандомизационный sign-flip тест** с bootstrap-
интервалами и поправкой Холма. Реализованы Уилкоксон (ведущий, выборки
связанные) и Манна — Уитни (рядом, как несвязанная оценка), плюс поправка
Холма и bootstrap-интервалы. Sign-flip тест **не реализован** — см. раздел 7.

**5.5. Число сравниваемых режимов.** Раздел 2.4.4 перечисляет шесть режимов:
`greedy`, `random_repair`, `ga_single`, `ga1_ga2`, `ga0_ga1_ga2`, `nsga2`.
Задание называет четыре. Реализованы четыре; `random_repair` и `nsga2` — см.
раздел 7.

**5.6. Что возвращает двухуровневый режим.** Раздел 2.4.2 говорит:
«Оставшийся бюджет используется для финального запуска выбранного GA2»;
раздел 2.4.5, шаг 6: «Вернуть лучшее назначение». Неясно, лучшее за финальный
запуск или за весь прогон, включая пилоты. **Реализованы оба**: в протоколе
есть и `J_p финала`, и `J_p` (лучшее за прогон). Головным взято второе —
система, увидевшая хороший план на пилоте, не имеет права его забыть, — но
оба числа лежат в JSON, и таблицу можно перестроить по любому из них.

**5.7. Достройка: нормировка `Q_s`.** Для компонент `C`, `I` и `S` формулы
выписаны в тексте полностью. Для `Q_s` сказано только «отделимость лучшего
значения от медианы популяции», без нормировки. Взята та же форма, что у `S`:

```
Q_s = clip( (J_p^med − J_p^best) / (0,02 + 0,15·|J_p^med|) )
```

Это **достройка, а не цитата**. Вес `Q_s` равен 0,10 — наименьший из
четырёх, — но при другой нормировке момент ранней остановки сдвинется.

**5.8. Достройка: готовность конструктивной эвристики.** У `greedy` нет ни
траектории, ни популяции: компоненты `S`, `I`, `Q_s` не определены в
принципе. Возвращается `c = 0,25·(1 − Δ) ≤ 0,25`. Это **дефиниционное
следствие**, а не результат соревнования: `c` описывает состояние поиска, а
поиска у эвристики нет. Сравнивать эвристику с эволюционными режимами по `c`
бессмысленно; по `J_p`, `Δ`, `σ` и `τ` — осмысленно.

## 6. Данные

Сценарии **синтетические**. Раздел 3.3 диссертации фиксирует это прямо: цель
эксперимента — проверить свойства модели и алгоритма, а не заявить
промышленную экономию. Ни один вывод, полученный на этих сценариях, не
переносится на реальный проектный контур; для утверждения о промышленном
эффекте нужен отдельный акт внедрения.

Классы и размерности — из таблицы раздела 3.3.1:

| Размер | Задачи `n` | Исполнители `M` | Изм. приоритета | Изм. ёмкости | Ошибка трудоёмкости | Ошибка компетенций |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| S | 30 | 5 | 0,20 | 0,10 | 0,10 | 0,05 |
| M | 100 | 10 | 0,30 | 0,15 | 0,20 | 0,10 |
| L | 200 | 20 | 0,40 | 0,20 | 0,30 | 0,15 |

Плотность зависимостей: 0,10 для `dense_dependencies`, 0,04 для
`priority_changes` и `noisy_inputs`.

Возмущение применяется **после** назначения сроков по опорному расписанию:
сценарий описывает состояние контура уже после изменения, когда действующий
план перестал соответствовать обстановке. Если возмущать до расчёта сроков,
получится просто другой случайный экземпляр, а не задача перепланирования.

## 7. Фактические результаты

Прогон: 30 повторов × 3 класса × 3 размерности × 4 режима = 1080 запусков,
`N_max = 1200`, `c_min = 0,85`, seed 1…30. Полные таблицы —
[`results/experiment.md`](results/experiment.md).

**Параметры не подбирались под результат.** Значения `N_max = 1200`,
`c_min = 0,85`, три конфигурации GA1, доля пилота 0,08 и минимум 128 оценок
взяты из диссертации. Параметры генерации сценариев (запас ёмкости 1,15,
разброс сроков 0,9…1,4, `K = 4` компетенции, трудоёмкость 1…10, приоритет
1…5) выбраны один раз до первого прогона и после получения чисел не
менялись. Серия прогонялась один раз; отбора «лучшего из нескольких
прогонов» не было.

### 7.1. Что совпало с ожиданиями автора

**Каскад лучше одноуровневого ГА по `J_p` — в 9 группах из 9** по медиане;
различие значимо в 8 из 9 (кроме `noisy_inputs/S`, p = 0,217). Размер эффекта
Клиффа от −0,089 до −0,397: от пренебрежимого до среднего.

**GA0 экономит бюджет почти даром.** Среднее число оценок 1060 против 1184 у
двухуровневого режима — экономия 10,5%, от 4,9% (`dense_dependencies/L`) до
23,7% (`noisy_inputs/S`). Цена по качеству: медиана `J_p` совпадает в 4
группах из 9, в остальных пяти каскад хуже с размером эффекта Клиффа не более
0,129 (пренебрежимый). Ранняя остановка срабатывала от 4 до 23 раз из 30.

**`c` у каскада выше, чем у одноуровневого**, значимо в 7 группах из 9.

### 7.2. Что не совпало

**Главный отрицательный результат: доля допустимых планов.**

| Режим | Доля допустимых, среднее по 9 группам | Диапазон |
| --- | ---: | --- |
| `heuristic` | 88,5 % | 63,3…100 % |
| `single` | 57,4 % | 30,0…76,7 % |
| `two-level` | 34,8 % | 16,7…63,3 % |
| `cascade` | 34,8 % | 16,7…63,3 % |

**Чем лучше поиск, тем реже план допустим.** Это не артефакт реализации, а
следствие устройства самой модели раздела 2.3. Допустимость требует
`V_skill = 0` — жёсткий ноль, ступенька. А в `J_p` компетенции входят
линейно с эффективным весом `0,45 · 0,70 = 0,315`, тогда как просрочка `T`
несёт вес 0,25. На `dense_dependencies/M` средние компоненты таковы:

| Режим | `V_skill` | `T` | Доля допустимых |
| --- | ---: | ---: | ---: |
| `heuristic` | 0,000 | 0,102 | 93,3 % |
| `single` | 0,011 | 0,078 | 60,0 % |
| `cascade` | 0,027 | 0,047 | 20,0 % |

Обмен выгоден по `J_p`: 0,315 · 0,027 ≈ 0,009 проигрыша против
0,25 · (0,102 − 0,047) ≈ 0,014 выигрыша. И он же катастрофичен для предиката
допустимости, которому достаточно одного нарушения. **Скаляризация `J_p` и
определение допустимости в модели рассогласованы**, и каскад, будучи более
сильным оптимизатором `J_p`, страдает от этого сильнее прочих.

Практический вывод для текста диссертации: пункт 1 шаблона выводов раздела 3.5
(«каскад достиг порога… что на X п.п. выше базового ГА») на этом стенде
подтверждается по `c` и по `J_p`, но **не подтверждается по доле допустимых
решений** — там каскад проигрывает и одноуровневому ГА, и жадной эвристике.
Возможные направления: вынести `V_skill` из скаляризации в жёсткое
ограничение, ввести repair-оператор (он был в черновике `03-chapter2-model-plan.md`
и исчез в финальной редакции — см. п. 5.2), либо поднять вес компетенций
настолько, чтобы обмен перестал быть выгодным.

**Вклад GA1 сводится к выбору размера популяции.** Пилот выбрал `compact` в
265 запусках из 270. Причина — в самом правиле раздела 2.4.2: пилот меряется
в ОЦЕНКАХ, а не в поколениях. При 128 оценках `compact` (N_pop = 32) успевает
4 поколения, `balanced` (48) — 2, `exploratory` (64) — 2. Пилот
систематически предпочитает меньшую популяцию, потому что при равном бюджете
оценок она успевает больше поколений, а не потому, что она лучше на дистанции.
Практически весь выигрыш `two-level` над `single` в этой серии — это разница
между `N_pop = 32` и `N_pop = 48`, которую дала бы и просто другая
фиксированная конфигурация.

**`Δ` у каскада не лучше, чем у эвристики** — на `dense_dependencies/S`
медиана 0,0068 против 0,0032 у `greedy`, различие значимо в пользу эвристики.
Та же причина, что и у доли допустимых.

### 7.3. Как читать сравнение `cascade` против `two-level`

В большинстве пар прогонов эти режимы дают **побитово одинаковый** результат:
GA0 либо не сработал, либо сработал, не изменив чемпиона. Критерий Уилкоксона
отбрасывает нулевые разности, поэтому он отвечает на вопрос «среди тех
прогонов, где ранняя остановка что-то изменила, изменила ли она в худшую
сторону» — и на части групп даёт формально значимое p при пренебрежимом
размере эффекта. Число отброшенных нулевых разностей есть в JSON
(`нулевых разностей`); без него p-value этой строки читать нельзя.

## 8. Что из методики не реализовано

Перечислено полностью, чтобы объём проверенного не путался с объёмом
описанного.

1. **NSGA-II и недоминируемый архив** (раздел 2.4.4). Шестой режим сравнения,
   оптимизирующий вектор `(Δ, T, B, H)` напрямую. Не реализован: задание
   называет четыре режима.
2. **`random_repair`** (раздел 2.4.4) — случайное допустимое назначение с
   repair. Не реализован по той же причине.
3. **Парный рандомизационный sign-flip тест** (раздел 3.3.2). Вместо него —
   Уилкоксон и Манна — Уитни, как их называет задание и
   `04-chapter3-experiment-plan.md`.
4. **Контрольные серии раздела 3.3.3**: точный перебор малых экземпляров и
   разрыв с оптимумом; гиперобъём фронта; независимая калибровка с отложенной
   проверкой; чувствительность к четырём значениям `c_min` и 70 векторам
   весов; серия динамического перепланирования; расхождение наблюдаемых и
   истинных характеристик; масштабируемость при `n = 20…300`; повтор по
   сохранённым manifest-файлам.
5. **Внешняя проверка графового слоя на архиве Apache Jira** (раздел 3.3.3,
   пункт 9) и **весь графовый слой** `G_t = (V_t, E_t, W_t, Ξ_t)` раздела 2.2:
   `sim_sem`, `sim_ctx`, `sim_time`, векторизация текстовых полей. Каскад
   работает с уже сформированным описанием задач и исполнителей.
6. **Командное назначение** `Σ_m x_jm ∈ {0,…,r_j^max}` (раздел 2.1). Раздел
   сам оговаривает, что в экспериментальном ядре остаётся один основной режим.
7. **Анализ чувствительности** к размеру популяции, `p_mut`, `p_cross` и весам
   критериев (раздел 3.3, таблица параметров). Стенд принимает эти величины
   параметрами CLI, но серия чувствительности не оформлена.
8. **Графики** (раздел 3.4, не менее восьми). Стенд отдаёт JSON, из которого
   они строятся, но сам их не рисует.
9. **Наблюдаемые против истинных характеристик.** Сценарий класса
   `noisy_inputs` искажает данные, и `J_p` считается по наблюдаемым величинам,
   как требует раздел 3.3.1. Отдельного расчёта по истинным величинам и
   сравнения с наблюдаемыми нет.
