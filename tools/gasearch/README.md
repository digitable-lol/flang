# gasearch — эволюционный поиск с фитнес-функцией на FTS

`gasearch` — генетический алгоритм, у которого фитнес-функция и ограничения
записаны не в коде движка, а как исполняемая утилита FTS: с примерами-тестами,
свойствами-инвариантами и проверкой `validate` до старта поиска.

Оркестрация эволюции (популяция, поколения, отбор) — обычный JavaScript. FTS
отвечает ровно за то, что можно и нужно проверить: чего стоит особь и допустима
ли она вообще.

## Чем это отличается от обычного ГА

У классической реализации ГА две болезни, и обе лечатся здесь одним и тем же
приёмом — вынести проверяемое в проверяемый формат.

**Фитнес-функцию никто не читал.** Обычно она закопана в коде поиска, живёт
в одной функции с нормализацией, штрафами и парой магических констант, и
единственный способ узнать, что именно оптимизировалось, — прочитать эту
функцию глазами. Здесь фитнес — это `.fts`-модель:

```fts
правило «Дневной спрос закрыт»
  если «смен днём» не меньше 8
  то добавить 120

свойство «Вариант не убыточен»
  результат не меньше 0

пример «Оптимальный вариант»
  дано «смен днём» равно 8
  ...
  ожидается результат равен 130
```

Её можно показать заказчику до запуска поиска; примеры исполняются как тесты
(`gasearch check расписание`), а свойства проверяются на каждом вычислении.
Движок не имеет права трогать возвращённое число — единственное, что он с ним
делает, это меняет знак при минимизации.

**Прогон невоспроизводим.** «ГА нашёл решение» — утверждение, которое нельзя
перепроверить, если случайность бралась из `Math.random`. Здесь случайность —
данные: целое семя плюс имя потока. Два прогона с одним семенем совпадают
побайтово, включая историю поколений; это главный тест инструмента, и он
проверяется в том числе между процессами, сравнением stdout двух запусков CLI.

## Как это работает

```
модель .fts ──compile──▶ документ FTS ──executeUtility──▶ число
                              ▲                              │
                              │                              ▼
                     особь = запись полей ◀──── операторы ◀── фитнес
```

Особь — это ровно запись полей входного объекта FTS, без промежуточной
кодировки «хромосома → декодер». Как только между генотипом и входом утилиты
появляется кодировка, читаемость фитнеса теряется: заказчик видит биты вместо
«8 дневных смен». Плата за это — набор типов генов ограничен тем, что умеет
объект FTS: число (с диапазоном и шагом) и признак.

### Воспроизводимость: расщепление потоков

Генератор — splitmix64 на BigInt с явной 64-битной маской (в double 2^53
сломало бы точность). Ключевая деталь не в самом генераторе, а в том, что
единого потока нет вообще.

Если вся эволюция черпает числа из одного потока, результат зависит от **порядка
обращений**: поменяли местами мутацию и кроссовер — при том же семени получили
другой прогон. Поэтому каждая сущность получает подпоток, выведенный из его
**имени**:

```
корень
  └ "начальная популяция" ─ "особь:i"
  └ "поколение:g"
       └ "пара:j"
            ├ "родитель:1" / "родитель:2"
            ├ "кроссовер"
            └ "мутация:1" / "мутация:2"
```

Имя потока — путь в этом дереве, а не порядковый номер обращения. Следствия
проверены тестами:

- популяция из 10 особей совпадает с первыми 10 особями популяции из 40;
- подпоток не меняется от того, сколько чисел израсходовал родительский поток;
- кэширование оценок не влияет на результат — только на счётчик вызовов;
- параллельная реализация дала бы тот же ответ.

Поток кроссовера расходуется даже тогда, когда рекомбинация не происходит:
иначе изменение `--crossover-rate` сдвигало бы всю дальнейшую выдачу.

### Недопустимые особи: штраф, а не отбраковка

Утилита FTS может отказаться считать: нарушение `свойство` завершает
вычисление диагностикой `FTS_UTILITY_PROPERTY`. Такая особь трактуется как
**недопустимая**, а не как ошибка прогона, и получает **штраф** — константу
`-1e6`, заведомо ниже любой достижимой оценки. Отбраковка отвергнута по трём
причинам.

1. **Вырождение.** В модели «расписание» на нулевом поколении недопустимы
   32 особи из 50 (признак «доплата за ночь» бросается честной монетой, а
   ночные смены без доплаты запрещены). Отбраковка означала бы либо ресемплинг
   до посинения, либо популяцию вдвое меньше запрошенной — и то и другое
   ломает воспроизводимость по числу обращений к генератору.
2. **Градуированный штраф взять неоткуда.** FTS сообщает «свойство нарушено»,
   и всё: вычисление прервалось исключением **до** возврата значения, степени
   нарушения не существует. Значит, штраф обязан быть константой; это и есть
   правило Деба «feasibility first», выраженное одним числом.
3. **Недопустимые особи полезны как носители генов.** Особь с идеальными
   числами смен и неверным признаком доплаты — одна мутация до оптимума.
   Отбраковка выбросила бы её.

Отдельно: **любая другая диагностика FTS пробрасывается наружу**
(`FTS_UTILITY_INPUT_TYPE`, `FTS_UNKNOWN_UTILITY` и прочие). Это ошибки движка,
а не свойства особи; штрафовать собственный баг — самый быстрый способ
получить «работающий» поиск, который ищет не то.

Второй канал недопустимости — отдельная утилита-допуск, возвращающая признак
(`Конфигурация допустима`). Она нужна там, где ограничение не торгуется против
качества: бюджет памяти и лимит соединений — это рамки эксплуатации, а не
слагаемое в оценке.

## Запуск

```bash
npm run build                                   # gasearch читает ядро из dist/

node tools/gasearch/bin/gasearch.mjs models
node tools/gasearch/bin/gasearch.mjs check расписание
node tools/gasearch/bin/gasearch.mjs run расписание --seed 42 --generations 100 --population 50
```

JSON — в stdout, диагностики — в stderr, ненулевой код возврата при неудаче:
тот же контракт, что у ядра FTS, `ftsc` и `ftspec`.

Основные параметры: `--utility «имя»`, `--admissibility «имя»`
(`--no-admissibility` отключает), `--direction максимум|минимум`, `--seed`,
`--generations`, `--population`, `--elite`, `--selection турнирная|рулетка`,
`--tournament`, `--crossover равномерный|одноточечный`, `--crossover-rate`,
`--mutation-rate`, `--mutation-sigma`, `--stagnation`, `--history`.

Тесты:

```bash
node --test tools/gasearch/test/*.test.mjs
```

## Модели

### `models/schedule.fts` — распределение смен

Направление — **больше лучше**. Оценка выражена как чистая ценность: польза
от закрытого спроса минус стоимость назначенных смен. Так выбрано потому, что
«минимизировать стоимость» — вырожденная задача (ноль смен), «максимизировать
покрытие» — тоже вырожденная (все смены); разность делает оптимум внутренним.
Известный оптимум **130** посчитан на бумаге и подтверждён полным перебором
в `test/models.test.mjs`.

Два свойства-инварианта: `Вариант не убыточен` (результат не меньше 0) и
`Оценка не превышает потолок` (не больше 200). Первое достижимо нарушить — оно
и порождает недопустимых особей.

### `models/config.fts` — конфигурация системы

Пул соединений, таймаут, размер кэша, политика повторов. Две утилиты:
`Оценить конфигурацию` → число и `Конфигурация допустима` → признак. Границы
поиска в каталоге намеренно шире эксплуатационных рамок из допуска: поиск
обязан **сам** упереться в ограничение, иначе проверялась бы не работа
движка, а честность автора при выборе диапазонов. Известный оптимум **135.5**.

Все проценты в модели — дроби со знаменателем-степенью двойки (25, 12.5,
3.125), чтобы арифметика IEEE-754 была точной и примеры не зависели от
последней цифры мантиссы.

Заголовок `модуль`/`экспортирует` в этих файлах отсутствует: его понимает
сборщик `ftsc`, а `gasearch` отдаёт файл прямо в ядровой `compile`, который
начинает разбор с `категория`. Роль заголовка выполняет комментарий в начале
файла.

альтернатива, а не как рекомендация.

## Граница применимости — честно

**FTS не занимается поиском.** Он оценивает. Утверждение «фитнес проверен»
означает ровно то, что написано: спецификация оценки скомпилирована, прошла
`validate`, её примеры сошлись, а свойства выполнены на каждом вычислении.
Оно **не** означает, что найденное решение оптимально, что модель верно
описывает реальность или что поиск сойдётся.

**Эволюция здесь — обычный код.** В `evolve.mjs` нет ничего доказанного: это
цикл с элитизмом и двумя критериями останова. Тесты сходимости прибиты к
фиксированным семенам и известным оптимумам; на другой задаче поведение будет
другим, и это нормальное свойство стохастического поиска, а не недоделка.

**Для дорогого фитнеса движок не предназначен.** Он рассчитан на фитнес
ценой в микросекунды — вычисление утилиты FTS. Если оценка особи требует
компиляции проекта, прогона тестов или запуска нагрузочного стенда, тысяча
вызовов превращается в часы, и правильный ответ — суррогатные модели
(surrogate-assisted EA): дешёвая аппроксимация фитнеса плюс редкая проверка
настоящей. Здесь этого нет.

**Выразительность фитнеса ограничена языком.** Утилита FTS — это
конъюнкции сравнений поля с константой и сложение слагаемых, включая проценты
от поля. Значит, выразимы кусочно-линейные оценки. Произведения полей,
нелинейности, агрегаты по коллекциям — нет: в FTS нет коллекций, нет
случайности, нет времени. Пространство поиска (границы и шаг) в модели тоже
не выражается и живёт в каталоге движка — это решение о том, где мы согласны
искать, а не бизнес-правило.

**Один критерий.** Многокритериальности (Парето-фронт) нет; несколько целей
приходится сворачивать в одно число прямо в модели, со всеми известными
последствиями такой свёртки.

## Что переедет на flang

`flang` (см. `flang/SPEC.md`) добавляет коллекции, суммы типов и структурную
рекурсию с доказанной завершаемостью. Когда он будет готов, естественно
переедут:

- **кроссовер и мутация** — это чистые преобразования списков полей, ровно то,
  для чего в flang есть `отобразить` и списочные типы. Сейчас они на
  JavaScript только потому, что в FTS нет коллекций;
- **турнирная селекция** — свёртка по популяции с выбором максимума;
- **сама фитнес-функция** станет выразительнее: агрегаты по списку позиций
  снимут ограничение «кусочно-линейная функция фиксированного числа полей».

Не переедет и не должен: генератор случайных чисел (тотальный класс flang —
про детерминированные вычисления, а PRNG уместнее оставить данными на входе)
и цикл поколений с его изменяемым состоянием.
