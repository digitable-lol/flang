# tools/locate

Разметка документа FTS и приведение диагностик к координатам в файле.

Задача одна: ответить, **в какой строке и колонке** находится ошибка. До сих
пор её решали заново в языковом сервере (`tools/ftsls`) и в GitHub Action
(`.github/actions/fts-check`), и решения успели разойтись. Здесь она решена
один раз.

Зависимостей нет — ни внешних, ни на ядро: модуль читает только текст.
Поэтому им пользуется и языковой сервер, работающий с несохранённым буфером,
и Action, работающий с файлом на диске.

## API

```js
import { outline, locate, toLspRange, classifyPath, resolvePath } from "../locate/index.mjs"

const view = outline(source)                       // разметка с координатами
const spot = locate(diagnostic, view, { origin })  // { line, column, endLine, endColumn } | null
```

### `outline(source)`

Строит по исходнику те же индексы, что строит `compile()`, и помнит, из какой
строки и с какой колонки взялся каждый узел. Это разметка, а не второй парсер:
семантики она не знает и ошибок не выносит.

Кроме дерева (`objects`, `morphisms`, `utilities`, `theorem`, `byPath`,
`byLine`) отдаёт:

- `surface` — `"natural"` | `"bracket"` | `"empty"`;
- `kind` — `"document"` | `"functor"` (файл-функтор ftsc ядру не документ);
- `compileSource` — текст без заголовка модуля ftsc, но **с прежней нумерацией
  строк**: заголовок ядру не по зубам, а координаты обязаны остаться
  координатами файла, который открыт в редакторе и виден в диффе.

Координаты узлов — нумерация LSP, с нуля.

### `locate(diagnostic, outline, options)`

Возвращает `{ line, column, endLine, endColumn }` **с единицы** — как `span`
ядра и как аннотации GitHub — либо `null`. Для редакторов есть `toLspRange`.

`options.origin` — происхождение диагностики, `"core"` или `"tool"`.
`options.fallback` — искать ли место для диагностики, у которой его нет вовсе:
`"document"` (по умолчанию) ищет по имени в кавычках из сообщения, `"none"`
не ищет. В редакторе догадка полезна, в CI вредна — там она поставит
аннотацию на случайную строку диффа.

## Четыре источника координат, и ни один не полон

| Источник | Что даёт | Чего нет |
|---|---|---|
| `src/parser.ts` (скобочная поверхность) | настоящий `span` с `line`/`column` | — |
| `src/natural-parser.ts` (отступная) | `path: "строка 13"` | колонок |
| `src/validate.ts` | `path: "$.utilities[0].rules[0].when[0].field"` | строк |
| `testUtilities` | `{ expected, actual }` | координат вообще |

Пятый случай выглядит как третий, но им не является: у `ftsc` и `ftspec`
в `path` лежит настоящий путь к файлу — противоположный смысл того же поля.

## Как отличается путь к файлу от указателя

Не по первому символу. `$` — законный символ имени файла в любой POSIX-файловой
системе, и `ftsc` вполне может сообщить о файле `$.fts` или о пути внутри
каталога `$`; проверка «начинается с `$`» назвала бы их указателями и увела бы
аннотацию на чужую строку.

Признак надёжнее: указатель ядра начинается с `$.` и **одного из шести ключей
канонического документа** (`category`, `structures`, `functors`, `proposition`,
`utilities`, `ts_compat` — см. `src/model.ts`), за которым идёт `.`, `[` или
конец строки. Множество ключей закрыто и задано моделью, а не догадкой: других
корней ядро не порождает. Поэтому `$.utilities[0].examples[1].expected` —
указатель, а `$.fts`, `$/models/a.fts` и `specs/001/model.fts` — файлы.

А когда вызывающий знает происхождение диагностики — а он его знает, ядро он
зовёт сам, `ftsc` запускает отдельным процессом, — угадывать не нужно вовсе:
`options.origin` перекрывает разбор строки. Форма строки остаётся запасным
вариантом, а не основным.

## Инвариант нумерации

Указатель `$.utilities[0].rules[1].when[0].field` не содержит ни имён, ни
координат — только номера. Если разметка пронумерует правила иначе, чем
`compile()`, диагностика молча подчеркнёт не ту строку.

Поэтому инвариант не подразумевается, а проверяется — на **всех** `.fts`
репозитория, сверкой с результатом `compile()`
(`test/invariant.test.mjs`). Проверяется именно точное попадание: сползание
указателя к ближайшему известному предку (нужное само по себе) сделало бы
проверку «разрешился хоть во что-то» всегда истинной.
